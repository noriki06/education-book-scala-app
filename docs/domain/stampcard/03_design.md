# <スタンプ> — 詳細要件定義

呼称は日本語も英語もそろえる（→ 02_analysis.md / naming.md）。

**追加の要求による差分は、節を①②③に分けて示す**（→ 01_requirements.md の「差分の示し方」）。

| 節 | 中身 |
|---|---|
| ① 当初の要求からある分 | 当初の要求だけで決まり、追加の要求では動いていないもの |
| ② 追加の要求で変わった分 | 当初の要求にもあったが、内容や条件が変わったもの |
| ③ 追加の要求で加わった分 | 当初の要求には無かったもの |

**この設計書は③が大半を占める。** リワード（マスタ）・カードの状態・特典の延長期間・発行上限・
中断と再開は、いずれも追加の要求で初めて入った概念のため。

## 用語 — 全体の用語集に追加する呼称
（**呼称をそろえる取り決め。個別の仕様書で用語を定義しない**。追加を申請する分だけ挙げる）

**① 当初の要求からある呼称**

| 呼称（これで統一する） | 何を指すか | 言い換えない |
|---|---|---|
| スタンプ | 注文ごとに1個押され、特典交換に必要な数を数える単位 | ポイント、来店記録 |

**② 追加の要求で意味が変わった呼称**

| 呼称（これで統一する） | 何を指すか | 言い換えない |
|---|---|---|
| リワードカード | リワードが定める数のスタンプを貯める1枚。有効期限を持ち、特典交換の単位になる | スタンプカード、台紙、シート、保有カード |
| 有効期限 | リワードカードが持つ、そのカードにスタンプを押せなくなる日。できた日（＝最初のスタンプを得た日）＋リワードが定める有効期間で確定する。以後延長しないが、中断していたカードを再開すると中断日数だけ加算される | 失効予定日、有効期間 |
| 特典 | 必要スタンプ数を満たしたときに交換できるもの。全額無料／半額／金額割引（円）のいずれか1つをリワードが定める | クーポン、サービス券 |

**③ 追加の要求で加わった呼称**

| 呼称（これで統一する） | 何を指すか | 言い換えない |
|---|---|---|
| リワード | カードの有効期間・必要スタンプ数・特典の内容を定める定義。本部が管理する（→ naming.md） | キャンペーン、プラン、マスタ、種別 |
| 配布期間 | リワードが持つ。この期間中に会員が最初のスタンプを得た場合だけ、そのリワードのカードができる | 開催期間（会員への案内文言としては使うが、モデルの呼称は配布期間で統一する） |
| 特典の延長期間 | リワードが持つ、満杯後の特典の有効期限をカードの有効期限からどれだけ延ばすか（例：＋1ヶ月） | 猶予期間、延長 |
| 特典の有効期限 | 満杯になったカードの特典が使えなくなる日。**カードの有効期限 ＋ リワードが定める延長期間**で求まる。保存しない（→ 付録B） | 特典の期限、失効日 |
| 発行上限 | リワードが持つ、1人が作れるカードの最大枚数。通常スタンプは上限なし、期間限定のリワードは1枚だけ | 上限枚数、最大枚数 |
| 発行済み枚数 | その会員がそのリワードで作ったカードの枚数。期限切れ・使用済みも数える。保存しない | 保有枚数、参加回数 |
| 中断 | 期間限定のリワードに参加したときに、それまで貯めていたカードへのスタンプ付与を止めること。スタンプは消えず、そのまま保持される | 停止、凍結、リセット |
| 中断日 | リワードカードが持つ、中断した日。再開時にここから中断日数を数えて有効期限に加算する | 停止日 |
| 再開 | 期間限定のカードが満杯になるか期限切れになった時点で、中断していたカードにスタンプを押せる状態に戻すこと | 復活、解除 |
| カードの状態 | カードがいまどの段階にあるか。収集中／特典獲得／使用済み／期限切れの4値 | 消化、消費済み |
| 有効スタンプ | 期限内かつ未使用のリワードカードに属するスタンプ。中断中のカードのスタンプも含む | 残スタンプ、使えるスタンプ |

## EntityModel

**3つのモデルはすべて今回追加する。**うち `Reward`（リワード）と `RewardCardStamp`（スタンプの台帳）は
③追加の要求で初めて必要になったもの。`RewardCard`（リワードカード）は当初の要求の「10個たまったら無料」を
形にしたものだが、必要スタンプ数がリワードごとになり、中断日が加わったので②の変更を含む。
**既存モデル（`User` / `Shop` / `Order` / `MenuItem`）には属性を1つも足さない。**

### <リワード（Reward）>

カードの中身を定める定義。本部が決める。今回は作成のみを扱う（→ 付録A）。

```scala
case class Reward(
  id:                   Option[Id],           // 管理 ID（永続化前は None）
  name:                 String,                // 名称（例："通常スタンプ"、"サマースタンプ"）
  distributionStartAt:  Option[LocalDate],     // 配布期間の開始日。None なら常に配布中（通常スタンプ用）
  distributionEndAt:    Option[LocalDate],     // 配布期間の終了日。None なら終了日を定めない
  requiredStampCount:   Int,                   // カードが満杯になる数（例：10）
  cardValidityPeriod:   Period,                // カードができた日から数える有効な長さ（例：Period.ofYears(1)）
  bonusExtensionPeriod: Period,                // 満杯後の特典の有効期限を、カードの有効期限からどれだけ延ばすか（例：Period.ofMonths(1)）
  maxCardsPerUser:      Option[Int],           // 1人が作れるカードの最大枚数。None なら上限なし（通常スタンプ）。期間限定は Some(1)
  menuItemId:           MenuItem.Id,           // 特典の対象商品（MenuItem と *:1）
  bonusType:            BonusType,             // 特典の種類（区分値）
  discountAmount:       Option[Int] = None,    // 割引額（円）。bonusType が IS_AMOUNT_OFF のときだけ Some
  updatedAt:            LocalDateTime = Now,   // データ更新日
  createdAt:            LocalDateTime = Now    // データ作成日
) extends EntityModel[Id]

object Reward:

  type   Id = Id.Repr
  object Id extends Entity.Id[Long]

  /** 特典の種類 */
  enum BonusType(val code: Short) extends EnumStatus[Short]:
    case IS_FULLY_FREE extends BonusType(code = 1) // 全額無料
    case IS_AMOUNT_OFF extends BonusType(code = 2) // 金額割引（円）。discountAmount を使う
```

### <リワードカード（RewardCard）>

```scala
case class RewardCard(
  id:          Option[Id],                   // 管理 ID（永続化前は None）
  userId:      User.Id,                      // どの会員のカードか（User と *:1）
  rewardId:    Reward.Id,                     // どのリワードのカードか（Reward と *:1）。できた時点で決まり、以後変えない
  expiredAt:   LocalDate,                       // このカードの有効期限。できた日 ＋ リワードの有効期間で確定し、以後延長しない（再開時の加算を除く）
                                                //   特典獲得後の特典は、この日 ＋ リワードの bonusExtensionPeriod まで使える
  state:       Status = Status.IS_COLLECTING,   // カードの状態（区分値）
  suspendedAt: Option[LocalDate] = None,        // 中断した日。None なら中断していない。中断中はスタンプを押さない／期限切れにしない
  usedOrderId: Option[Order.Id] = None,         // このカードを特典交換に使った注文。未使用なら None
  usedAt:      Option[LocalDateTime] = None,    // 特典交換に使用した日時。未使用なら None
  updatedAt:   LocalDateTime = Now,             // データ更新日
  createdAt:   LocalDateTime = Now              // データ作成日
) extends EntityModel[Id]

object RewardCard:

  type   Id = Id.Repr
  object Id extends Entity.Id[Long]

  /** カードの状態 */
  enum Status(val code: Short) extends EnumStatus[Short]:
    case IS_EXPIRED    extends Status(code =  -1) // 期限切れ
    case IS_COLLECTING extends Status(code = 100) // 収集中（必要数に満たない）
    case IS_FILLED     extends Status(code = 200) // 特典獲得（必要数を満たし、特典が使える）
    case IS_USED       extends Status(code = 300) // 使用済み
```

### <スタンプ（RewardCardStamp）>

```scala
case class RewardCardStamp(
  id:           Option[Id],          // 管理 ID（永続化前は None）
  rewardCardId: RewardCard.Id,       // どのカードに押されたか（RewardCard と *:1）
  orderId:      Order.Id,            // どの注文で得たか（Order と 1:1）
  shopId:       Shop.Id,             // どの店舗での注文か（集計用。判定には使わない）
  updatedAt:    LocalDateTime = Now, // データ更新日
  createdAt:    LocalDateTime = Now  // データ作成日 ＝ 付与日時（受け渡し完了の時刻）
) extends EntityModel[Id]

object RewardCardStamp:

  type   Id = Id.Repr
  object Id extends Entity.Id[Long]
```

**ここで型が語っていること**

- `Reward` は変更を想定しない（作成のみ）。会員が持つ `RewardCard` は、できた時点の `rewardId` を参照し続ける
- **`RewardCard.rewardId` は不変。** 期間限定のリワードへの参加は、いまのカードを書き換えるのではなく
  **別のカードを新しく作る**ことで表す（→ 付録B）。1枚のカードの必要スタンプ数・特典が途中で変わることはない
- 必要スタンプ数・特典の内容・特典の延長期間を `RewardCard` 自身は持たない。常に `rewardId` をたどって `Reward` から読む
- `RewardCard.expiredAt` は保存する。リワードの有効期間から都度計算しない理由は、再開時の中断日数の加算（あとから動く要素）を表現できないため（→ 付録B）
- **特典の有効期限は保存しない。** `expiredAt` ＋ `Reward.bonusExtensionPeriod` で求まる。
  カードの期限が動けば（再開時の加算）特典の期限も自動で追従する（→ 付録B）
- **`suspendedAt` が中断中かどうかを表す。** 区分値を5値に増やさない。
  中断は `IS_COLLECTING` の内側の区別であり、`state` は「どこまで貯まったか」を表す列のままにする（→ 付録B）
- 中断日数を保存しない。再開時に `今日 - suspendedAt` で求めて `expiredAt` に足し、`suspendedAt` を `None` に戻す
- **カードには期限が2つある。** スタンプを押せる期限は `expiredAt`、特典を使える期限は `expiredAt` ＋ 延長期間。
  どちらを見るかは `state` で決まる（収集中は前者、特典獲得は後者）
- `RewardCard.state` の code は、マイナスが失効、プラスが進行中〜正常終了。100刻みで将来の状態を間に挟める
- `state` は、スタンプの件数・`usedAt` の有無・期限（`expiredAt`、満杯後は ＋ 延長期間）と今日の比較から求まる事実を、まとめて1列にしたもの。
  集計と一覧のために保存する。求まるものを保存しているので、必ずズレる余地がある（→ 型では守れない決めごと、付録B）
- `RewardCardStamp` は有効期限も区分値も持たない、追加専用の台帳
- `Reward.BonusType` は `EnumStatus[Short]` を継承する。DB に保存する区分値なので `Order.Status` と同じ形にそろえる
- `RewardCardStamp` は `userId` を持たない。`rewardCardId` からたどれるため
- `RewardCardStamp` は有効期限を持たない。期限はカード単位で一律なので `RewardCard` が持つ
- 有効スタンプ数を持たない。期限内かつ未使用のカードに属するスタンプを数えれば求まる
- 付与日時の専用カラムを持たない。スタンプは受け渡し完了の瞬間にしか作られないので、`createdAt` と必ず同じ値になる
- `Reward.maxCardsPerUser` が「1人が何枚まで作れるか」。`None` が上限なし、`Some(1)` が1枚だけ。
  **通常と期間限定の違いを配布期間の有無から導出しない。** 発行上限として独立に持つ（→ 付録B）
- 発行済み枚数を `RewardCard` も `Reward` も持たない。`userId` と `rewardId` で数えれば求まる
- `Reward.menuItemId` が特典の対象商品。リワードごとに1つ決まる。**既存の `MenuItem` には何も足さない**
- 半額を表す区分値はない。対象商品が1つに決まるので、割引額（円）で表せる（→ 付録B）

**型では守れない決めごと ①　当初の要求からある分**

- `RewardCardStamp.orderId` は一意。1つの注文に対してスタンプは1個までしか作れない
- `RewardCardStamp.createdAt` が付与日時。**レコードを後から作り直してはいけません。**
  作り直すと付与日時が変わり、有効期限の起点がズレる
- **1回の注文で交換できるのは1枚まで。** 満杯のカードを複数持っていても、特典が使えるのは1個
- **受け渡し後に返品されても `RewardCardStamp` を消さない・取り消さない。**
  スタンプは「商品を受け取った事実」への対価であり、台帳は追加専用に保つ。
  取り消しを表す列も持たない（→ 付録A）

**型では守れない決めごと ②　当初からあるが、追加の要求で条件が変わった分**

- 1枚のカードに属するスタンプは、そのカードの `rewardId` が指すリワードの `requiredStampCount` まで
  （当初は10個の固定だった。リワードごとに変わるため、カードから `rewardId` をたどって読む）
- `usedAt` を書き込めるのは、必要スタンプ数を満たしていて **特典の有効期限内**
  （`expiredAt` ＋ 延長期間 ≧ 今日）のカードだけ
  （当初は期限が一律だったので「期限内か」だけで足りた。延長期間が入って基準が2つになった）
- 期限切れのカードと交換済みのカードは、あとから更新しない（一度切れたら戻らない）。中断の対象にもならない
  （当初は「期限切れ」だけだった。交換済み・中断が加わって対象が増えた）

**型では守れない決めごと ③　追加の要求で加わった分**

リワード（マスタ）・カードの状態・特典の延長期間・発行上限・中断と再開に関わるもの。

- `state` と実体は必ず一致させる。
  `IS_COLLECTING` ⟺ スタンプ件数 < 必要数、`IS_FILLED` ⟺ 件数 = 必要数 かつ `usedAt` が `None`、
  `IS_USED` ⟺ `usedAt.isDefined`。
  `IS_EXPIRED` の条件は **直前の状態によって基準日が変わる**。
  収集中だったカードは `expiredAt` < 今日、特典獲得だったカードは `expiredAt` ＋ 延長期間 < 今日。
  更新は「スタンプを押す」「使用済みにする」「差し戻す」「失効させる」の操作関数にまとめ、個別に書き換えない
- **判定は `state` だけに頼らない。** 期限切れの書き込みはバッチで行うため、
  バッチが落ちた日は `state` が実態より遅れる。特典が使えるかの判定は `state` と日付の両方を見る
- スタンプを1件足したら、必要数に達したかを確認して `state` を更新する
- `usedOrderId` と `usedAt` は必ず両方埋まるか、両方 `None`。片方だけの状態は業務上ありえない
- **特典が使えるかを `expiredAt` だけで判定してはいけない。**
  `IS_FILLED` のカードは `expiredAt` を過ぎていても、`expiredAt` ＋ `Reward.bonusExtensionPeriod` までは使える。
  `expiredAt` 単独で切ると、獲得済みの特典を延長期間の分だけ早く失効させてしまう
- 延長期間が効くのは満杯になった後だけ。`IS_COLLECTING` のカードにスタンプを押せる期限は `expiredAt` のままで、
  延長期間は含めない（延長期間はスタンプを貯める猶予ではない）
- `Reward.bonusExtensionPeriod` は 0 以上。`Period.ZERO` なら延長なし（特典の期限＝カードの期限）
- `Reward.discountAmount` は `bonusType` が `IS_AMOUNT_OFF` のときだけ `Some`。それ以外は `None`
- `Reward.discountAmount` は、対象商品の価格を超えない（割引後がマイナスにならない）
- **対象商品の価格を改定したら、`discountAmount` も見直す。**
  半額のつもりで入れた金額は、価格が変わると半額でなくなる（→ 付録B）
- 特典を適用できるのは、注文の中の `Reward.menuItemId` の商品1点だけ
- `Reward` の配布期間は、開始と終了が両方 `Some` なら 開始 ≦ 終了
- 新しく作る `RewardCard` の `rewardId` は、その時点で配布期間内のリワードでなければならない
- 配布期間が終わっても、すでにできているカードは有効期限まで使える。終わるのは新規作成だけ
- `Reward.maxCardsPerUser` は `Some` なら 1 以上。0 や負の値は許さない
- **会員1人が持てる同一リワードのカードは `maxCardsPerUser` 枚まで。** `None` なら無制限。
  数えるのは `userId` と `rewardId` が一致する `RewardCard` の全件で、
  **期限切れ・使用済みも枚数に含める**（含めないと、失効や交換のあとに2枚目が作れてしまう）
- **期間限定のリワードへの参加を提示できるのは、そのリワードの発行済み枚数が上限未満のときだけ。**
  **いま貯めているカード1枚だけを見て判定してはいけない。** 参加後にできた期間限定のカードは
  満杯や期限切れになって収集中から外れるため、過去のカードを含めて数えないと未参加と誤判定する
- `RewardCard.rewardId` は作成時に決めたら変更してはいけない
- **カードは作られたら `rewardId` が変わらない。これが参加の記録そのものである。**
  期間限定のカードが1行できていれば、それが「この開催に参加した」という消えない事実になる
- **スタンプを押せるカードは、`suspendedAt` が `None` かつ `IS_COLLECTING` かつ期限内のもの。常に0枚か1枚。**
  中断中のカードには押さない
- **中断中のカードは常に最大1枚。** 中断中にさらに別のリワードへ参加することはできない
- **中断中のカードを期限切れにしてはいけない。** 日次バッチの対象から `suspendedAt` が `Some` のカードを除く。
  除かないと、中断させられている間に失効し、中断日数を加算する機会が永久に失われる
- 中断と再開は必ず対で起こる。中断したカードは、期間限定のカードが満杯になるか期限切れになった時点で必ず再開する。
  再開しないまま放置される状態は業務上ありえない
- 再開時の加算は `今日 - suspendedAt` の日数を `expiredAt` に足す形で行う。カードを作り直さない
- `suspendedAt` が `Some` のカードは `state` が必ず `IS_COLLECTING`。
  満杯・使用済み・期限切れのカードを中断することはない
- 部分的に埋まった（未使用・必要数未満の）カードは、貯めている1枚と中断中の1枚を合わせて**最大2枚**。
  満杯後に届いたスタンプは、中断中のカードがあればそれを再開して押し、なければ新しいカードに押す

## 区分値の考え方

この節は全体が③（追加の要求で加わった分）。カードの状態を区分値にしたのは
「管理側で特典の利用実績を集計したい」という追加の要求から。

カードの状態は4値。管理側から「特典の利用実績を集計したい」という要求があるため、
求まる事実をあえて1列にまとめて保存する（→ 付録B）。

| 値 | 意味 | 何から求まるか |
|---|---|---|
| `IS_COLLECTING` | 収集中 | スタンプ件数 < リワードの必要数 |
| `IS_FILLED` | 特典獲得（必要数を満たし、特典が使える） | 件数 = 必要数 かつ 未使用 |
| `IS_USED` | 使用済み | `usedAt` が入っている |
| `IS_EXPIRED` | 期限切れ | 収集中は `expiredAt` < 今日、特典獲得は `expiredAt` ＋ 延長期間 < 今日 |

**保存する以上、実態とズレる余地がある。** とくに `IS_EXPIRED` は日付が変わった瞬間に発生するため、
日次バッチで書き込む。バッチが落ちた日は `state` が実態より遅れる。

そのため **特典が使えるかの判定は、`state` だけでなく日付も必ず見る。**
このとき見る日付は `state` によって違う。**収集中は `expiredAt`、特典獲得は `expiredAt` ＋ 延長期間。**

| state | 見るべき期限 | 期限が今日以降 | 期限が今日より前 |
|---|---|---|---|
| `IS_FILLED` | `expiredAt` ＋ `Reward.bonusExtensionPeriod` | **○ 特典が使える** | × 失効。`state` が `IS_EXPIRED` でなくても使わせない |
| `IS_COLLECTING` | `expiredAt` | × まだ必要数に届いていない（スタンプは押せる） | × 失効。スタンプも押せない |
| `IS_USED` | — | × 交換済み | × 交換済み |

**`IS_FILLED` の行を `expiredAt` 単独で判定してはいけない。** 延長期間の分だけ早く失効させてしまう。

集計するときは `state` だけで足りる（バッチ後の値を見るため）。
判定するときは両方見る。**役割が違う。**


## <複数のエンティティにまたがる判定ルール>

**この節は全体が③（追加の要求で書き換わった分）。** リワード・配布期間・発行上限・特典の延長期間・
中断と再開は、いずれも追加の要求で入った概念のため、当初の要求のまま残っているルールがない。

### いつ何をするか

| きっかけ | すること |
|---|---|
| 本部がリワードを決めた | `Reward` を1行追加する（→ 付録A、作成のみ）。期間限定なら `maxCardsPerUser` に `Some(1)` を入れる |
| 注文を確定した（特典利用あり） | `IS_FILLED` かつ `expiredAt` ＋ 延長期間 が今日以降のカードのうち最も古い1枚を `IS_USED` にし、`usedOrderId`・`usedAt` を書き込む（1注文につき1枚まで） |
| 特典を使った注文がキャンセルされた | その `usedOrderId` を持つカードを `IS_FILLED` に戻し、`usedOrderId`・`usedAt` を `None` にする |
| 受け渡し前に注文がキャンセルされた | 何もしない。スタンプはまだ押されていない |
| 受け渡し後に返品された | 何もしない。押したスタンプは取り消さない |
| 商品を受け渡した（特典対象以外の商品を含む注文） | 「どのカードに押すか」（次項）に従ってスタンプを1件記録し、必要数に達していれば `state` を `IS_FILLED` にする |
| 日付が変わった | バッチで、`expiredAt` を過ぎた `IS_COLLECTING` のカードと、**`expiredAt` ＋ リワードの延長期間を過ぎた** `IS_FILLED` のカードを `IS_EXPIRED` にする。`IS_FILLED` を `expiredAt` だけで失効させない。**`suspendedAt` が `Some` のカードは対象外** |
| 会員が期間限定のリワードへの参加を選んだ | いま貯めているカードに `suspendedAt` ＝今日 を書き込み、期間限定のカードを1行作る（`expiredAt` ＝今日 ＋ 期間限定の `cardValidityPeriod`） |
| 期間限定のカードが満杯または期限切れになった | 中断中のカードがあれば再開する。`expiredAt` に `今日 - suspendedAt` の日数を加算し、`suspendedAt` を `None` にする |

### どのカードに押すか

1. **中断中のカードを再開できるか確認する。** `suspendedAt` が `Some` のカードがあり、
   その会員に「`suspendedAt` が `None` かつ `IS_COLLECTING` かつ期限内」のカードが1枚もなければ、
   中断中のカードを再開する（`expiredAt` に `今日 - suspendedAt` を加算し、`suspendedAt` を `None` に）。
   期間限定のカードが満杯や期限切れになった直後は、ここで通常のカードが戻ってくる。
2. その会員の、`suspendedAt` が `None` かつ `expiredAt` が今日以降かつ `state = IS_COLLECTING` のカードを探す
   （常に0枚か1枚）。
3. 現在配布期間内の期間限定のリワードがあり、**その会員のそのリワードの発行済み枚数が `maxCardsPerUser` 未満**で、
   かつ中断中のカードがまだ1枚もなければ、会員にその開催への参加を選べるようにする。
   - 参加を選べば、2で見つかったカードに `suspendedAt` ＝今日 を書き込んで中断し、
     期間限定のカードを新しく1行作る（`rewardId` ＝期間限定のリワード、
     `expiredAt` ＝今日 ＋ 期間限定の `cardValidityPeriod`、`state` ＝ `IS_COLLECTING`）。
     **スタンプは0個から数え直す。** この時点で発行済み枚数が1枚になり、`Some(1)` なら以後この開催には参加できない。
   - 2でカードが見つからなかった場合は、中断するものがないので期間限定のカードを作るだけでよい。
   - 参加しなければ何も変えない。同じ開催中は次回以降選択画面を出さない。
4. 貯める先のカードにスタンプを1件記録する。
   まだカードがなければ新しく作る。リワードは **通常のリワード**（配布期間内であることを確認する）
   （`expiredAt` ＝今日 ＋ 通常のリワードの `cardValidityPeriod`、`state` ＝ `IS_COLLECTING`）。
5. 記録した結果、スタンプ件数がリワードの `requiredStampCount` に達していれば、`state` を `IS_FILLED` にする。
   このカードが期間限定のカードだった場合、次の注文では1で通常のカードが再開される。

**発行済み枚数の数え方**：`userId` と `rewardId` が一致する `RewardCard` の全件。
`state` は問わない（期限切れ・使用済みも数える）。これが「1開催1枚」を保証している唯一の根拠なので、
`state` で絞り込んではいけない。

**中断したカードのスタンプは1件も動かさない。** `RewardCardStamp.rewardCardId` は書き換えないため、
再開したときに中断前の件数がそのまま残っている。8個貯めて中断したカードは、再開後も8個から続く。

### 有効スタンプ数の求め方

1. その会員のカードのうち、次のいずれかを満たすものを集める
   - `state` が `IS_COLLECTING` で、`expiredAt` が今日以降
   - `state` が `IS_COLLECTING` で、`suspendedAt` が `Some`（中断中。期限は判定しない）
   - `state` が `IS_FILLED` で、**`expiredAt` ＋ リワードの延長期間**が今日以降
2. それらのカードに属するスタンプの件数を合計する

`IS_FILLED` のカードが1枚でもあれば、特典が使える。

**1の条件を `expiredAt` だけで書くと、延長期間中の満杯カードが集計から漏れる。**
会員のアプリに「特典が使える」と出ているのに有効スタンプ数が0、という食い違いが起きる。

**中断中のカードのスタンプも数える。** 中断は預かっている状態であって、失効ではない。
ただし会員の画面では合計を1つの数字で見せると「8個」と「期間限定3個」が混ざって意味が通らないため、
**表示はカードごとに分ける**（貯めているカード／中断中のカード）。集計に使う合計値とは役割が違う。


## 置き場所（コンテキスト）

**リワード（`Reward`）の判断：`common` に置く。**

理由：本部が管理し、業務の操作（注文）のたびには変わらず、`RewardCard` から参照される側にある。
common の3条件をすべて満たす（→ 02_analysis.md）。

**リワードカード・スタンプの判断：既存の `sales` コンテキストに置く。**

理由：日常的に書き換えるのは会員と店舗スタッフで、`Cart` / `Order` と同じ人・同じ画面・同じ頻度。
書き換えるきっかけも注文の確定・受け渡しであり、注文フローの一部として動く。

`RewardCard` が `Reward.Id` を持つのは `sales → common` の参照であり、逆流ではない
（`OrderItem` が `MenuItem.Id` を持つのと同じ形）。

`udb` には置けない。`Order.Id` を参照する側のため、`udb → sales` の逆流が生まれる。
既存の参照はすべて `sales` または `shop` が始点で、`udb` は参照される側にある。

# 付録A：今回やらないこと

（下記のうち、リワード・発行上限・中断まわりはすべて③追加の要求で生まれたスコープ外項目）

- **有効期限が近いことのお知らせ通知。** 会員がアプリを開いたときに有効期限を表示するだけにする
- **スタンプの譲渡・合算。** 会員間で受け渡す仕組みは作らない
- **1注文で複数個のスタンプを押す運用。** 金額や点数に応じた加算はしない
- **期限切れカード・スタンプの物理削除。** 期限切れのカードは数えないだけで、レコードは残す
- **返品によるスタンプの取り消し。** 受け渡し後に返品されても取り消さないと決めたため、
  取り消しを表す列も操作も作らない。返品でスタンプが残ることを問題視する要求が出た時点で見直す
- **店舗ごとのスタンプ発行数の集計画面。** `shopId` は持つが、画面は作らない
- **無料特典を「権利」として記録すること。** 有効スタンプの件数から判定する
- **データ移行・手動でのスタンプ遡及付与。** 付与日時は `createdAt` のみで表す前提を崩さない。
  発生したら `stampedAt` を専用カラムとして分ける（→ 付録B）
- **スタンプ以外の特典（誕生日特典など）。** リワード（`Reward`）の形はそのまま使える見込みだが、今回は作らない
- **リワードの編集・削除。** 本部による作成のみを扱う。配布期間の変更や特典内容の修正は今回のスコープ外
- **複数の期間限定のリワードが同時に配布期間中であること。** 重ならない前提で進める
- **期間限定のリワードへの参加を取り消す（オプトアウトする）機能。** 一度参加を選んだら、その開催中は解除できない
- **同じ開催への再参加。** 期間限定のカードは1開催1枚。使い切っても期限切れになっても2枚目は作らない
- **中断中にさらに別のリワードへ参加すること。** 中断中のカードは常に最大1枚。入れ子の中断は作らない
- **中断を会員が任意に解除すること。** 再開のきっかけは、期間限定のカードが満杯または期限切れになったときだけ
- **期間限定のリワードで2枚以上を許す運用。** `maxCardsPerUser` の値を変えれば表せるが、今回は `Some(1)` 固定
- **発行されたら消える実際のクーポン券。** `Coupon` という語は空けておく（→ naming.md）


# 付録B：判断の記録

判断を①②③に分けて並べる。①は追加の要求では動いていないもの、②は当初の判断が覆ったもの、
③は追加の要求で初めて必要になったもの。

## ① 当初の要求の範囲で決めたこと

#### 付与日時を専用のカラムで持つか、`createdAt` で足りるか

判断は `createdAt` で足りる。専用のカラムは作らない。

スタンプは受け渡し完了の瞬間にしか作られない。付与のタイミングとレコード作成のタイミングが
常に一致するため、専用カラムを足しても `createdAt` と同じ値が入るだけになる。

**代償：データ移行や手動付与（遡っての付与）が発生すると、この前提が崩れる。**
その場合はレコード作成日時と付与日時が一致しなくなるため、`stampedAt` を専用カラムとして分ける必要がある。
今回はどちらも扱わない（→ 付録A）。

#### 使用済み日時をスタンプに持つか、リワードカードに持つか

判断はカードに持つ。

交換は必要スタンプ数まとめての1回なので、スタンプに持つと同じ値が複数行に重複する。
1枚のカードにつき交換は1回だけなので、カードの属性として過不足なく収まる。

結果として `RewardCardStamp` から `Option` が消え、`id` 以外はすべて必須になった。
スタンプは「いつどの注文で得たか」だけの台帳になり、状態を持たない。

#### スタンプの消費と付与を、同じタイミングにするか

判断は揃えない。消費は注文確定時、付与は受け渡し完了時。

付与を支払い完了時にすると、商品を受け取っていない注文でスタンプが増え、
受け取らずに特典だけ取れてしまう。付与は「受け取った事実」への対価なので、受け渡しの後になる。

消費を受け渡し時にすると、必要数を持った状態で2件注文したときに両方へ特典を適用できてしまう。
消費は「使う宣言」なので、注文確定の時点で押さえる。

この非対称の結果、キャンセルによるスタンプの無効化が不要になった（受け渡し前のスタンプは存在しない）。

#### 「無料特典」をエンティティにするか

判断は作らない。有効スタンプ数が、現在のリワードが定める必要数以上あるかで判定する。

エンティティにすれば「必要数を満たした」という権利確定の事実を保存でき、その後スタンプが失効しても特典を残せる。
しかし要件定義で「特典もカードと同様、カードの有効期限＋延長期間で使えなくなる」と確認しているため、
カードが失効したら特典も消えてよい。

特典の内容が「全額無料・半額・金額割引（円）」の3種類に増えたが、これは `Reward` の属性
（`bonusType` / `discountAmount`）を増やすだけで表現できた。特典ごとに件数や残額を管理する必要がないため、
エンティティを新設する理由には至らない。

**代案：`Coupon` を新設する。** リワードを `Reward` と名付けたことで、誕生日特典のようなスタンプを使わない発行理由も
同じ枠に収まる見込みが立った（→ naming.md）。それでも表現できない発行理由（発行されたら消える実際のクーポン券など）
が要件に入った時点で、この代案を検討する。


## ② 当初の判断が、追加の要求で変わったこと

#### リワードカードをエンティティにするか、有効期限を計算で求めるか

判断は `RewardCard` を作り、有効期限を保存する。

要件で「できた日＋リワードの有効期間で確定し、以後延長しない」に確定した（→ 01_requirements.md）。
一律の値ということは、そのカードの期限はできた時点で決まる1つの値になる。
1つしかない値を10行に分散させるのは重複であり、判定もカードの2列を見るだけで終わる。

もし要件が「スタンプごとに押した日から1年」だったら、期限は1件ずつ違う値になるので `RewardCardStamp` が持つのが正しく、
カードは不要だった。**この分岐が `RewardCard` を作った理由のすべてである。**

#### リワードカードを会員につき1枚にするか、複数枚にするか

判断は複数枚。必要スタンプ数を満たして満杯になったら、次のスタンプは新しいカードに押す。

1枚だと、期限切れの後に来店したとき `expiredAt` が未来へ更新され、
失効したはずのスタンプが復活してしまう。複数枚なら、期限切れのカードを更新しないだけで済む。
期間限定への参加を「別のカードを作る」形にできるのも、複数枚を許したからである。
古いカードのスタンプには構造上たどれないので、復活が起こりえない。

代償として、押す先のカードを毎回決める処理と、「1枚はリワードが定める必要数まで」という型で守れない制約が増えた。

#### カードの有効期限を、できた時点で固定するか、注文のたびに延長するか

判断は固定する。できた日＋リワードが定める有効期間で確定し、以後は延長しない
（期間限定のリワードへの参加を除く）。

注文のたびに延長する案もあった。しかしリワードごとに「この期間だけ有効」と定めたい以上
（→ 01_requirements.md の追加要求）、注文ごとに動く延長ロジックはその定義を壊す。
また延長する設計では、満杯のカードを延長し続けると特典が永久に消えなくなるため、
「満杯後だけ延長を止める」という例外が必要になる。固定なら、満杯かどうかで扱いを分ける理由がない。

例外として期間限定のリワードへの参加だけは加算する。これは注文のたびに自動で起こるものではなく、
会員が選んだときに一度だけ起こる、別種の操作だからである。

**固定したことの帰結として、特典を使える締切も固定される。**
特典の有効期限は「カードの有効期限 ＋ 延長期間」なので、満杯になった日には左右されない。
つまり **早く貯めた会員ほど、特典を使える残り期間が長くなる**（→ 01_requirements.md で確認済み）。
これは意図した挙動であり、早く貯める動機づけになる。
満杯になった日から数える案（例：満杯後1ヶ月）だと、遅く貯めた会員のほうが実質の期限が延びてしまう。

#### 「使用済み」を区分値にするか、日時の有無で表すか

判断は4値の区分値（`state`）を持ち、`usedAt` も残す。

`state` の4値は、どれも他のデータから求まる。
`IS_COLLECTING` / `IS_FILLED` はスタンプの件数とリワードの必要数から、`IS_USED` は `usedAt` の有無から、
`IS_EXPIRED` は期限（収集中は `expiredAt`、特典獲得は `expiredAt` ＋ 延長期間）と今日の比較から。
**求まるものは保存しない**というこれまでの方針からは外れる。

それでも保存するのは、管理側から「特典の利用実績を集計したい」という要求が出たため。
件数を数えたり日付を比べたりせず、1列を GROUP BY するだけで済む。
集計・一覧表示のための列（`state`）と、個々の記録のための列（`usedOrderId` / `usedAt`）で役割を分ける。

代償は2つある。

**書き忘れ。** スタンプを1件足したら `state` も更新する、使用済みにしたら `state` も変える、
という対応を人手で守ることになる。片方だけ書き換えると矛盾する。
更新経路を操作関数に絞ることで対応する（→ 型では守れない決めごと）。

**`IS_EXPIRED` のズレ。** 期限切れは日付が変わった瞬間に発生するので、書き込むには日次バッチが要る。
バッチが落ちた日は `state` が実態より遅れ、失効したはずのカードが `IS_FILLED` のまま残る。
そのため **特典が使えるかの判定では `state` だけに頼らず、`expiredAt` も必ず見る。**
集計は `state` だけで足りる（バッチ後の値を見るため）。判定と集計で見るものが違う。

#### 「収集中」と「特典獲得」を区分値で持つか、件数から判定するか

判断は区分値で持つ。スタンプを押すたびに件数を確認し、必要数に達したら `IS_FILLED` にする。

件数はいつでも数えられるので、持たなくても判定できる。しかも必要数はリワードごとに違うため、
`rewardId` をたどって `requiredStampCount` を読む必要があり、`state` があれば1列で済む。

「特典が使えるカードを持っている会員は何人か」という集計も、区分値なら即座に出る。
代償は、スタンプを足すたびに `state` の更新が必要になること。

#### 期限切れを書き込むか、判定だけにするか

判断は書き込む。日次バッチで `IS_EXPIRED` にする。ただし判定では期限も併せて見る。

書き込まない案（`expiredAt` と今日を比べるだけ）のほうが、バッチが不要で事故らない。
比べれば分かるものは保存しない、という原則にも合う。

それでも書き込むのは、`state` を4値にして集計を1列で済ませると決めたためである。
`IS_EXPIRED` だけ保存しないと、集計のたびに日付比較が混ざり、区分値を作った意味が薄れる。

代償はバッチ落ちのリスク。これを消せないので、**判定は `state` と期限の両方を見る**ことで、
バッチが遅れても失効したカードが使われないようにする。
バッチは表示を速くするためのもので、正しさの根拠は `expiredAt`（特典獲得なら `expiredAt` ＋ 延長期間）に置く。


## ③ 追加の要求で新しく判断したこと

#### リワードを独立した定義にするか、`RewardCard` の属性として複製するか

判断は独立させる。`Reward` を新設し、`RewardCard` は `rewardId` で参照する。

要件で「特典の種別ごとに有効期限を設定したい」と確認している
（→ 01_requirements.md）。複数の `RewardCard` が同じリワードの設定（必要数・有効期間・特典）を共有するため、
属性として複製すると同じ設定が `RewardCard` の行数だけ重複し、リワードの設定を直そうとすると全行の更新が必要になる。
独立させれば、`Reward` の1行を直すだけで済む（今回は作成のみのため実際には更新しないが、
将来変更を許すとしても影響範囲が閉じる）。

#### 特典の対象商品を、リワードの属性にするか、商品の属性にするか

判断はリワードの属性にする。`Reward.menuItemId` で対象商品を1つ指定する。

商品側にフラグ（`isBonusEligible`）を持たせる案もあった。リワードが何個に増えても判定が変わらない利点がある。
しかしその場合、対象商品が複数になりうる。すると「どの商品に適用するか」を注文ごとに選ぶ必要が出るうえ、
価格が違う商品に同じ特典を当てることになり、半額や金額割引が商品ごとに違う額になる。

リワードが対象商品を1つ持てば、特典の内容が金額で確定する。
**既存の `MenuItem` に何も足さずに済む**ことも大きい。今回の変更は `common` と `sales` に閉じる。

代償は、同じ商品を対象にしたリワードが増えると `menuItemId` が重複すること。
ただしリワードはキャンペーン単位でしか増えないため、重複の量はたかが知れている。

#### 「半額」を区分値で持つか、金額割引で表すか

判断は金額割引で表す。`IS_HALF_PRICE` は作らない。

対象商品が1つに決まったため、半額は「その商品の価格の半分」という具体的な金額として書ける。
590円の商品なら `discountAmount = 295`。区分値が1つ減り、割引の計算経路も1つになる。

代償は、**価格改定で半額でなくなること。** 590円が650円になれば、295円引きは半額ではなく約45%引きになる。
率で持てばこの問題は起きないが、「割引は円で」と確認しているため（→ 01_requirements.md）採らない。
価格を改定したら `discountAmount` も見直す、を型では守れない決めごとに書く。

「30%引き」のような率のバリエーションが要件に入った時点で、割引率の列を新設して見直す。

#### 特典の有効期限を保存するか、カードの有効期限から計算するか

判断は計算する。`RewardCard` に列を足さず、`expiredAt` ＋ `Reward.bonusExtensionPeriod` で都度求める。

保存する案もあった。判定のたびにリワードをたどらずに済み、1列の比較で終わる。

それでも計算にするのは、**`expiredAt` が後から動くため**である。
中断していたカードを再開すると `expiredAt` に中断日数が加算される。
保存すると、そのたびに追従して書き換える処理が必要になり、書き忘れれば矛盾する。
`state` で同じ代償（書き忘れ）を既に1つ抱えているので、2つ目は増やさない。

代償は、判定のたびに `Reward` を読む必要があること。
ただし判定の場面では必要スタンプ数・特典の内容を読むために `Reward` を引く必要があり、
延長期間はそのついでに読める。追加のクエリは発生しない。

`state` と違って集計の要求もない。「特典の期限が切れた件数」は `IS_EXPIRED` で数えられる。

#### 発行上限を枚数で持つか、真偽値で持つか、配布期間の有無から導出するか

判断は枚数（`maxCardsPerUser: Option[Int]`）。`None` が上限なし、`Some(n)` が n 枚まで。

**真偽値（`isOneCardOnly: Boolean`）の案。** いまの要件（上限なし／1枚だけ）はこれで足りる。
しかし「2枚まで」というキャンペーンが来た時点で列を作り直すことになる。
枚数で持てば値を変えるだけで済み、`Option` が「上限なし」を素直に表せる。

**配布期間の有無から導出する案（`distributionEndAt` が `Some` なら1枚だけ）。** 列が増えない利点がある。
却下したのは、**「終了日がある」と「1枚だけ」という別の性質を1つの値に相乗りさせるため**である。
「終了日はあるが何枚でも貯めていい年末キャンペーン」を作りたくなったとき、終了日を消すしか手がなくなる。
配布期間はカードを作れる期間の話で、発行上限は1人が持てる枚数の話であり、動く理由が違う。

代償は列が1つ増えたこと。ただし本部がリワードを決めるときに1つ選ぶだけで、判定経路は増えていない。

#### 期間限定のリワードを何枚まで作れるようにするか

判断は1開催1枚。`maxCardsPerUser` に `Some(1)` を入れ、満杯になったら次のスタンプは通常リワードの新しいカードに押す。

通常スタンプと同じく何枚でも作れる案もあった。よく来る会員がキャンペーン中に2枚3枚と貯められる。

それでも1枚に限るのは、**期間限定の特典が「開催に参加した会員への1回の特典」だという性質を持つため**である。
何枚でも作れると、開催期間が長いほど特典の配布量が読めなくなり、原価の見積もりが立たない。
1枚に限れば、参加者数がそのまま配布上限になる。

副産物として、参加済み判定が単純になった。
判定は「そのリワードのカードを過去に作ったか」の1点で済み、
いま貯めているカードが何かにも、そのカードが満杯か期限切れかにも依存しない。
`rewardId` が不変になったこととあわせて、参加の事実は一度作られたら動かない記録になった。

代償は、判定のたびに発行済み枚数を数えるクエリが増えること。
`userId` と `rewardId` の複合インデックスがあれば件数だけで済む。

#### 期間限定のリワードへの参加を、いまのカードのリワードを切り替える形にするか、新しいカードを作る形にするか

判断は新しいカードを作る。いまのカードは中断して保持し、期間限定のカードはスタンプ0個から始める。

**切り替える案を先に採り、あとで覆した。** 切り替え案は「進行中のカードは常に1枚」という制約を素直に守れて、
それまでのスタンプもそのまま持ち越せる。カードは1行のまま、必要スタンプ数と特典の参照先だけが変わる。

覆した理由は3つある。

**1つ目。1枚のカードの途中で必要スタンプ数が変わる。** 通常（必要10）で9個貯めた会員が
サマースタンプ（必要8）に参加すると、切り替えた瞬間に 9 > 8 になり、
「1枚のカードに属するスタンプはリワードの必要数まで」という決めごとを破る。
必要数が減る方向の切り替えを禁止する、超過分を繰り越す、といった例外が必要になる。

**2つ目。会員から見て何が起きたか分からない。** 貯めていた9個が、参加した瞬間に別の特典の9個に化ける。
「通常のハンバーガー無料まであと1個」だったものが「サマーの半額」に置き換わり、元には戻せない。

**3つ目。`rewardId` が可変になる。** 参加の記録を可変な列から数えることになり、
オプトアウトや複数同時開催を将来入れた時点で参加済み判定が壊れる。

新しいカードを作る案は、この3つがすべて消える。必要スタンプ数は1枚のカードの中で不変になり、
通常のカードは中断されるだけで内容が変わらず、`rewardId` は不変列に戻る。
参加の事実は「期間限定のカードが1行あるかどうか」で表せる。

代償は「進行中のカードは常に1枚」を「**貯めているのは1枚、中断中を1枚まで持てる**」に緩めたこと。
`suspendedAt` という列と、中断・再開という操作が増えた。

**「中断中は1枚まで」は型（テーブル構造）の制約ではない。** `suspendedAt` は `RewardCard` の各行が個別に持つ列なので、
複数行が同時に `suspendedAt` を持つこと自体は構造上できる。「1枚まで」は
**「期間限定のリワードは同時に1つしか開催しない」というスコープ限定（→ 付録A）に基づくアプリ側の決めごと**であり、
その前提が崩れたら列を増やさずにルールだけ緩めればよい（→ 判断が変わる条件）。

#### 中断を区分値で表すか、中断日で表すか

判断は中断日（`suspendedAt: Option[LocalDate]`）。`state` に5つ目の値は作らない。

`IS_SUSPENDED` を足す案もあった。`state` 1列を見れば状態が分かる。

採らなかったのは、**再開時に「中断していた日数」が必要になるため**である。
区分値だけでは日数が計算できず、結局は中断日を別に持つことになる。
中断日を持てば中断中かどうかも `Option` の有無で分かるので、区分値は要らない。

`state` の役割にも合う。`state` は「どこまで貯まったか」の4段階で、集計のために置いた列である。
中断はその内側の区別（`IS_COLLECTING` のうち止まっているもの）なので、段階を増やす話ではない。
「中断中の枚数」を数えたければ `suspendedAt IS NOT NULL` で足りる。

代償は、収集中のカードを探すときに毎回 `suspendedAt` の条件が付くこと。
これを書き忘れると中断中のカードにスタンプが押されるので、決めごとに明記した。

#### 中断していた分の有効期限を、どう補償するか

判断は再開時に「実際に中断していた日数」（`今日 - suspendedAt`）を `expiredAt` に加算する。

**開催期間の長さを参加時に一括で足す案。** 計算が1回で済み、`suspendedAt` を持たなくてもよい。
採らなかったのは、期間限定のカードが開催の途中で満杯になったときに補償が過大になるためである。
2ヶ月の開催で最初の2週間で貯め切った会員に2ヶ月ぶん足すことになる。

**補償しない案。** 列も処理も増えない。採らなかったのは、参加が損になるためである。
キャンペーンに乗ったせいで通常カードの期限が実質的に縮むなら、貯め込んでいる会員は参加しない。

実際の日数で補償すれば、中断は会員にとって完全に中立になる。止まっていた分だけ後ろへずれる。

代償は `suspendedAt` を持つことと、**中断中のカードを失効させてはいけない**という決めごとが増えたこと。
中断中に期限が来て `IS_EXPIRED` になると、加算する機会が永久に失われる。
日次バッチから `suspendedAt` が `Some` のカードを除くことで対応する。

#### 使った注文の ID を持つか

判断は `usedOrderId` を持つ。

`state` や `usedAt` だけでは、特典を使った注文がキャンセルされたときに戻すカードを特定できない。
問い合わせで「この特典はどの注文で使ったか」に答えるためにも必要になる。

#### リワードとリワードカードを、同じ語根（`Reward`）でつなぐか、別の語根にするか

判断は同じ語根でつなぐ。`Reward` / `RewardCard` / `RewardCardStamp`。

`Stamp` を語根にすると、最上位と中間の両方に `Stamp` が現れ、深い階層ほど名前が短くなる。
`Cart` < `CartItem` < `CartItemOption` とは逆向きの並びになり、階層を取り違えやすい。
`Stamp` を末端の1語に限定し、上位2階層を別の語根から組み立てることで、深いほど長くなる並びに直した。

日本語の呼称も英語に合わせた。要求文にある語は「スタンプ」だけで、
カードやリワードを業務が何と呼ぶかは確認できていない。
確認できていない語を業務語として扱わないほうが、後で食い違わない（→ 01_requirements.md の質問リスト）。
評価軸・候補・却下理由は `naming.md`。


## 判断が変わる条件（まとめ）

上の判断はどれも「今回の要件・スコープではこう」という条件付きの結論であり、条件が変われば結論も変わる。
個々の判断に埋め込まれている前提を、ここに一覧としてまとめる。

| 条件 | どうなるか | 関連する判断 |
|---|---|---|
| 業務が「スタンプカード」と呼んでいると確認できる | 日本語の呼称を戻すか、対応表を持つかを検討する | `naming.md` |
| スタンプを使わない発行理由（誕生日特典など）が要件に入る | `Coupon` を新設し、`RewardCard` が持つ `usedOrderId` / `usedAt` を `Coupon` 側に移す | ①「無料特典」をエンティティにするか |
| 率の割引（30%引きなど）が要件に入る | 割引率の列を新設し、`bonusType` を見直す | ③「半額」を区分値で持つか |
| データ移行・手動付与（遡っての付与）が発生する | `createdAt` では付与日時を表せなくなる。`stampedAt` を専用カラムとして分ける | ①「付与日時を専用のカラムで持つか」 |
| 複数の期間限定リワードが同時に配布期間中になる | 「中断は常に最大1枚」という決めごとが崩れる。テーブル構造は変えずに済むが、複数枚が同時に中断中になったときの再開順のルールを新たに決める必要がある | ③「期間限定のリワードへの参加を…」／付録A
