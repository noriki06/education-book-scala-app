# <スタンプカード>  — 詳細要件定義

## 用語 — 全体の用語集に追加する呼称
（**呼称をそろえる取り決め。個別の仕様書で用語を定義しない**。追加を申請する分だけ挙げる）
| 呼称（これで統一する） | 何を指すか | 言い換えない |
|---|---|---|
| スタンプ | 注文ごとに1個押され、特典交換に必要な数を数える単位 | ポイント、来店記録 |
| スタンプカード | 会員が保有するスタンプのまとまりと、その有効期限 | 台紙、シート |
| 有効期限 | スタンプカードが持つ、スタンプが使えなくなる日。最後の付与から1年後に更新される | 失効予定日、有効期間 |
| 有効スタンプ | スタンプカードが期限内で、かつ未使用のスタンプ | 残スタンプ、使えるスタンプ |
| 使用済み | 特典交換で消費されたスタンプの状態 | 消化、消費済み |
| 無料特典 | 有効スタンプ10個と引き換えに、ハンバーガー1個を無料で受け取れること | クーポン、割引、サービス券 |

## EntityModel

### <スタンプカード>

```scala
case class StampCard(
  id:        Option[Id],           // 管理 ID（永続化前は None）
  userId:    User.Id,              // どの会員のカードか（User と 1:1）
  expiredAt: LocalDate,            // 有効期限。最新の付与日時 ＋ 1年
  updatedAt: LocalDateTime = Now,  // データ更新日
  createdAt: LocalDateTime = Now   // データ作成日
) extends EntityModel[Id]

object StampCard:

  type   Id = Id.Repr
  object Id extends Entity.Id[Long]
```

### <スタンプ>

```scala
case class Stamp(
  id:          Option[Id],                   // 管理 ID（永続化前は None）
  stampCardId: StampCard.Id,                 // どのカードのスタンプか（StampCard と *:1）
  orderId:     Order.Id,                     // どの注文で得たか（Order と 1:1）
  shopId:      Shop.Id,                      // どの店舗での注文か（集計用。判定には使わない）
  stampedAt:   LocalDateTime,                // 付与日時。有効期限の起点になる
  usedOrderId: Option[Order.Id] = None,      // どの注文で使ったか。未使用なら None
  usedAt:      Option[LocalDateTime] = None, // 特典交換に使用した日時。未使用なら None
  updatedAt:   LocalDateTime = Now,          // データ更新日
  createdAt:   LocalDateTime = Now           // データ作成日
) extends EntityModel[Id]

object Stamp:

  type   Id = Id.Repr
  object Id extends Entity.Id[Long]
```

**ここで型が語っていること**

- 区分値を持ちません。受け渡し完了時に付与するため、無効になるスタンプが存在しません
- `usedAt` の `None` が「未使用」。同じ意味を区分値でも書ける構造にすると、必ずどちらか片方を書き忘れます
- `Stamp` は `userId` を持ちません。`stampCardId` からたどれるので、両方持つと二重管理になります
- `Stamp` は有効期限を持ちません。期限は会員単位で一律なので、`StampCard` が1件だけ持ちます
- 有効スタンプ数を持ちません。カードが期限内かを見て、未使用の件数を数えれば求まります
- `stampedAt` は `LocalDateTime`。同じ日に複数得たときの順序を保ち、問い合わせで「何時にもらったか」を答えるためです
- `expiredAt` は `LocalDate`。「その日いっぱいは使える」という業務感覚に合わせ、日で判定します
- 交換した商品を持ちません。商品券型（ハンバーガー1つと交換）なので、選んだ商品は `OrderItem` にあります
- `Option` が付くのは `id` / `usedOrderId` / `usedAt` の3つだけ。それ以外はすべて必須です

**型では守れない決めごと**

- `orderId` は一意。1つの注文に対してスタンプは1個までしか作れません
- `usedOrderId` と `usedAt` は必ず両方埋まるか、両方 `None`。片方だけの状態は業務上ありえません
- `stampedAt` は、その注文を受け渡した日時。注文の受け渡し日時と食い違わないこと
- `expiredAt` は、そのカードの最新の `stampedAt` の日付 ＋ 1年。付与のたびに更新します
- 特典交換では、未使用スタンプのうち **古い順に10件** に `usedOrderId` と `usedAt` を書き込みます
- 特典を使った注文がキャンセルされたら、その `usedOrderId` の10件を `None` に戻します

**保存されるデータの例**（会員 A・`expiredAt` は 2027-07-28）

| orderId | stampedAt | usedOrderId | usedAt | どんなスタンプか |
|---|---|---|---|---|
| 1001 | 2025-05-02 10:15 | 1120 | 2026-07-20 12:30 | 特典交換で消費した |
| 1042 | 2026-06-15 18:40 | 1120 | 2026-07-20 12:30 | 同じ交換で消費した10件のうちの1つ |
| 1120 | 2026-07-20 12:35 | `None` | `None` | 未使用。特典を使った注文でもスタンプは付く |
| 1131 | 2026-07-28 19:02 | `None` | `None` | 未使用。このカードの最新の付与 |

有効期限はカードが持つ **2027-07-28**（最新の `stampedAt` 2026-07-28 ＋ 1年）。
有効スタンプ数は **2個**（1120 と 1131）。1001 と 1042 は使用済みなので数えない。

1001 の `stampedAt` は1年以上前だが、期限の判定はカード1件で行うため、スタンプが個別に失効することはない。
カードが期限切れになれば、未使用スタンプは一斉に数えられなくなる（9個に減るのではなく0個になる）。


## 区分値を作らない理由

業務には「使用済み」「期限切れ」の2語があるが、**区分値は1つも作らない。**

**「使用済み」は区分値にしない。** `usedAt` に日時が入っているかどうかで表す。
日時は問い合わせ対応で必要になるため結局持つことになり、区分値を足すと同じ事実が2か所に現れる。

**「期限切れ」も区分値にしない。** 保存すると、日付が変わった瞬間に嘘になる。
毎日書き換えるバッチが必要になり、そのバッチが落ちた日は失効したはずのスタンプが使えてしまう。
`StampCard.expiredAt` と今日を比べれば求まる。

**数の対象になるかどうかは、カードの期限と `usedAt` の2つで判定する。**

| カードが期限内か | usedAt | 数の対象か |
|---|---|---|
| 期限内 | `None` | **○ 数える** |
| 期限内 | `Some(...)` | × 特典交換で消費済み |
| 期限切れ | — | × カードごと失効。未使用スタンプも数えない |

期限の判定は `StampCard` 1件で終わる。**スタンプを1件ずつ見て失効しているか調べる必要はない。**
これが `StampCard` をエンティティにした理由である。


## <複数のエンティティにまたがる判定ルール>

### いつ何をするか

| きっかけ | すること |
|---|---|
| 注文を確定した（特典利用あり） | 未使用スタンプの古い10件に `usedOrderId` と `usedAt` を書き込む |
| 特典を使った注文がキャンセルされた | その `usedOrderId` の10件を `None` に戻す |
| 商品を受け渡した | スタンプを1件記録し、`StampCard.expiredAt` を「その日 ＋ 1年」に更新する |
| 期限が切れた | **何もしない**（判定のたびにカードの `expiredAt` と今日を比べる） |

### 有効スタンプ数の求め方

1. その会員の `StampCard` を探す。無ければ 0
2. `expiredAt` が今日より前なら 0
3. そのカードの `Stamp` のうち `usedAt` が `None` のものを数える

10個以上あれば無料特典が使える。

## 置き場所（コンテキスト）

判断：既存の sales コンテキストに入れる。新しく作らない。

理由：日常的に書き換えるのは会員と店舗スタッフで、`Cart` / `Order` と同じ人・同じ画面・同じ頻度です。
      書き換えるきっかけも注文の確定・受け渡しであり、注文フローの一部として動きます。

`common` には置けません——業務の操作で変わり（会員の注文のたびに増える）、
本部が管理するマスタでもなく、`Order.Id` を参照する側だからです。

`udb` にも置けません——`Order.Id` を持つため、`udb → sales` の逆流が生まれます。
既存の参照はすべて `sales` または `shop` が始点で、`udb` は参照される側にあります。

# 付録A：今回やらないこと

- **有効期限が近いことのお知らせ通知。** 会員がアプリを開いたときに有効期限を表示するだけにする
- **スタンプの譲渡・合算。** 会員間で受け渡す仕組みは作らない
- **無料で渡せる商品の範囲設定。** 現在はハンバーガーであればどれでもよい、で固定する
- **1注文で複数個のスタンプを押す運用。** 金額や点数に応じた加算はしない
- **期限切れスタンプの物理削除。** カードが期限切れなら数えないだけで、レコードは残す
- **店舗ごとのスタンプ発行数の集計画面。** `shopId` は持つが、画面は作らない
- **無料特典を「権利」として記録すること。** 有効スタンプの件数から判定する
- **スタンプ以外の特典（誕生日特典など）。** クーポンの仕組みは今回作らない


# 付録B：判断の記録

#### スタンプカードをエンティティにするか、有効期限を計算で求めるか

判断は `StampCard` を作り、有効期限を保存する。

計算でも求まる（最新の `stampedAt` ＋ 1年）が、その場合スタンプ全件を見ないと期限が分からない。
カードが1件持てば、判定はカード1件で終わり、スタンプごとの失効を見る必要がなくなる。
保存しても二重管理にならないのは、期限を持つのがカードだけで、スタンプ側は持たないため。
付与のたびにカードを1レコード更新するが、全件 UPDATE は起きない。

#### スタンプの消費と付与を、同じタイミングにするか

判断は揃えない。消費は注文確定時、付与は受け渡し完了時。

付与を支払い完了時にすると、商品を受け取っていない注文でスタンプが増え、
受け取らずに特典だけ取れてしまう。付与は「受け取った事実」への対価なので、受け渡しの後になる。

消費を受け渡し時にすると、10個持った状態で2件注文したときに両方へ特典を適用できてしまう。
消費は「使う宣言」なので、注文確定の時点で押さえる。

この非対称の結果、キャンセルによるスタンプの無効化が不要になった（受け渡し前のスタンプは存在しない）。

#### 「使用済み」を区分値にするか、日時の有無で表すか

判断は `usedAt` の有無で表す。区分値は作らない。

「いつ交換したか」は問い合わせ対応で必要なので、日時は結局持つ。
日時を持つなら、区分値は同じ事実の言い換えにすぎない。
両方持つと「区分値は使用済みなのに日時が空」という矛盾が作れてしまう。

#### 使った注文の ID を持つか

判断は `usedOrderId` を持つ。

`usedAt` の日時だけでは、特典を使った注文がキャンセルされたときに戻す10件を特定できない。
同じ日時のものを探す手はあるが、時刻の一致を頼りにする設計は脆い。
問い合わせで「この特典はどの注文で使ったか」に答えるためにも必要になる。

#### 期限切れを書き込むか、判定だけにするか

判断は書き込まない。表示や注文確定のたびにカードの `expiredAt` と今日を比べる。

書き込む案は毎日走るバッチが必要になり、そのバッチが落ちた日は失効したはずのスタンプが使えてしまう。
比べれば分かるものは保存しない。

#### 「無料特典」をエンティティにするか

判断は作らない。有効スタンプが10個以上あるかで判定する。

エンティティにすれば「10個たまった」という権利確定の事実を保存でき、その後スタンプが失効しても特典を残せる。
しかし要件定義で「特典もスタンプと同様、最後の注文から1年で使えなくなる」と確認しているため、
スタンプが失効したら特典も消えてよい。

商品券型（ハンバーガー1つと交換）に決まったことも効いている。
金券型なら残額の管理が必要でエンティティが要ったが、10個で1個の交換なら件数だけで足りる。
