# <スタンプカード>  — 詳細要件定義

## 用語 — 全体の用語集に追加する呼称
（**呼称をそろえる取り決め。個別の仕様書で用語を定義しない**。追加を申請する分だけ挙げる）
| 呼称（これで統一する） | 何を指すか | 言い換えない |
|---|---|---|
| スタンプ | 注文ごとに1個押され、特典交換に必要な数を数える単位 | ポイント、来店記録 |
| スタンプカード | スタンプ10個を貯める1枚。有効期限を持ち、特典交換の単位になる | 台紙、シート |
| 有効期限 | スタンプカードが持つ、そのカードが使えなくなる日。最後の付与から1年後。満杯になると確定し、以後は延長されない | 失効予定日、有効期間 |
| 有効スタンプ | 期限内かつ未使用のスタンプカードに属するスタンプ | 残スタンプ、使えるスタンプ |
| 使用済み | 特典交換に使われたスタンプカードの状態 | 消化、消費済み |
| 無料特典 | 有効スタンプ10個と引き換えに、ハンバーガー1個を無料で受け取れること | クーポン、割引、サービス券 |

## EntityModel

### <スタンプカード>

```scala
case class StampCard(
  id:          Option[Id],                   // 管理 ID（永続化前は None）
  userId:      User.Id,                      // どの会員のカードか（User と *:1）
  expiredAt:   LocalDate,                    // このカードの有効期限。付与のたびに「その日 ＋ 1年」へ更新
  usedOrderId: Option[Order.Id] = None,      // このカードを特典交換に使った注文。未使用なら None
  usedAt:      Option[LocalDateTime] = None, // 特典交換に使用した日時。未使用なら None
  updatedAt:   LocalDateTime = Now,          // データ更新日
  createdAt:   LocalDateTime = Now           // データ作成日
) extends EntityModel[Id]

object StampCard:

  type   Id = Id.Repr
  object Id extends Entity.Id[Long]
```

### <スタンプ>

```scala
case class Stamp(
  id:          Option[Id],          // 管理 ID（永続化前は None）
  stampCardId: StampCard.Id,        // どのカードに押されたか（StampCard と *:1）
  orderId:     Order.Id,            // どの注文で得たか（Order と 1:1）
  shopId:      Shop.Id,             // どの店舗での注文か（集計用。判定には使わない）
  stampedAt:   LocalDateTime,       // 付与日時。受け渡し完了の日時
  updatedAt:   LocalDateTime = Now, // データ更新日
  createdAt:   LocalDateTime = Now  // データ作成日
) extends EntityModel[Id]

object Stamp:

  type   Id = Id.Repr
  object Id extends Entity.Id[Long]
```

**ここで型が語っていること**

- 区分値を持ちません。受け渡し完了時に付与するため、無効になるスタンプが存在しません
- `Stamp` に `Option` は `id` だけ。押されたら二度と変わらない台帳で、状態を持ちません
- 使用済みかどうかは `StampCard` が持ちます。1枚のカードにつき交換は1回なので、カードの属性に収まります
- `StampCard.usedAt` の `None` が「未使用」。同じ意味を区分値でも書ける構造にすると、必ずどちらか片方を書き忘れます
- `Stamp` は `userId` を持ちません。`stampCardId` からたどれるので、両方持つと二重管理になります
- `Stamp` は有効期限を持ちません。期限はカード単位で一律なので、`StampCard` が持ちます
- 有効スタンプ数を持ちません。期限内かつ未使用のカードに属するスタンプを数えれば求まります
- `stampedAt` は `LocalDateTime`。同じ日に複数得たときの順序を保ち、問い合わせで「何時にもらったか」を答えるためです
- `expiredAt` は `LocalDate`。「その日いっぱいは使える」という業務感覚に合わせ、日で判定します
- 交換した商品を持ちません。商品券型（ハンバーガー1つと交換）なので、選んだ商品は `OrderItem` にあります
- 無料特典の有効期限を別に持ちません。満杯のカードが特典そのものなので、`expiredAt` が両方を表します。
  貯めている間は「スタンプが失効する日」、満杯後は「特典が失効する日」。どちらも「このカードが死ぬ日」です

**型では守れない決めごと**

- `Stamp.orderId` は一意。1つの注文に対してスタンプは1個までしか作れません
- 1枚のカードに属するスタンプは **10件まで**。満杯になったら次の注文では新しいカードを作ります
- `usedOrderId` と `usedAt` は必ず両方埋まるか、両方 `None`。片方だけの状態は業務上ありえません
- `usedAt` を書き込めるのは、スタンプが10件揃っていて期限内のカードだけです
- **1回の注文で交換できるのは1枚まで。** 満杯のカードを複数持っていても、無料になるのは1個です
- 付与のたびに、その会員の **期限内・未使用・満杯でないカード** の `expiredAt` を「その日 ＋ 1年」へ更新します
- **満杯のカードは延長しません。** 10個目を押した時点で `expiredAt` が確定します
- **期限切れのカードと交換済みのカードも更新しません。** 一度切れたカードは二度と有効になりません
- 特典を使った注文がキャンセルされたら、そのカードの `usedOrderId` と `usedAt` を `None` に戻します
- **部分的に埋まったカードは、常に最大1枚。** 満杯にしてから次のカードへ移るためです。
  この不変条件があるので「有効スタンプ数が10以上 ⟺ 満杯の未使用カードが存在する」が成り立ちます

**保存されるデータの例**（会員 A）

`StampCard`

| id | expiredAt | usedOrderId | usedAt | どんなカードか |
|---|---|---|---|---|
| 11 | 2025-04-10 | `None` | `None` | 期限切れ。スタンプ7個のまま失効した |
| 12 | 2027-06-30 | 1120 | 2026-07-20 12:30 | 10個目を 2026-06-30 に押して満杯。期限はその日 ＋ 1年で確定。注文 1120 で交換した |
| 13 | 2027-07-28 | `None` | `None` | 現行のカード。スタンプ2個。付与のたびに延長される |

`Stamp`（カード 13 の分）

| stampCardId | orderId | stampedAt |
|---|---|---|
| 13 | 1120 | 2026-07-20 12:35 |
| 13 | 1131 | 2026-07-28 19:02 |

有効スタンプ数は **2個**（カード 13 の2件）。
カード 12 は交換済み、カード 11 は期限切れなので数えない。

カード 11 の7個は、カード 12・13 が延長されても復活しません。期限切れのカードを更新しないためです。
1120 が「交換に使った注文」と「スタンプを得た注文」の両方に出ているのは、
特典を使った注文にもスタンプが付くためです。


## 区分値を作らない理由

業務には「使用済み」「期限切れ」の2語があるが、**区分値は1つも作らない。**

**「使用済み」は区分値にしない。** `StampCard.usedAt` に日時が入っているかどうかで表す。
日時は問い合わせ対応で必要になるため結局持つことになり、区分値を足すと同じ事実が2か所に現れる。

**「期限切れ」も区分値にしない。** 保存すると、日付が変わった瞬間に嘘になる。
毎日書き換えるバッチが必要になり、そのバッチが落ちた日は失効したはずのスタンプが使えてしまう。
`StampCard.expiredAt` と今日を比べれば求まる。

**数の対象になるかどうかは、カードの2つの属性だけで判定する。**

| expiredAt | usedAt | そのカードのスタンプ |
|---|---|---|
| 今日以降 | `None` | **○ 数える** |
| 今日以降 | `Some(...)` | × 特典交換で消費済み |
| 今日より前 | — | × 失効。カードごと数えない |

判定は `StampCard` の2列を見るだけで終わる。**スタンプを1件ずつ見て失効しているか調べる必要はない。**
これが `StampCard` をエンティティにした理由である。


## <複数のエンティティにまたがる判定ルール>

### いつ何をするか

| きっかけ | すること |
|---|---|
| 注文を確定した（特典利用あり） | 期限内・未使用・10個揃っているカードのうち最も古い1枚に、`usedOrderId` と `usedAt` を書き込む（1注文につき1枚まで） |
| 特典を使った注文がキャンセルされた | そのカードの `usedOrderId` と `usedAt` を `None` に戻す |
| 商品を受け渡した | 押す先のカードを決めてスタンプを1件記録し、期限内・未使用・満杯でないカードの `expiredAt` を「その日 ＋ 1年」に更新する。押した結果10個目になったカードは、その日 ＋ 1年で確定する |
| 期限が切れた | **何もしない**（判定のたびにカードの `expiredAt` と今日を比べる） |

### どのカードに押すか

1. その会員のカードのうち、期限内・未使用・スタンプが10件未満のものを探す
2. 見つかればそこに押す
3. 無ければ新しいカードを作り（`expiredAt` はその日 ＋ 1年）、そこに押す

### 有効スタンプ数の求め方

1. その会員のカードのうち、`expiredAt` が今日以降かつ `usedAt` が `None` のものを集める
2. それらのカードに属するスタンプの件数を合計する

10個以上あれば無料特典が使える。

## 置き場所（コンテキスト）

判断：既存の sales コンテキストに入れる。新しく作らない。

理由：日常的に書き換えるのは会員と店舗スタッフで、`Cart` / `Order` と同じ人・同じ画面・同じ頻度です。
      書き換えるきっかけも注文の確定・受け渡しであり、注文フローの一部として動きます。

`common` には置けません——業務の操作で変わり（会員の注文のたびに増える）、
本部が管理するマスタでもなく、`Order.Id` を参照する側だからです。

`udb` にも置けません——`Order.Id` を持つため、`udb → sales` の逆流が生まれます。
既存の参照はすべて `sales` または `shop` が始点で、`udb` は参照される側にあります。

# 付録A：今回やらないこと

- **有効期限が近いことのお知らせ通知。** 会員がアプリを開いたときに有効期限を表示するだけにする
- **スタンプの譲渡・合算。** 会員間で受け渡す仕組みは作らない
- **無料で渡せる商品の範囲設定。** 現在はハンバーガーであればどれでもよい、で固定する
- **1注文で複数個のスタンプを押す運用。** 金額や点数に応じた加算はしない
- **期限切れカード・スタンプの物理削除。** 期限切れのカードは数えないだけで、レコードは残す
- **店舗ごとのスタンプ発行数の集計画面。** `shopId` は持つが、画面は作らない
- **無料特典を「権利」として記録すること。** 有効スタンプの件数から判定する
- **スタンプ以外の特典（誕生日特典など）。** クーポンの仕組みは今回作らない


# 付録B：判断の記録

#### スタンプカードをエンティティにするか、有効期限を計算で求めるか

判断は `StampCard` を作り、有効期限を保存する。

要件で「全スタンプが一律で、最後の付与から1年」に確定した（→ 01_requirements.md）。
一律ということは、その会員のスタンプの期限は全部同じ値になる。
1つしかない値を10行に分散させるのは重複であり、しかも付与のたびに全件 UPDATE が必要になる。
カードが持てば1〜2レコードの更新で済み、判定もカードの2列を見るだけで終わる。

もし要件が「スタンプごとに押した日から1年」だったら、期限は1件ずつ違う値になるので `Stamp` が持つのが正しく、
カードは不要だった。**この分岐が `StampCard` を作った理由のすべてである。**

#### スタンプカードを会員につき1枚にするか、複数枚にするか

判断は複数枚。10個で満杯になったら、次のスタンプは新しいカードに押す。

1枚だと、期限切れの後に来店したとき `expiredAt` が未来へ更新され、
失効したはずのスタンプが復活してしまう。回避するには起算日をもう1つ持ち、
数えるたびに「起算日以降か」を条件に加えることになる。

複数枚なら、期限切れのカードを更新しないだけで済む。古いカードのスタンプには構造上たどれないので、
復活が起こりえない。1枚 ＝ 10マスの台紙という紙の運用にも一致する。

代償として、押す先のカードを毎回決める処理と、「1枚10件まで」という型で守れない制約が増えた。

#### 満杯になったカードの期限を延長し続けるか

判断は延長しない。10個目を押した日 ＋ 1年で確定する。

延長する案もあった。要件の「一律延長」を素直に読めば、保有するカードすべてが対象になる。
しかしそうすると、10個揃えた会員は注文を続けるかぎり特典が永久に消えない。
「最後の注文から1年」という制限が、いちばん価値のあるカードにだけ効かなくなる。

満杯になった時点で権利が確定したと捉え、そこから1年とする。
紙のカードで「満了日から1年以内にご利用ください」と印字するのと同じ考え方である。

結果として、延長の対象は **期限内・未使用・満杯でないカード** に絞られた。
不変条件（部分的に埋まったカードは常に最大1枚）と合わせると、
延長で更新されるレコードは常に1枚以下になる。

#### 使用済み日時をスタンプに持つか、カードに持つか

判断はカードに持つ。

交換は10個まとめての1回なので、スタンプに持つと同じ値が10行に重複する。
1枚のカードにつき交換は1回だけなので、カードの属性として過不足なく収まる。

結果として `Stamp` から `Option` が消え、`id` 以外はすべて必須になった。
スタンプは「いつどの注文で得たか」だけの台帳になり、状態を持たない。
古い順に10件を選ぶ処理も不要になった。

#### スタンプの消費と付与を、同じタイミングにするか

判断は揃えない。消費は注文確定時、付与は受け渡し完了時。

付与を支払い完了時にすると、商品を受け取っていない注文でスタンプが増え、
受け取らずに特典だけ取れてしまう。付与は「受け取った事実」への対価なので、受け渡しの後になる。

消費を受け渡し時にすると、10個持った状態で2件注文したときに両方へ特典を適用できてしまう。
消費は「使う宣言」なので、注文確定の時点で押さえる。

この非対称の結果、キャンセルによるスタンプの無効化が不要になった（受け渡し前のスタンプは存在しない）。

#### 「使用済み」を区分値にするか、日時の有無で表すか

判断は `usedAt` の有無で表す。区分値は作らない。

「いつ交換したか」は問い合わせ対応で必要なので、日時は結局持つ。
日時を持つなら、区分値は同じ事実の言い換えにすぎない。
両方持つと「区分値は使用済みなのに日時が空」という矛盾が作れてしまう。

#### 使った注文の ID を持つか

判断は `usedOrderId` を持つ。

`usedAt` の日時だけでは、特典を使った注文がキャンセルされたときに戻すカードを特定できない。
問い合わせで「この特典はどの注文で使ったか」に答えるためにも必要になる。

#### 期限切れを書き込むか、判定だけにするか

判断は書き込まない。表示や注文確定のたびにカードの `expiredAt` と今日を比べる。

書き込む案は毎日走るバッチが必要になり、そのバッチが落ちた日は失効したはずのスタンプが使えてしまう。
比べれば分かるものは保存しない。

#### 「無料特典」をエンティティにするか

判断は作らない。有効スタンプが10個以上あるかで判定する。

エンティティにすれば「10個たまった」という権利確定の事実を保存でき、その後スタンプが失効しても特典を残せる。
しかし要件定義で「特典もスタンプと同様、最後の注文から1年で使えなくなる」と確認しているため、
スタンプが失効したら特典も消えてよい。

商品券型（ハンバーガー1つと交換）に決まったことも効いている。
金券型なら残額の管理が必要でエンティティが要ったが、10個で1個の交換なら件数だけで足りる。

**代案：`Coupon` を新設する。** 発行理由（スタンプ満了 / 誕生日）と有効期限、使用日時を持たせ、
`StampCard` は満杯になった時点で `Coupon` を発行する形にする。
スタンプ以外の発行理由（誕生日特典など）が要件に入った時点で、この案に切り替える。
そのとき `StampCard` から `usedOrderId` と `usedAt` を `Coupon` へ移す。カラム2本の移動で済む。
命名の選定で `Coupon` という語を採らなかったのは、この形が来たときに空けておくためでもある。
