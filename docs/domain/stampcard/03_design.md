## EntityModel
### <スタンプ>

case class Stamp(
  id:        Option[Id],                   // 管理 ID（永続化前は None）
  userId:    User.Id,                      // どの会員のスタンプか
  shopId:    Shop.Id,                      // どの店舗での注文か（集計用。判定には使わない）
  orderId:   Order.Id,                     // どの注文で得たか（Order と 1:1）
  stampedAt: LocalDate,                    // 付与日。有効期限の起点になる
  state:     Status = Status.IS_ACTIVE,    // スタンプの状態（有効か無効か）
  usedAt:    Option[LocalDateTime] = None, // 特典交換に使用した日時。未使用なら None
  updatedAt: LocalDateTime = Now,          // データ更新日
  createdAt: LocalDateTime = Now           // データ作成日
) extends EntityModel[Id]

object Stamp:

  type   Id = Id.Repr
  object Id extends Entity.Id[Long]

  /** スタンプが数の対象になるかどうか */
  enum Status(val code: Short) extends EnumStatus[Short]:
    case IS_ACTIVE   extends Status(code =  1) // 有効
    case IS_INACTIVE extends Status(code = -1) // 無効（キャンセル・未受け取り）

**ここで型が語っていること**
- idのNoneは未保存、usedAtのNoneは未使用と意味合いが違う
- 有効期限を持ちません。その会員の最新の stampedAt ＋ 1年で求まるので、保存すると二重管理になります
- 有効スタンプ数を持ちません。state が有効、usedAt が None、期限内、の3条件を満たす件数を数えれば求まります
- stampedAt は LocalDate。時刻を持ちません。期限は「その日いっぱいは使える」という業務感覚に合わせて日で判定します
- usedAt は LocalDateTime。こちらは問い合わせ対応で「何時に使ったか」を追う必要があるため、時刻まで持ちます
- Option が付いているのは id と usedAt の2つだけ。 それ以外はすべて必須です

**型では守れない決めごと**
- orderId は一意。1つの注文に対してスタンプは1個までしか作れません
- stampedAt は、その注文の支払いが完了した日。注文の日付と食い違わないこと
- 有効期限は、その会員の有効なスタンプのうち最新の stampedAt ＋ 1年。
- IS_INACTIVE かつ usedAt が入っている組み合わせは業務上ありえない

**保存されるデータの例**
| userId | orderId | state | stampedAt | usedAt | どんなスタンプか |
|---|---|---|---|---|---|
| 1 | 1001 | `IS_ACTIVE` | 2025-05-02 | 2026-06-10 12:30 | 特典交換で消費した |
| 1 | 1042 | `IS_INACTIVE` | 2026-06-15 | `None` | 注文がキャンセルされ、無効化された |
| 1 | 1120 | `IS_ACTIVE` | 2026-07-20 | `None` | 未使用。数の対象になる |
| 1 | 1131 | `IS_ACTIVE` | 2026-07-28 | `None` | 未使用。この会員の最新の付与日 |

この会員の有効期限は、最新の `stampedAt`（2026-07-28）＋ 1年で **2027-07-28**。未使用スタンプはすべてこの日まで有効。

有効スタンプ数は **2個**（1120 と 1131）。1001 は使用済み、1042 は無効なので数えない。

1001 の `stampedAt` は1年以上前だが、期限の判定は会員単位で行うため、個別に失効することはない。


## 区分値の考え方
業務には「使用済み」「無効」「期限切れ」の 3 語があるが、`Status` は 2 値。

| 値 | 意味 | 業務での呼ばれ方 |
|---|---|---|
| `IS_ACTIVE` | 取り消されていない | （通常の状態。名前で呼ばれない） |
| `IS_INACTIVE` | キャンセル・未受け取りで取り消された | 無効 |

**「使用済み」は区分値にしない。** `usedAt` に日時が入っているかどうかで表す。
日時は問い合わせ対応で必要になるため結局持つことになり、区分値を足すと同じ事実が 2 か所に現れる。

**「期限切れ」も区分値にしない。** 保存すると、日付が変わった瞬間に嘘になる。
毎日書き換えるバッチが必要になり、そのバッチが落ちた日は失効したはずのスタンプが使えてしまう。
その会員の最新の `stampedAt` ＋ 1年 と今日を比べれば求まる。

つまり `Status` が表すのは「人やシステムが明示的に取り消したかどうか」だけ。
**数の対象になるかどうかは、`state`・`usedAt`・期限の 3 つを見て判定する。**

| state | usedAt | 期限内か | 数の対象か |
|---|---|---|---|
| `IS_ACTIVE` | `None` | 期限内 | **○ 数える** |
| `IS_ACTIVE` | `None` | 期限切れ | × 失効した |
| `IS_ACTIVE` | `Some(...)` | — | × 特典交換で消費済み |
| `IS_INACTIVE` | `None` | — | × キャンセル・未受け取りで無効化 |
| `IS_INACTIVE` | `Some(...)` | — | この組み合わせは作らない(ありえない) |

`state` と `usedAt` はレコード自身が持つ値だが、
「期限内か」はその会員のスタンプ全体から求める。**1 件だけを見ても判定できない。**

## <複数のエンティティにまたがる判定ルール>

### いつ何をするか
| きっかけ | すること |
|---|---|
| 支払いが完了した | スタンプを 1 件記録する（`IS_ACTIVE` / `usedAt` は `None`） |
| 特典を交換した | 有効スタンプのうち古い 10 件に `usedAt` を書き込む |
| 注文がキャンセル・未受け取りになった | そのスタンプを `IS_INACTIVE` にする。特典に使っていた 10 件は `usedAt` を `None` に戻す |
| 期限が切れた | **何もしない**（判定のたびに計算する） |

### 有効スタンプ数の求め方

1. `state` が `IS_ACTIVE` かつ `usedAt` が `None` のものを集める
2. そのうち最新の `stampedAt` ＋ 1年 が今日以降なら、1 の件数。今日より前なら 0

10 個以上あれば無料特典が使える。

## 置き場所（コンテキスト）
判断：既存の sales コンテキストに入れる。新しく作らない。
理由：日常的に書き換えるのは会員と店舗スタッフで、`Cart` / `Order` と同じ人・同じ画面・同じ頻度です。
      書き換えるきっかけも注文の確定・キャンセルであり、注文フローの一部として動きます。

`common` には置けません——業務の操作で変わり（会員の注文のたびに増える）、
本部が管理するマスタでもなく、`Order.Id` を参照する側だからです。
`udb` にも置けません——`Order.Id` を持つため、`udb → sales` の逆流が生まれます。
既存の参照はすべて `sales` または `shop` が始点で、`udb` は参照される側にあります。

# 付録A：今回やらないこと
- **有効期限が近いことのお知らせ通知。** 会員がアプリを開いたときに失効予定日を表示するだけにする
- **スタンプの譲渡・合算。** 会員間で受け渡す仕組みは作らない
- **無料で渡せる商品の範囲設定。** 現在はハンバーガーであればどれでもよい、で固定する
- **1注文で複数個のスタンプを押す運用。** 金額や点数に応じた加算はしない
- **期限切れスタンプの物理削除。** 判定で除外するだけで、レコードは残す
- **店舗ごとのスタンプ発行数の集計画面。** `shopId` は持つが、画面は作らない
- **無料特典を「権利」として記録すること。** 有効スタンプの件数から判定する



# 付録B：判断の記録
#### 「いま何個たまっているか」を数値として保存するか、押した記録（履歴）から数え上げるか。
判断は保存しない。最新のstampedAt + 1年で求める。
理由は、一律延長ルールを選んだ結果、保存すると注文のたびに保有スタンプ全件のUPDATEが必要になること。
有効かどうかの判定は 3 条件（`state`・`usedAt`・期限）になる。

#### 「使用済み」を区分値にするか、日時の有無で表すか
判断は `usedAt` の有無で表す。区分値は作らない。
「いつ交換したか」は問い合わせ対応で必要なので、日時は結局持つ。
日時を持つなら、区分値は同じ事実の言い換えにすぎない。
両方持つと「区分値は使用済みなのに日時が空」という矛盾が作れてしまう。


####  キャンセル時にスタンプを物理的に削除するか、無効化するか
判断は削除しない。無効にする（`state` を `IS_INACTIVE` にする）。
受け入れ条件に「いつ・どの注文で押されたかを後から一覧できる」がある。
削除すると履歴から消え、問い合わせ対応で追えなくなる。
この判断があるため `Status` が必要になった。削除する設計なら区分値は要らなかった。

#### 期限切れを書き込むか、判定だけにするか
判断はき込まない。表示や注文確定のたびに日付から判定する。
期限切れで `IS_INACTIVE` にする案もあるが、毎日書き換えるバッチが必要になる。
この結果、`state` が表すのは「明示的に取り消したかどうか」だけになった。
期限切れは `state` に現れない。

#### 「無料特典」をエンティティにするか
判断は作らない。有効スタンプが 10 個以上あるかで判定する。
スタンプが失効したら特典も消えていいから
