# スタンプカード — 思考過程（メモ・提出しない）

## 名詞と動詞

**名詞**：会員、店舗、注文、スタンプ、スタンプカード、有効期限、無料特典、ハンバーガー、アプリ

**動詞**：ログインする、支払う、（無料のハンバーガーを）選ぶ、スタンプを押す、貯める、スキャンする、キャンセルする、スタンプを消す、使用済みにする、記録する、（いま何個あるか）見る、（期限切れか）判定する

| 種類 | 動詞 | 行き先 |
|---|---|---|
| 状態を変える | スタンプを押す / スタンプを消す / 使用済みにする | スタンプを1件記録する・削除する・使用日時を記録することで表す（新しい状態遷移は増えない） |
| 値を返す | いま何個たまっているか数える / 期限切れか判定する | モデルのメソッド |

表に入らないもの（既存機能の動詞）：ログインする、支払う、（ハンバーガーを）選ぶ。スタンプを押すきっかけにはなるが、今回のモデルの操作ではない。

「貯める」は「スタンプを押す」の言い換え、「スキャンする」も結果はスタンプを1件記録する操作なので、表では1行に畳んでいる。

状態を変える動詞のうち、押す・消すはレコードの増減であり、EnumStatus の遷移にならない。「使用済みにする」だけが既存レコードの書き換えなので、ここを区分値で持つか使用日時の有無で表すかの判断が残る（→ 論点2）。

## ふるい分け

| 名詞 | 仕分け | 理由 |
|---|---|---|
| 会員 | 既存エンティティ（`User`） | スタンプの持ち主。今回は変更しない |
| 店舗 | 既存エンティティ（`Shop`） | どの店舗で押したかを持つ。ただし店舗をまたいで共通なので、店舗ごとに集計しない |
| 注文 | 既存エンティティ（`Order`） | スタンプを押すきっかけ。スタンプ側が `Order.Id` を参照する。`Order` 自体は変更しない |
| ハンバーガー | 既存エンティティ（`MenuItem`） | 無料で渡す商品。既存の商品マスタで足りる。今回は変更しない |
| スタンプ | **エンティティ（新規）** | 1件ずつ、いつ・どの注文で押されたかを追跡する必要がある。押される→消費される／失効する／取り消される、というライフサイクルを持つ |
| 有効期限 | 値オブジェクト | スタンプを押した日から1年後の日付。同じ日付なら区別する意味がない |
| スタンプカード | **対象外（＝計算結果）** | 保存しない。未使用で期限内のスタンプを数えれば求まる → 論点1 |
| 無料特典 | **対象外（＝計算結果）** | 保存しない。未使用で期限内のスタンプが10個以上あるかで判定できる → 論点3 |
| アプリ | **対象外** | 表示手段であって業務の概念ではない |

⚠️ 「スタンプカード」を対象外にしたことが、この仕分けの山場である。要求文にも業務フローにも繰り返し出てくるが、保存された実体ではない。実体はスタンプ1件ずつの記録で、「いま何個たまっているか」はそこからの数え上げで求まる。ここを仕分けずに進めると、「スタンプカードを白紙に戻す」のような、実体のない操作を書いてしまう。

9個の名詞のうち、既存で足りるものが4個、新規エンティティは1個、対象外が3個。**要求1つに対して、足すエンティティは1個で足りる。**

## ユビキタス言語（候補）

| 日本語 | 英語名 | 意味 | 多重度・備考 |
|---|---|---|---|
| スタンプ | `SalesStamp` | 注文1回につき1個獲得し、特典交換に使う単位 | `Order` と 1:1、`User` と 1:* |
| 有効期限 | `deadline` | そのスタンプを押した日から1年後の日付 | `SalesStamp` の属性。専用の型は作らない |
| 使用日時 | `usedAt` | 特典交換でそのスタンプを消費した日時 | 未使用なら未設定 |
| スタンプカード | （モデルなし） | 会員がいま持っている、未使用で期限内のスタンプのまとまり | 保存しない。件数として算出する |
| 無料特典 | （モデルなし） | スタンプ10個と引き換えにハンバーガー1つを無料で受け取れること | 保存しない。件数から判定する |

「スタンプカード」「無料特典」は業務の人が使い続ける言葉なので、呼称としては残す。モデルにならないことを備考で明示する。

## 名前を並べて確認する

`sales` コンテキストの既存の名前に混ぜて、名前順に並べる。

```
Cart
CartItem
CartItemOption
Order
OrderItem
OrderItemOption
Payment
SalesStamp                ← 今回追加
```

```
sales_cart
sales_cart_item
sales_cart_item_option
sales_order
sales_order_item
sales_order_item_option
sales_payment
sales_stamp               ← 今回追加
```

`Stamp` 単体では、会員のものか店舗のものか名前から読み取れない。`SalesStamp` とすることで、テーブル名でも `sales_stamp` が `sales_cart` 〜 `sales_payment` の並びに収まる。

なお既存の `Cart` / `Order` / `Payment` はコンテキスト名を接頭辞に持たない。今回だけ接頭辞を付けるのは既存の流儀から外れるが、`Stamp` が単独で意味を持ちにくい語であるため、あえて外した（→ 論点5）。

## コンテキストの判断

| 日常的に書き換える人 | 何を書き換えるか | 更新の頻度 | 見る画面 |
|---|---|---|---|
| 会員 | 注文のたびにスタンプが1つ増える | 毎回の注文 | スマホアプリ |
| 店舗スタッフ | 店舗購入時にスキャンして反映させる | 日常的 | 店舗のタブレット |
| システム | キャンセル・未受け取り時にスタンプを消す | 不定期 | — |

`common` に置けないかを 3 条件で確認する。

| 条件 | 判定 | 理由 |
|---|---|---|
| 1. 業務の操作では変わらない | ✗ | 会員の注文のたびに書き換わる |
| 2. 管理者が別にいる | ✗ | 本部が管理するものではない |
| 3. 他のコンテキストから参照されるだけ | ✗ | `Order.Id` / `User.Id` を参照する側 |

3 条件すべてで落ちる。売り切れ（`ShopMenuStock`）が条件1で落ちたのと同じ理由である。

**判断：** 既存の `sales` コンテキストに入れる。新しく作らない。
**理由：** スタンプを増減させるのは会員と店舗スタッフで、`Cart` / `Order` と同じアクター・同じ頻度。ライフサイクルも注文に連動する（1年で失効、履歴としては永久）。「スタンプ」という新しいコンテキストを作ると、注文を確定する処理から 2 つのリポジトリを呼ぶことになる。
