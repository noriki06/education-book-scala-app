# スタンプカード — 詳細要件定義

対象：スタンプによる特典交換 ／ 前提：要件定義で合意済み

## 概要

注文1回につきスタンプを1個記録し、未使用のスタンプが10個たまったらハンバーガー1つを無料にする。既存の `Order` / `User` / `MenuItem` は変更しない。`sales` コンテキストにエンティティを1つ追加する。

## 用語 — 全体の用語集に追加する呼称

| 呼称（これで統一する） | 何を指すか | 言い換えない |
|---|---|---|
| スタンプ | 注文1回につき1個獲得し、特典交換に使う単位 | 「ポイント」「来店記録」 |
| スタンプカード | 会員がいま持っている、未使用で期限内のスタンプのまとまり | 「台紙」「カード」 |
| 有効期限 | そのスタンプが使えなくなる日（押した日から1年後） | 「失効日」「期限日」 |
| 使用済み | 特典交換で消費されたスタンプの状態 | 「消化」「消費済み」 |
| 無料特典 | スタンプ10個と引き換えにハンバーガー1つを無料で受け取れること | 「クーポン」「割引」 |

「ポイント」と呼ばない理由：金額換算で貯まり、任意の量を使えるものと誤解される。スタンプは1注文1個で、10個単位でしか使えない。

「クーポン」と呼ばない理由：発行されて残高を持つ実体があるように読める。無料特典はスタンプの件数から算出するもので、レコードとして存在しない。

## ER 図

```
User (既存)                          MenuItem (既存)
  │                                   ▲
  │ 1                                 │ 無料で渡す商品として選ばれる
  │                                   │ （既存の OrderItem 経由。今回は変更しない）
  │ *
SalesStamp （今回追加）
  会員 ID / 店舗 ID / 注文 ID / 有効期限 / 使用日時
  │ 1
  │
  │ 1
Order (既存)
```

- `User` : `SalesStamp` ＝ 1:*（会員は複数のスタンプを持つ）
- `Order` : `SalesStamp` ＝ 1:1（1注文につきスタンプ1個）
- 「スタンプカード」「無料特典」に対応するデータは存在しない。`SalesStamp` を数えて求める。

## EntityModel

### SalesStamp — スタンプ

```scala
case class SalesStamp(
  id:        Option[Id],                // 管理 ID（永続化前は None）
  userId:    User.Id,                   // どの会員のスタンプか
  shopId:    Shop.Id,                   // どの店舗での注文か（集計用。判定には使わない）
  orderId:   Order.Id,                  // どの注文で押されたか（Order と 1:1）
  deadline:  LocalDate,                 // 有効期限（押した日から1年後）
  usedAt:    Option[LocalDateTime],     // 特典交換で消費した日時。未使用なら None
  updatedAt: LocalDateTime = Now,       // データ更新日
  createdAt: LocalDateTime = Now        // データ作成日
) extends EntityModel[Id]

object SalesStamp:

  type   Id = Id.Repr
  object Id extends Entity.Id[Long]
```

**ここで型が語っていること**

- `usedAt` の `None` が「未使用」。別に `isUsed` のようなフラグや区分値を持たない。同じ意味を2通りに書ける構造は、必ずどちらか片方を書き忘れる
- 有効期限を `LocalDate` で持つ。時刻では判定しない（「その日いっぱいは使える」という業務感覚に合わせる）
- `userId` を持つ。`orderId` からたどれるが、会員のスタンプを数えるたびに `Order` との結合が必要になるため、自分で持つ（→ 論点4）
- 「スタンプカード」に対応する属性はない。件数は数え上げで求める（→ 論点1）

**型では守れない決めごと**

- `orderId` は一意。1つの注文に対してスタンプは1個までしか作れない
- `deadline` は `createdAt` の日付 + 1年。生成時に計算して入れる
- 「いま何個たまっているか」＝ `usedAt` が `None` かつ `deadline` が今日以降のものの件数
- 特典交換では、上記のうち **期限が近い10件** に `usedAt` を書き込む（古いものから使う）
- 注文がキャンセル・未受け取りになったら、その `orderId` のスタンプを削除する

**保存されるデータの例**（会員 A）

| orderId | deadline | usedAt | 状態 |
|---|---|---|---|
| 1001 | 2027-03-01 | 2026-08-10 12:30 | 使用済み（特典交換に使った） |
| 1015 | 2027-04-02 | 2026-08-10 12:30 | 使用済み（同じ交換で消費した10件のうちの1つ） |
| 1120 | 2027-07-20 | None | 未使用。カウント対象 |
| 0812 | 2026-06-30 | None | 未使用だが期限切れ。カウントしない |

## 「いま何個たまっているか」の求め方

1. その会員の `SalesStamp` を引く
2. `usedAt` が `None` のものに絞る
3. `deadline` が今日以降のものに絞る
4. 件数がそのまま表示する数。10 以上なら無料特典が使える

保存された数値と照合する処理はない。**正は `SalesStamp` の件数のみ** である。

## 置き場所（コンテキスト）

**判断：** 既存の `sales` コンテキストに入れる。新しく作らない。

**理由：** スタンプを増減させるのは会員と店舗スタッフで、`Cart` / `Order` と同じアクター・同じ頻度。`common` の3条件はすべて満たさない（業務の操作で変わり、本部が管理せず、`Order.Id` を参照する側）。検討の詳細は 02_analysis.md のコンテキストの判断にある。

# 付録A：今回やらないこと

- 期限が近いスタンプのお知らせ通知
- スタンプの譲渡・合算
- 無料で渡せる商品の範囲設定（現在はどのハンバーガーでもよい）
- 1注文で複数個のスタンプを押す運用（金額や点数に応じた加算）
- 期限切れスタンプの物理削除（判定で除外するだけで、レコードは残す）
- 店舗ごとのスタンプ発行数の集計画面（`shopId` は持つが、画面は作らない）

# 付録B：判断の記録

### 論点1：「いま何個たまっているか」を数値として保存するか、記録から数え上げるか

**判断：** 数え上げる。数値としては保存しない。

「スタンプカード」というレコードを作れば、そこに残数を持てる。しかしその瞬間から、スタンプの件数と残数という2つの正が生まれる。片方だけ更新されるバグが起きたとき、どちらが正しいか誰も判断できない。数え上げなら情報は1か所にしかないので、そもそもズレない。

受け入れ条件の「いつ・どの注文で押されたかを後から一覧できる」も、1件ずつのレコードがあれば自動的に満たせる。残数だけを持つ設計では満たせない。

代償：会員のスタンプ数を出すたびに件数を数えるクエリが走る。1会員あたりのスタンプは年間数十件程度なので、問題にならない範囲と判断した。

### 論点2：「使用済み」を区分値で持つか、使用日時の有無で表すか

**判断：** `usedAt: Option[LocalDateTime]` で表す。区分値は作らない。

両方を持つと、「区分値が使用済みなのに使用日時が未設定」という矛盾した組み合わせが作れてしまう。`usedAt` だけなら、未使用は `None` の1通りしか書けない。

また「いつ交換したか」は問い合わせ対応で必要になる情報であり、日時は結局持つことになる。日時を持つなら、区分値は同じ事実の言い換えにすぎない。

営業時間の設計では逆に区分値を残したが、あれは業務が「臨時休業」を状態として呼び、休業日を状態で絞って一覧する要求があったためである。今回、業務は「使用済みスタンプの一覧」を必要としていない。

### 論点3：「10個たまったら無料」の特典を、記録として持つか

**判断：** 持たない。未使用で期限内のスタンプが10個以上あるかで判定する。

特典をエンティティにすれば、権利が確定した事実を保存できる。しかし今回は、10個たまってから交換までの間に古いスタンプが失効し、9個に戻る可能性を **許容する** と判断した。要求は「次の注文で無料になる」であり、10個目を押した注文の次の注文までに1年が経過することは実務上起きない。

「使用済みの10個」と「新しい1個」の区別は、`usedAt` が入っているかどうかで付く。交換時に10件へ日時を書き込み、それ以降のカウントから外れるため、11個目のスタンプは新しい1個目として数えられる。

代案：`SalesStampReward` を作り、権利確定日と交換日時を持つ。この場合はスタンプ側の `usedAt` を捨てて `rewardId` を持たせ、二重管理を避ける形にする。「権利確定後に絶対に消えないこと」が要件になった時点で、この案に切り替える。

### 論点4：会員 ID をスタンプが持つか、注文からたどるか

**判断：** `userId` を自分で持つ。

`orderId` があれば `Order.userId` から会員は分かる。しかし「いま何個たまっているか」はアプリを開くたびに引かれる、この機能でもっとも多い問い合わせである。そのたびに `Order` と結合するのは、参照する側のコンテキストにとって重い。

同じ事実を2か所に持つことになるが、`Order.userId` は注文確定後に変わらないため、ズレる余地がない。**変わらない値の複製は、二重管理にならない。**

`shopId` も同じ理由で持つが、こちらは判定に使わない。店舗別の発行数を将来集計するための情報であり、いま画面は作らない（付録A）。

### 論点5：`Stamp` ではなく `SalesStamp` と名付けた理由

**判断：** `SalesStamp` にする。既存の `Cart` / `Order` / `Payment` は接頭辞を持たないが、そこから外れることを認めて選んだ。

`Stamp` 単体では、会員に属するのか店舗に属するのか、名前から読み取れない。名前順に並べたとき `Shop*` の一族と `Sales*` の一族のどちらにも寄らず、迷子になる。`SalesStamp` なら、テーブル名 `sales_stamp` が `sales_cart` 〜 `sales_payment` の並びに収まる。

既存の流儀を優先して `Stamp` にする判断もあり得る。その場合はコンテキストがパッケージで示されるため、クラス名としては問題にならない。テーブル名 `sales_stamp` は規則どおり付くので、実害は「クラス名だけを見たときに所属が分からない」ことに限られる。今回は、会員向けの機能が今後増える見込み（クーポン・通知など）を踏まえ、`Sales*` の一族を作る側に倒した。
