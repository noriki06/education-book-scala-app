# 命名の選定記録

対象はリワード／ユーザーリワードカード／ユーザーリワードカードスタンプの3階層。

## 評価軸

APPENDIX_02 の7軸に、⑧⑨を加えた9軸。重みは ②⑤⑥⑦ を1、①③④⑧ を2、⑨ を4とする
（⑨ を最重要視点として扱う）。4点以下は致命的欠点とする。総合は9軸すべての重み付き平均（整数に四捨五入）。

① 役割差 ② 正確さ ③ 並び ④ 業務語 ⑤ 長さ ⑥ 拡張余地 ⑦ 多重度
⑧ 親子の向き（構造上の親子と、接頭辞が示す親子が一致するか）
⑨ 所属関係の明示（名前だけで、どのエンティティに属するかが分かるか）

⑧ を足したのはレビューの指摘から。3階層になると、深い階層ほど名前が短くなる並びが起こりやすく、
`Cart` < `CartItem` < `CartItemOption`（深いほど長い）と逆向きになると階層を取り違える。

**⑨ を足し、最重要視点にしたのは「関係性が見やすい名前がいい」という判断から。** ⑧は`Reward`階層
内部の親子関係、⑨は`User`など**階層の外側にある参照先**が名前だけで分かるかを見る、別の視点である。
`userId`という列自体はすでにあるので、⑨がなくても関係を追うことはできる。それでも、
デバッグ・調査でコードや画面を見たときに名前だけで判断できることを、②正確さや④業務語より優先する、
という明示的な判断（→ 決定打）。

**④ の扱いに注意。** 要求文にある業務語は「スタンプ」だけで、
カードやリワードを業務が何と呼ぶかは確認できていない（→ 01_requirements.md の質問リスト）。
そのため ④ は「要求文の語（スタンプ）を残せているか」として採点し、
カード・リワードの呼び方については減点しない。確認できていない語を業務語として扱わない。

## 決定打

**採用は `Reward` / `UserRewardCard` / `UserRewardCardStamp`。対抗は `RewardCard` 系（総合8）。**

差は⑨（所属関係の明示）1軸のみ。他の8軸で見れば `RewardCard` 系のほうが総じて高い
（とくに⑧親子の向きと③並びは`RewardCard`系が上）。それでも⑨を最重要視点に置くと決めたため、
`UserRewardCard` 系が上回る。**これは「どちらが優れた名前か」ではなく「何を優先するかを決めた」結果**である。

**なぜ `Reward` を語根に残すかは、`RewardCard` 系のときの決定打がそのまま引き継がれる。**

**② 正確さ：`Reward` は「特典」そのものの語で、誤解の余地がない。**
`Coupon` は「発行され、使われたら消える券」を指す語。貯めている途中（まだ特典に届いていない）カードを
`CouponCard` と呼ぶのは早すぎる——0個の状態でも `Coupon` と呼ぶことになってしまう。
`Reward` には「発行されて消える」という含意がなく、「特典を得るためのカード」と読めるので、
貯め始めの0個でも、必要数を満たした状態でも、同じ名前で通る。

**⑥ 拡張余地：`Reward` は誕生日特典のような、スタンプを使わない特典も同じ枠に収められる。**
最上位が `Reward`（特典の定義）である以上、必要スタンプ数・配布期間・特典の内容を持つ形は変えずに、
将来「スタンプを貯めずに条件を満たしたら発行される特典」が来ても、同じ `Reward` の1種として扱える。
`StampCard` 系の名前で始めていたら、最上位の名前自体がスタンプを前提にしてしまい、この余地がなかった。

`Coupon` を採らなかったのは②が理由だが、**`Coupon` という語は空けておく。**
将来、発行されたら消える実際のクーポン券（配布して終わりのもの）が要件に入ったときのために取っておく。

**`RewardCard`（`User` を前置しない案）を採らなかったのは⑨のみ。**
`⑧` 親子の向き・③ 並びでは`RewardCard`系のほうが優れている（`Reward`で始まり、`Cart`<`CartItem`<
`CartItemOption`と同じ向きになる）。それでも、デバッグ・調査でコードやテーブルを見たときに
「誰のものか」が名前だけで分かることを、②③⑧より優先する、という明示的な判断を今回下した。

**代償：** ⑤ 長さ（テーブル名が23字→28字）、⑧ `Reward`で始まらなくなる、③ 並びがやや読みにくくなる
（`User`+`Reward`+`Card`の3語が連結される）。1人が持つカードであることは`userId`列だけでも表現できて
いたので、名前でも重複して表すのは厳密には過剰であることは変わらない。それでも今回はこの代償を払う。

**日本語の呼称も英語に合わせる。** リワード／ユーザーリワードカード／ユーザーリワードカードスタンプ。

**ただし使い分けがある。** `UserRewardCard` / `UserRewardCardStamp` という**複合語そのもの**を指すときは
「ユーザーリワードカード」「ユーザーリワードカードスタンプ」と、英語の3語（`User` + `Reward` + `Card`）を
そのままカタカナ化する。理由は、`Reward`→リワード、`Card`→カードもすでに音訳（意味を訳さずカタカナにする）
なので、`User`だけ意味を訳した「会員」にすると、同じ複合語の中で訳し方が混ざってしまうため。

一方、`User`エンティティそのものを指す一般的な文章（「会員が持つ」「会員ID」など）では、
既存の用語表に合わせて引き続き「会員」を使う。こちらは`UserRewardCard`という複合語の一部ではなく、
既存の`User`モデルを指す独立した言及なので、既存の呼称を変える理由がない。

要求文にある語は「スタンプ」だけで、カードやリワードを業務が何と呼ぶかは確認できていない。
確認できていない語（「スタンプカード」）を業務語として扱い、それに英語名を合わせようとすると、
実際の呼び方が判明したときに二重に直すことになる。

日本語と英語を1対1で対応させれば、訳の対応表が要らない。
用語表の「言い換えない」欄に「スタンプカード」を入れて、途中で戻ることを防ぐ（→ 03_design.md）。

## 名前を並べて確認する

**クラス名**
- MenuItem                 ← 既存（common）
- Reward                   ← 今回追加（common）
- Cart ... Payment         ← 既存（sales）
- UserRewardCard           ← 今回追加（sales）
- UserRewardCardStamp      ← 今回追加（sales）

**テーブル名**
- common_menu_item                   ← 既存
- common_reward                      ← 今回追加（13字）
- sales_cart ... sales_payment       ← 既存
- sales_user_reward_card             ← 今回追加（22字）
- sales_user_reward_card_stamp       ← 今回追加（28字）

深い階層ほど名前が長くなる：`Reward`(6) < `UserRewardCard`(14) < `UserRewardCardStamp`(19)。
長さの向きは `Cart`(4) < `CartItem`(8) < `CartItemOption`(14) と同じだが、**先頭が揃っていない**
（`UserRewardCard` は `Reward` ではなく `User` から始まる）。これは⑨を優先した結果の意図的な差異
であり、見落としではない（→ 決定打）。

**`UserRewardCardStamp` の親参照フィールドは `cardId` ではなく `pId`（parent ID）にする。**
型が `UserRewardCard.Id` なのでどのエンティティを指すかは型から分かり、フィールド名で重ねて
表す必要はない。あえて具体名を避けて汎用名にしておくのは、将来 `Card` という別エンティティが
入ってきたときに、その名前を汎用名で衝突させずに済むようにするため。

## 判断が変わる条件

| 条件 | どうなるか |
|---|---|
| 業務が「スタンプカード」と呼んでいると確認できる | ④ の前提が変わる。日本語の呼称をスタンプカードに戻し、英語名との対応表を持つかを検討する |
| 発行されたら消える実際のクーポン券が要件に入る | `Coupon` という語が使える。`Reward` の1種として持たせるか、別に並べるかを検討する |
| 期間限定のリワードしか扱わなくなる | `Campaign` 系が有力になる。恒常的なリワードが同じ枠にある限りは意味が広がりすぎる |
| ⑨より②③⑧（正確さ・並び・親子の向き）を優先すべきという判断に戻る | `RewardCard` / `RewardCardStamp`（総合8）に戻すことを検討する。所属は `userId` 列で足りると考え直した場合 |
