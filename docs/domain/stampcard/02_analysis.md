| 有効スタンプ数 | 対象外（計算結果） | 未使用のスタンプを数えれば求まるため、保存しない |

## 名前を並べて確認する

**クラス名**
- Cart                        ← 既存
- CartItem                    ← 既存
- CartItemOption              ← 既存
- Order                       ← 既存
- OrderItem                   ← 既存
- OrderItemOption             ← 既存
- Payment                     ← 既存
- Stamp                       ← 今回追加

**テーブル名**
- sales_cart                    ← 既存
- sales_cart_item               ← 既存
- sales_cart_item_option        ← 既存
- sales_order                   ← 既存
- sales_order_item              ← 既存
- sales_order_item_option       ← 既存
- sales_payment                 ← 既存
- sales_stamp                   ← 今回追加


**判断:** Stampとする。

**理由:** SalesStampは所属が名前で読める利点があるが、既存のCart/Order/Paymentが接頭辞を持たない流儀から外れる。
所属はテーブル名とパッケージが示すため、既存の規則に揃えることを優先した。


## コンテキストの判断
| 日常的に書き換える人 | 何を書き換えるか | 更新の頻度 | 見る画面 |
|---|---|---|---|
| 会員 | 注文のたびにスタンプが1個増える | 毎回の注文| スマホアプリ |
|店舗スタッフ|	店頭注文時にコードをスキャンして付与を指示する|日常的|店舗のタブレット|
|システム|キャンセル時に無効化する／特典交換時に使用済みにする|不定期|---|


**判断：** 既存の sales コンテキストに入れる。新しいコンテキストは作らない。

**理由：** 書き換えるきっかけが注文の確定であり、アクター・画面・頻度が Cart・Order と同じ。
ライフサイクルも1年（履歴としては永久）で Order と揃う。
common は3条件すべてで落ちる（注文のたびに変わる／本部が管理しない／Order.Id を参照する側）。
udb も、会員に紐づくため検討したが、Order.Id を持つと udb → sales の逆流が生まれるため置けない。
「会員特典」の新設は、触る人が sales と同じで配線が1セット増えるだけなので、いまは作らない。
