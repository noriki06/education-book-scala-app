# <スタンプ> — 思考過程（メモ・提出しない）

構造はリワード／リワードカード／スタンプの3階層。

表は**①②③に分けて並べる**（→ 01_requirements.md の「差分の示し方」）。

| 節 | 中身 |
|---|---|
| ① 当初の要求からある分 | 当初の要求だけで決まり、追加の要求では動いていないもの |
| ② 追加の要求で変わった分 | 当初の要求にもあったが、内容や条件が変わったもの |
| ③ 追加の要求で加わった分 | 当初の要求には無かったもの |
命名の評価軸・候補・却下理由は `naming.md` に切り出した。ここでは仕分けと属性の判断だけを書く。

呼称は日本語も英語もそろえる。要求文にある語は「スタンプ」だけで、
カードやリワードを業務が何と呼ぶかは確認できていないため、日本語も `naming.md` の結論に合わせた。

| 日本語 | 英語名 |
|---|---|
| リワード | `Reward` |
| リワードカード | `RewardCard` |
| スタンプ | `RewardCardStamp` |

## 名詞と動詞

名詞（①当初から）：会員、店舗、注文、スタンプ、リワードカード、必要スタンプ数、有効期限、コード（会員提示用）

名詞（③追加で）：商品、リワード、配布期間、カードの有効期間、特典の延長期間、発行上限、
      特典の種類、割引額、カードの状態、中断日

動詞（①当初から）：ログインする、支払う、(商品を)選ぶ、スタンプを押す、スキャンする、キャンセルする、
　　　使用済みにする、記録する、(いま何個あるか)見る、受け渡す、(カードを)作る

動詞（③追加で）：差し戻す（復元する）、失効させる、リワードを決める、リワードに参加する、
　　　(カードを)中断する、(カードを)再開する、判定する、算出する

| 種類 | 対象 | 動詞 | 行き先 | 由来 |
|---|---|---|---|---|
| 追加 | `Reward` | リワードを決める（本部） | レコードを1行足す | ③追加 |
| 追加 | `RewardCardStamp` | スタンプを押す／記録する | レコードを1行足す | ①当初 |
| 追加 | `RewardCard` | (カードを)作る | 会員がそのリワードで最初のスタンプを得たとき、配布期間内であれば1行足す | ②変更 |
| 更新 | `RewardCard` | 使用済みにする／差し戻す／失効させる | カードの状態を書き換える | ②変更 |
| 追加 | `RewardCard` | リワードに参加する | 期間限定のカードを新しく1行足す。スタンプは0個から数え直す | ③追加 |
| 更新 | `RewardCard` | (カードを)中断する | いま貯めているカードに中断日を書き込む。スタンプは押されなくなる | ③追加 |
| 更新 | `RewardCard` | (カードを)再開する | 中断日を消し、中断していた日数を有効期限に加算する | ③追加 |
| 値を返す | — | 判定する／算出する | モデルのメソッド（期限切れかどうか、有効スタンプ数、特典が使えるか） | ③追加 |

`RewardCardStamp` は追加しかしない（押したら書き換えない台帳）。削除は1行もない（履歴を消さない）。
`Reward` も、本部が決めた後の変更（配布期間の延長など）は今回のスコープでは扱わない（作成のみ）。

表に入らないもの（既存機能の動詞）：
ログインする、支払う、(商品を)選ぶ、スキャンする、受け渡す、キャンセルする。
スタンプを押す・差し戻すきっかけにはなるが、注文側の操作であって今回のモデルの操作ではない。

## ふるい分け

**① 当初の要求からある名詞**

| 名詞 | 仕分け（エンティティ／値オブジェクト／属性／対象外／既存） | 理由 |
|---|---|---|
| 会員(既存) | **エンティティ** | スタンプの持ち主。今回は変更しない |
| 店舗(既存) | **エンティティ** | どの店舗で押したかを持つ。店舗をまたいで共通なので、店舗ごとに集計しない |
| 注文(既存) | **エンティティ** | スタンプを押すきっかけ。スタンプ側が Order.Id を参照する。Order 自体は変更しない |
| スタンプ | **エンティティ（新設。`RewardCardStamp`）** | 「いつどの注文で得たか」を1件ずつ追う履歴。ID による区別が必要 |
| 付与日時 | 対象外（既存の属性で足りる） | スタンプは受け渡し完了の瞬間にしか作られないので、`createdAt` と必ず同じ値になる |
| 会員コード | 既存の属性 | 既存の `User.uuid`（公開用識別子）で足りる |
| 有効スタンプ数 | 対象外（計算結果） | 未使用のスタンプを数えれば求まるため、保存しない |

**② 追加の要求で仕分けが変わった名詞**

| 名詞 | 仕分け（エンティティ／値オブジェクト／属性／対象外／既存） | 理由 |
|---|---|---|
| リワードカード | **エンティティ（新設。`RewardCard`）** | リワードが定める数のスタンプを貯める1枚。有効期限・使用状態・中断日を持ち、特典交換の単位になる。会員は「貯めている1枚」と「中断中の1枚」を同時に持てる |
| 有効期限 | 属性 | リワードカードが持つ。できた日（＝最初のスタンプを得た日）＋リワードが定める期間で確定する。以後延長しないが、中断していたカードを再開すると中断日数だけ加算される |
| 必要スタンプ数 | 属性 | リワードが持つ。カードが満杯になる数（例：10個） |

**③ 追加の要求で加わった名詞**

| 名詞 | 仕分け（エンティティ／値オブジェクト／属性／対象外／既存） | 理由 |
|---|---|---|
| 商品(既存、`MenuItem`) | **エンティティ** | 特典の対象商品。リワード側が `menuItemId` で参照する。今回は変更しない |
| リワード | **エンティティ（新設。`Reward`）** | 名称・配布期間・必要スタンプ数・カードの有効期間・特典の延長期間・発行上限・特典の種類・割引額を持つ定義。本部が管理する |
| 中断日 | 属性 | リワードカードが持つ。期間限定に参加してこのカードを中断した日。中断していなければ持たない。再開時に有効期限へ加算する日数の起点になる |
| カードの状態 | 属性 | リワードカードが持つ。収集中／特典獲得／使用済み／期限切れの4値。どれも他のデータから求まるが、管理側が利用実績を集計したい要求があるため区分値にする |
| 配布期間 | 属性 | リワードが持つ。この期間中に会員が最初のスタンプを得た場合だけ、そのリワードのカードができる |
| カードの有効期間 | 属性 | リワードが持つ。カードができた日から数える、有効な長さ（例：通常＝1年、サマースタンプ＝3ヶ月） |
| 特典の延長期間 | 属性 | リワードが持つ。満杯後の特典の有効期限を、カードの有効期限からどれだけ延ばすか（例：＋1ヶ月） |
| 発行上限 | 属性 | リワードが持つ。1人が作れるカードの最大枚数。通常は上限なし、期間限定は1枚だけ。枚数で持つ（真偽値にしない） |
| 特典の種類 | 属性 | リワードが持つ。全額無料／金額割引のいずれか1つ。半額は金額割引で表す |
| 割引額 | 属性 | リワードが持つ。特典の種類が金額割引のときだけ使う。円で持つ（パーセントにしない） |
| 特典の対象商品 | 属性 | リワードが持つ。`MenuItem.Id` を1つ参照する。商品側には何も足さない |
| 特典の有効期限 | 対象外（計算結果） | カードの有効期限 ＋ リワードが定める延長期間で求まるため、保存しない |
| アプリ | 対象外（業務の外） | スタンプを表示するためのもの |

## 名前の判断

命名の評価軸・候補・却下理由は `naming.md` に切り出した。ここでは結論だけ書く。

- リワード → `Reward`（`common_reward`。新設）
- リワードカード → `RewardCard`（`sales_reward_card`。新設）
- スタンプ → `RewardCardStamp`（`sales_reward_card_stamp`。新設）

`Stamp` を末端の1語に限定し、上位2階層を `Reward` という別の語根から組み立てた。
深いほど名前が長くなり、`Cart` < `CartItem` < `CartItemOption` と同じ向きになる。
`Coupon` を採らなかった理由は `naming.md` を参照。

## コンテキストの判断

| 日常的に書き換える人 | 何を書き換えるか | 更新の頻度 | 見る画面 |
|---|---|---|---|
| 本部 | リワードを新しく決める | キャンペーンごと（不定期） | 本部の管理画面 |
| 会員 | 注文のたびにスタンプが1個増える | 毎回の注文 | スマホアプリ |
| 店舗スタッフ | 店頭注文時にコードをスキャンして付与を指示する | 日常的 | 店舗のタブレット |
| システム | 受け渡し完了時に付与する／特典交換時に使用済みにする | 毎回の注文 | --- |

**リワード（`Reward`）の判断：`common` に入れる。**

理由：本部が管理し、業務の操作（注文）のたびには変わらず、`RewardCard` から参照される側にある。
common の3条件をすべて満たす。

**リワードカード・スタンプの判断：既存の `sales` コンテキストに入れる。**

理由：書き換えるきっかけが注文の確定・受け渡しであり、アクター・画面・頻度が `Cart`・`Order` と同じ。
`RewardCard` が `Reward.Id` を持つのは `sales` から `common` への参照であり、逆流ではない
（`OrderItem` が `MenuItem.Id` を持つのと同じ形）。`udb` にも置けない理由は変更なし
（`Order.Id` を参照する側のため、`udb → sales` の逆流が生まれる）。
