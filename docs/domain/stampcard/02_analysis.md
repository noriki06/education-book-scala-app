# <リワードカード> — 思考過程（メモ・提出しない）

構造はマスタ／リワードカード／スタンプの3階層。
命名の評価軸・候補・却下理由は `naming.md` に切り出した。ここでは仕分けと属性の判断だけを書く。

呼称は日本語も英語もそろえる。要求文にある語は「スタンプ」だけで、
カードやその種別を業務が何と呼ぶかは確認できていないため、日本語も `naming.md` の結論に合わせた。

| 日本語 | 英語名 |
|---|---|
| リワード（種別） | `Reward` |
| リワードカード | `RewardCard` |
| スタンプ | `RewardCardStamp` |

## 名詞と動詞

名詞：会員、店舗、注文、商品、スタンプ、リワードカード、リワード（種別）、配布期間、必要スタンプ数、
      カードの有効期間、特典の延長期間、特典の種類、割引額、カードの状態、有効期限、コード（会員提示用）

動詞：ログインする、支払う、(商品を)選ぶ、スタンプを押す、スキャンする、キャンセルする、
　　　使用済みにする、記録する、(いま何個あるか)見る、差し戻す（復元する）、失効させる、
　　　種別を決める、種別に参加する（切り替える）、判定する、算出する、受け渡す、(カードを)作る

| 種類 | 対象 | 動詞 | 行き先 |
|---|---|---|---|
| 追加 | `Reward` | 種別を決める（本部） | レコードを1行足す |
| 追加 | `RewardCardStamp` | スタンプを押す／記録する | レコードを1行足す |
| 追加 | `RewardCard` | (カードを)作る | 会員がその種別で最初のスタンプを得たとき、配布期間内であれば1行足す |
| 更新 | `RewardCard` | 使用済みにする／差し戻す／失効させる | カードの状態を書き換える |
| 更新 | `RewardCard` | 種別に参加する（切り替える） | 種別への参照と有効期限を書き換える。必要数・特典は参照先が変わるだけで、カード自身は持たない |
| 値を返す | — | 判定する／算出する | モデルのメソッド（期限切れかどうか、有効スタンプ数、特典が使えるか） |

`RewardCardStamp` は追加しかしない（押したら書き換えない台帳）。削除は1行もない（履歴を消さない）。
`Reward` も、本部が決めた後の変更（配布期間の延長など）は今回のスコープでは扱わない（作成のみ）。

表に入らないもの（既存機能の動詞）：
ログインする、支払う、(商品を)選ぶ、スキャンする、受け渡す、キャンセルする。
スタンプを押す・差し戻すきっかけにはなるが、注文側の操作であって今回のモデルの操作ではない。

## ふるい分け

| 名詞 | 仕分け（エンティティ／値オブジェクト／属性／対象外／既存） | 理由 |
|---|---|---|
| 会員(既存) | **エンティティ** | スタンプの持ち主。今回は変更しない |
| 店舗(既存) | **エンティティ** | どの店舗で押したかを持つ。店舗をまたいで共通なので、店舗ごとに集計しない |
| 注文(既存) | **エンティティ** | スタンプを押すきっかけ。スタンプ側が Order.Id を参照する。Order 自体は変更しない |
| 商品(既存、`MenuItem`) | **エンティティ** | 特典の対象商品。リワード側が `menuItemId` で参照する。今回は変更しない |
| リワード（種別） | **エンティティ（新設。`Reward`）** | 名称・配布期間・必要スタンプ数・カードの有効期間・特典の延長期間・特典の種類・割引額を持つマスタ。本部が管理する |
| リワードカード | **エンティティ（新設。`RewardCard`）** | 種別が定める数のスタンプを貯める1枚。有効期限と使用状態を持ち、特典交換の単位になる |
| スタンプ | **エンティティ（新設。`RewardCardStamp`）** | 「いつどの注文で得たか」を1件ずつ追う履歴。ID による区別が必要 |
| 有効期限 | 属性 | リワードカードが持つ。できた日（＝最初のスタンプを得た日）＋種別が定める期間で確定する。以後延長しないが、期間限定の種別に参加すると開催期間の長さだけ加算される |
| カードの状態 | 属性 | リワードカードが持つ。貯め中／必要数を満たした／使用済み／期限切れの4値。どれも他のデータから求まるが、管理側が利用実績を集計したい要求があるため区分値にする |
| 配布期間 | 属性 | 種別が持つ。この期間中に会員が最初のスタンプを得た場合だけ、その種別のカードができる |
| 必要スタンプ数 | 属性 | 種別が持つ。カードが満杯になる数（例：10個） |
| カードの有効期間 | 属性 | 種別が持つ。カードができた日から数える、有効な長さ（例：通常＝1年、サマースタンプ＝3ヶ月） |
| 特典の延長期間 | 属性 | 種別が持つ。満杯後の特典の有効期限を、カードの有効期限からどれだけ延ばすか（例：＋1ヶ月） |
| 特典の種類 | 属性 | 種別が持つ。全額無料／金額割引のいずれか1つ。半額は金額割引で表す |
| 割引額 | 属性 | 種別が持つ。特典の種類が金額割引のときだけ使う。円で持つ（パーセントにしない） |
| 特典の対象商品 | 属性 | 種別が持つ。`MenuItem.Id` を1つ参照する。商品側には何も足さない |
| 付与日時 | 対象外（既存の属性で足りる） | スタンプは受け渡し完了の瞬間にしか作られないので、`createdAt` と必ず同じ値になる |
| 会員コード | 既存の属性 | 既存の `User.uuid`（公開用識別子）で足りる |
| 有効スタンプ数 | 対象外（計算結果） | 未使用のスタンプを数えれば求まるため、保存しない |
| 特典の有効期限 | 対象外（計算結果） | カードの有効期限 ＋ 種別が定める延長期間で求まるため、保存しない |
| アプリ | 対象外（業務の外） | スタンプを表示するためのもの |

## 名前の判断

命名の評価軸・候補・却下理由は `naming.md` に切り出した。ここでは結論だけ書く。

- リワード（種別） → `Reward`（`common_reward`。新設）
- リワードカード → `RewardCard`（`sales_reward_card`。新設）
- スタンプ → `RewardCardStamp`（`sales_reward_card_stamp`。新設）

`Stamp` を末端の1語に限定し、上位2階層を `Reward` という別の語根から組み立てた。
深いほど名前が長くなり、`Cart` < `CartItem` < `CartItemOption` と同じ向きになる。
`Coupon` を採らなかった理由は `naming.md` を参照。

## コンテキストの判断

| 日常的に書き換える人 | 何を書き換えるか | 更新の頻度 | 見る画面 |
|---|---|---|---|
| 本部 | 種別を新しく決める | キャンペーンごと（不定期） | 本部の管理画面 |
| 会員 | 注文のたびにスタンプが1個増える | 毎回の注文 | スマホアプリ |
| 店舗スタッフ | 店頭注文時にコードをスキャンして付与を指示する | 日常的 | 店舗のタブレット |
| システム | 受け渡し完了時に付与する／特典交換時に使用済みにする | 毎回の注文 | --- |

**リワード（`Reward`）の判断：`common` に入れる。**

理由：本部が管理し、業務の操作（注文）のたびには変わらず、`RewardCard` から参照される側にある。
common の3条件をすべて満たす。

**リワードカード・スタンプの判断：既存の `sales` コンテキストに入れる。**

理由：書き換えるきっかけが注文の確定・受け渡しであり、アクター・画面・頻度が `Cart`・`Order` と同じ。
`RewardCard` が `Reward.Id` を持つのは `sales` から `common` への参照であり、逆流ではない
（`OrderItem` が `MenuItem.Id` を持つのと同じ形）。`udb` にも置けない理由は変更なし
（`Order.Id` を参照する側のため、`udb → sales` の逆流が生まれる）。
