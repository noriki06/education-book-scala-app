# <スタンプカード> — 思考過程（メモ・提出しない）

## 名詞と動詞
名詞：会員、店舗、注文、スタンプ、有効期限、スタンプカード、無料特典、ハンバーガー、アプリ
      使用済み日時、状態、付与日、有効スタンプ数、コード（会員提示用）

動詞：ログインする、支払う、(無料バーガーを)選ぶ、スタンプを押す、スキャンする、キャンセルする、
　　　無効化する、使用済みにする、記録する、(いま何個あるか)見る、差し戻す（復元する）、延長する
　　　判定する、算出する

| 種類 | 動詞 | 行き先 |
|---|---|---|
|状態を変える|スタンプを押す / 記録する|スタンプを1件記録する（レコードを1行足す。区分値は「未使用」で始まる）|
|状態を変える|使用済みにする / 無効化する / 差し戻す|スタンプの区分値の遷移（未使用 ⇄ 使用済み、未使用 → 無効）|
|状態を変える|延長する|保存しないので更新処理は発生しない。最新の付与日から算出するため、新しいスタンプが1件増えると期限が自動的に伸びる|
|値を返す|判定する / 算出する|モデルのメソッド（期限切れかどうか、有効スタンプ数、特典が使えるか）|


表に入らないもの(既存機能の動詞)：
ログインする、支払う、(無料バーガーを)選ぶ、スキャンする。
スタンプを押すきっかけにはなるが、今回のモデルの操作ではない

## ふるい分け

| 名詞 | 仕分け（エンティティ / 値オブジェクト / 属性 / 対象外 / 既存） | 理由 |
|---|---|---|
| 会員(既存) | **エンティティ** |スタンプの持ち主。今回は変更しない  |
| 店舗(既存) | **エンティティ** |どの店舗で押したかを持つ。店舗をまたいで共通なので、店舗ごとに集計しない|
| 注文(既存) | **エンティティ** |スタンプを押すきっかけ。スタンプ側がOrder.Idを参照する。Order自体は変更しない  |
|スタンプ|**エンティティ**|「いつどの注文で得たか」という履歴（台帳）であり、キャンセル時に特定して無効化するため、IDによる区別が必要|
|有効期限|対象外（計算結果）|その会員の最新の付与日 ＋ 1年、データから求まる値|
|使用済み日時 |属性|スタンプ単体では存在せず、特典交換に使用された「事実」を記録する  |
|状態|属性|	有効か無効（キャンセル）かを表す区分値|
|会員コード|既存の属性|既存の User.uuid（公開用識別子）で足りる|
|有効スタンプ数|対象外（計算結果）|（計算結果）有効かつ未使用のレコードを count すれば求まるため、保存しない|
|スタンプカード|対象外（概念）|スタンプ集合を指す言葉。別途テーブルを作る必要はない|
|無料特典|対象外（状態）|「スタンプ10個が使用済みになった状態」として表現するため、独立したエンティティにはしない|
|付与日|属性|履歴上の事実。有効期限算出の起点となる|
|ハンバーガー（既存）|エンティティ|ハンバーガーは無料で渡す商品。既存のMenuItemで足りる|
|アプリ|対象外（業務の外）|スタンプを表示するためのもの|

## 名前を並べて確認する
（既存の名前に混ぜて名前順に。クラス名とテーブル名の両方）
クラス名
Cart                        ← 既存
CartItem                    ← 既存
CartItemOption              ← 既存
Order                       ← 既存
OrderItem                   ← 既存
OrderItemOption             ← 既存
Payment                     ← 既存
Stamp                       ← 今回追加

テーブル名
sales_cart                    ← 既存
sales_cart_item               ← 既存
sales_cart_item_option        ← 既存
sales_order                   ← 既存
sales_order_item              ← 既存
sales_order_item_option       ← 既存
sales_payment                 ← 既存
sales_stamp                   ← 今回追加


判断:Stampとする。
理由:SalesStampは所属が名前で読める利点があるが、既存のCart/Order/Paymentが接頭辞を持たない流儀から外れる。
     所属はテーブル名とパッケージが示すため、既存の規則に揃えることを優先した。


## コンテキストの判断
| 日常的に書き換える人 | 何を書き換えるか | 更新の頻度 | 見る画面 |
|---|---|---|---|
| 会員 | 注文のたびにスタンプが1個増える | 毎回の注文| スマホアプリ |
|店舗スタッフ|	店頭注文時にコードをスキャンして付与を指示する|日常的|店舗のタブレット|
|システム|キャンセル時に無効化する／特典交換時に使用済みにする|不定期|---|


**判断：既存の sales コンテキストに入れる。新しいコンテキストは作らない。
**理由：書き換えるきっかけが注文の確定であり、アクター・画面・頻度が Cart・Order と同じ。
ライフサイクルも1年（履歴としては永久）で Order と揃う。
common は3条件すべてで落ちる（注文のたびに変わる／本部が管理しない／Order.Id を参照する側）。
udb も、会員に紐づくため検討したが、Order.Id を持つと udb → sales の逆流が生まれるため置けない。
「会員特典」の新設は、触る人が sales と同じで配線が1セット増えるだけなので、いまは作らない。
