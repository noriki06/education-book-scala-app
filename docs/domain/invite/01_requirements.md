# <お誘い> — 要件定義

## 受け取った要求

「職場の人をランチに誘うのは意外とハードルが高い。相手の都合を探ったり、断られたら気まずかったりで、
誘う側も誘われる側も気を使う。この気遣いをなくして、お互い誘いやすく断りやすくしたい。

そのために、匿名で『今日ランチに行きたい。何人集まったら行く』というイベントを出せて、
『参加』が設定した人数に達したら実施が決まる仕組みにしたい。
立案者が誰かも、誰が参加を押したかも、成立するまで見えないようにしたい。
言い出した人にも、集まらなかったイベントにも、恥や気まずさが残らないようにするため。

使い方の中心は『2時に行く人〜』くらいの軽いゆる募。ランチに限らず、飲み会やスマブラ大会、
日付を指定したランニングなど、イベント全般で使いたい。
参加を押すときに『遅れて行きます』のような一言コメントを添えられると、
遅れての参加や事情を伝えられていい。

アプリのダウンロードは面倒なので、Slack に流れる URL から誰でも使えるようにしたい。
ただし Slack への投稿で立案者がわかってしまわないように」

（人数・開示・キャンセル・規模などの細かい条件は、質問リストの仮回答で確定させる）

## 確認したいこと（質問リスト）

| 質問 | 今回の回答（仮） |
|---|---|
| 想定規模は？どこまで大きくなる想定か | まず自部署（6人）で始め、会社の成長に合わせて**30人規模**まで見込む。30人なら全員がいる雑談チャンネル1つで回るので、告知先チャンネルは当面1つのまま。部署ごとのチャンネル分けが要る規模（100人級）になったら Channel の昇格・管理者を検討する（→ 03_design.md 判断が変わる条件） |

| 集まる人数の下限は | **1人**。1人＝立案者だけで成立するので、作った瞬間から「成立」になり、「もう行くのは決まっていて追加を募るだけ」の使い方（仮に「確定型」と呼ぶ）を表せる。「N人集まったら行く」の条件付きは2人以上を設定する |
| 成立したあとのキャンセルは | **できる**。できないと『参加』を押すハードルが上がる。開示前の取り消しは誰にも知られない（→ 例外・ルール） |

| 開示のタイミングはどうやって知るか | 詳細ページに開示時刻を常時表示する（「メンバーは 11:30 から見られます」）。**ボットの投稿は募集と結末（成立・流れた・取り消された）の2本まで**で、開示のお知らせ投稿はしない |
| 開示は成立していなくても起きるか | **起きない。開示は「成立している」が前提**。未成立のまま開示時刻を過ぎても見せない（そのまま流れたとき、押した人の名前が出たままになるのを防ぐ）。開示時刻の後に成立したら、成立と同時に開示する |
| 確定型でも、参加者の一覧は開示時刻まで見えないままでよいか | 今回はルールを統一し、確定型も同じ開示ルール（既定30分前）とする。「誰と行くか見てから決めたい」という声が出たら見直す |
| 立案者はイベントを取り消せるか | 専用の取り下げ操作は作らない。**立案者が参加を取り消すと、開示前ならイベントごと取り消しになる**。行きたい人が他にいるなら、その人が新しく作ればいい。開示後の立案者の取り消しは普通の取り消しと同じ扱い（仮。理由は例外・ルールを参照） |
| 参加者の一覧を表示する「開始時刻の30分前」は固定か | **既定は30分前で、立案者がイベントごとに変えられる**。ただし開示時刻（開始時刻−設定値）が作成時点より過去になる設定は許さない（作った瞬間から参加者が見えてしまい、匿名の意味がなくなるため） |
| 参加を受け付ける締切は | 開始時刻まで。開始時刻までに人数が集まらなければそのイベントは終わり |
| 開始時刻・場所は誰が決めるか | 立案者がイベント作成時に開始時刻（開催日を含む）を入れる（必須）。場所は自由記述で任意。開催が決まったあとの細かい調整は開示された参加者同士に任せ、アプリでは扱わない |
| 同じ日に同じような募集が2件立ったら | 合流させず、別々のイベントとして扱う |
| ボットの投稿タイミングから立案者が推測されないか | 今回は対策しない（作成後すぐ投稿する）。気になれば投稿を数分遅らせる案があるが、次の要求で扱う |
| 参加できるのは誰か（メンバー管理はあるか） | **メンバー登録という仕組みは持たない**。URL を開いてログインした人なら誰でも参加できる。実質、告知チャンネルにいる人が対象。URL が外に漏れて部外者が参加できてしまうリスクは、社内ツールとして許容する |
| 会員（アカウント）はどう作るか | メールアドレスと表示名で誰でも登録できる、最小のログイン機能。表示名が、開示のときに参加者へ見える名前になる |
| Slack のプレビューや募集の投稿には何を載せるか | 内容・開始時刻などの概要だけ。**立案者・参加者・いま何人集まっているかは載せない**（ログイン前でも見える情報なので、見せないルールと矛盾しないものに限る） |
| 成立・開示の通知はどうやって届くか | **成立・流れたは、ボットがチャンネルに投稿する**（名前と人数は一切出さない）。守るべき秘密は「誰が」であって「成立した事実」ではないため。成立の公開はむしろ駆け込み参加を誘う。参加者の一覧はアプリの詳細ページだけで見せる。DM などの個人向け通知は作らない |
| 日付の指定はどこまでできるか | 開催日＋開始時刻を立案者が**1つに決めて**指定する。当日でも未来日でもよく、何日先まででも作れる。ただし候補日を並べてみんなで決める**日程調整はやらない**（成立条件を人数の一軸に保つ） |
| 開催が先のイベントのリマインドは | **今回はやらない**。ボットの投稿は募集時の1回だけ。忘れられて流れたら、それも記録に残るだけ |
| 「いつもと違うメンバーで」の宛先の手選びは | **今回はやらない**。相手は絞らない（URL が届く人全員）。次の要求で扱う |
| 人数が集まらなかったイベントの記録は | 消さずに残す。ただし誰が「参加」を押していたかは、本人以外の誰にも（立案者にも）表示しない |
| 要求文にない仮の呼称 | 人数が集まることを仮に「**成立**」、開示時刻に参加者の一覧が見えることを仮に「**開示**」、集まらずに終わることを仮に「**流れる**」と呼ぶ。業務の呼び方は未確認 |

## 業務フロー

[告知先を決める人（部署の誰か）]

1. アプリにログインし、募集を流す Slack チャンネルを告知先として設定する。

[立案者（部署の誰か）]

2. アプリにログインし、イベントを作る（内容＝ランチ・飲み・スマブラ・ランニングなど、
   開始時刻＝開催日を含む・当日でも未来日でもよい、成立人数、
   開示タイミング＝任意・既定は開始時刻の30分前）。
   作った時点で、立案者自身は参加者の1人に数えられる。

[システム]

3. 告知先の Slack チャンネルに、ボットの名義で募集を投稿する。
   立案者の名前は載せない。概要（内容・開始時刻）と詳細ページの URL を付ける。
4. URL が Slack に貼られたときは、概要のプレビューを出す（人数・立案者・参加者は出さない）。

[URL を見た人]

5. URL を開き、詳細（内容・開始時刻・場所・開示時刻）を見る。
   成立するまでは、いま何人集まっているかは見えない（成立後は人数だけ見える）。
6. 参加するなら、ログインして「参加」を押す。押すときに一言コメントを添えられる
   （任意。例：「遅れて行きます」）。押したこともコメントも、開示まで誰にも見えない。
   メンバー登録のような手続きは無く、押せばそのまま参加者になる。
7. 気が変わったら、開始時刻まで参加を取り消せる。

[システム]

8. 参加者が成立人数に達したら、ボットがチャンネルに「成立した」ことを投稿する。
   名前と人数は出さない。「参加者の一覧は開示時刻からアプリで見られる」旨を添える。
9. 成立していて開示時刻（既定は開始時刻の30分前。立案者がイベントごとに変えられる）を
   過ぎたら、その時点の参加者の一覧を、コメントと一緒に、アプリの詳細ページで開示する
   （URL を開いた人なら誰でも見られる）。ボットの追加投稿はしない。
10. 開示より前に、取り消しで参加者が成立人数を割ったら、自動で不成立に戻し、
    ボットがチャンネルに「流れた」ことを投稿する。
11. 開示より後に成立人数を割っても、不成立にはしない。取り消しは開示済みの一覧に
    反映され、行くかどうかは残った参加者に任せる。
12. 開始時刻までに成立しなければ「流れた」ものとして締め、
    ボットがチャンネルに「流れた」ことを投稿する。

[参加者]

13. 開示された参加者で集合し、開催する。

## 例外・ルール

- 立案者が誰かは、成立した後も開催した後も、永久に誰にも表示しない。
- 開示は「成立している」＋「開示時刻を過ぎている」の両方がそろって起きる。
  未成立のまま開示時刻を過ぎても見せない。開示時刻の後に成立したら、成立と同時に開示する。
- 成立した後も、開始時刻までは追加で「参加」を押せる（要求は「何人**以上**なら行く」）。
- 成立人数は1人から設定できる。1人なら作った瞬間に成立し、募集の投稿は最初から
  「やることは決まっている。来たい人はどうぞ」の体になる（確定型）。
- 通知はすべてボットのチャンネル投稿で行い、名前と人数は一切出さない。
  個人にだけ届く通知（DM）は作らない。参加者の一覧はアプリの詳細ページだけで見せる
  （開示後は URL を開いた人なら誰でも見られる。Slack には名前を載せない）。
- 参加の取り消しはいつでもできる。開示より前の取り消しは誰にも知られない。
  開示より後の取り消しは、開示済みの一覧から消えるので参加者に見える。それは現実のドタキャンと同じ扱い。
- 立案者も参加を取り消せる。**開示より前に立案者が取り消したら、イベントごと取り消しになり**、
  ボットがチャンネルに「取り消された」ことを投稿する（誰が立案者かは出さない）。
  確定型でも同じで、これが確定型を止める唯一の手段になる。
  まだ行きたい人がいれば、その人が新しくイベントを作ればいい。
- 開示より後に立案者が取り消した場合は、イベントごと取り消しにはせず、普通の取り消しと
  同じ扱いにする（仮）。イベントごと消すと、一覧から消えた人＝立案者だと推測できてしまうため。
- 流れたイベントは、誰が「参加」を押していたかを誰にも見せない（立案者にも見せない）。
  「3人の予定が2人しか集まらず、その2人だけ気まずい」を起こさないため。
- 参加の意思表示は必ずアプリの中で押す。Slack のリアクションや返信では受け付けない
  （Slack 上では誰が反応したか全員に見えてしまい、成立まで見せないルールが守れないため）。
- URL を開けば誰でも詳細を見られるが、「参加」を押すにはログインが要る。
  参加できる範囲は URL が届く範囲（実質、告知チャンネルにいる人）で、アプリ側では絞らない。
- Slack に出る募集の投稿とプレビューには、立案者・参加者・いま何人集まっているかを一切載せない。
  載せてよいのは内容・開始時刻など、誰に見られてもよい概要だけ。
- 流れた・取り消されたイベントも記録として消さずに残す。

## ドラフトの判断メモ（提出物ではない・レビュー用）

テンプレートの3節の外。レビューが済んだら、残すべきものは `03_design.md` の付録Bへ引き継いで、この節は消す。

#### タイトルの業務語をどれにするか

- **困った点**: 対話の中で「飲み」「誘い」「イベント」と語が変遷し、どれも発注者の言葉。
- **選択**: 当初は `<誘い>`。のちに発注者の指定で **`<お誘い>`** に改めた
  （「誘い」は名詞として裸すぎる。「お誘い」が自然な名詞形で、アプリ名 Osasoi とも揃う）。
- **理由**: 最初の要求の核が「こっちからも誘いたいし、誘って欲しい」であり、規約の
  「最初の要求で使われていた業務語」に最も合う。「イベント」は後から出た一般化の語、
  「飲み会」は対象を狭めすぎる（ランチ・スマブラも扱う）ため却下。

#### 受け取った要求の文面をどう扱うか

- **困った点**: 要求が壁打ちの対話形式で出てきた。最初は発言ログをそのまま時系列で
  引用したが、会話ベースすぎて読みにくく、飲み会中心・上司が登場する文になった。
- **選択**: 発注者が要求を**語り直した文**に差し替えた。ランチを主役に、上司は登場させず、
  一人称（自分が誘うハードルを下げたい）で書く。細部の決定（追加参加OK・下限人数等）は
  質問リストの仮回答の列に置いたまま。
- **理由**: 「原文をそのまま引用・直さない」の規約は、**書き手が他人の言葉を勝手に直さない**
  ためのルール。今回は発注者自身が言い直したので、要求の更新として扱う。
  ランチ中心にしたのは「飲み会中心だと社内で悪目立ちしそう」という発注者の意向。
  その後さらに「今後要求が増える」前提で、理由の説明を削って短くまとめ直した
  （落とした理由づけは例外・ルールと質問リストに残っている）。
  最終的に「**コア（何がしたくて、なぜ）だけを要求文に残し、細かい条件は質問リストへ移す**」
  という役割分担に確定した（発注者の指定）。要求文は4段落: 動機／仕組み／使い方／入口。

#### 立案者を成立人数に数えるか

- **困った点**: 要求の「何人集まったら」が立案者込みかどうかは発言からは読めず、
  自然な読みが人によって割れる。
- **選択（仮）**: 含む。
- **理由**: 立案者は当然行く人であり、「3人いれば行ける」という判断の実感は
  自分を含めた頭数のはず。未確認なので質問リストにも残した。

#### 「告知先を決める人」をアクターに立てるか

- **困った点**: 要求文には一度も登場しない人物。6人の部署なら暗黙でも回りそう。
- **選択**: アクターとして立てた。当初は「グループを作る人」としてメンバー登録まで
  担わせていたが、メンバー管理を持たない判断（次項）で仕事が「告知先チャンネルの設定」
  だけに縮んだ。
- **理由**: カリキュラムの「運営者を立て忘れるとまったく違うものができる」。
  仕事が1つでも、誰かがやる仕事である以上、業務フローに主語が要る。

#### メンバー管理（グループへの登録）を持つか

- **困った点**: 当初はアプリ側でグループにメンバーを手で登録する案だった。しかし
  Slack チャンネルの顔ぶれとアプリのグループがズレたとき、「募集は見えるのに押せない人」
  「登録されたのに気づかない人」が生まれる。Slack API での自動同期は外部依存が重い。
  発注者からは「個別アプリ＋プッシュ通知の方がいいか」という揺り戻しも出た。
- **選択**: メンバー管理そのものを持たない。URL を開いてログインした人なら誰でも参加できる。
  対象者の境界は Slack チャンネル（URL が届く範囲）に委ねる。
- **理由**: 境界を Slack に委ねれば、ズレという問題が構造的に消える。
  ネイティブアプリ＋プッシュ通知は「ダウンロードは面倒」という当初要求と衝突するうえ、
  研修スタック（Web アプリ）の外に出るため却下した。
- **代償**: URL が漏れると部外者もログインさえすれば参加できる。社内ツールとして許容し、
  承認制にする案は次の要求の候補として残す。

#### 成立の通知を個人宛てにするか、チャンネルに流すか

- **困った点**: 当初要求の「押した人にだけ実施の通知」を素直に読むと個人宛て通知（DM）が
  要るが、実装が重い。かといって全員が見えるチャンネル投稿は要求と矛盾するように見えた。
- **選択**: 成立・流れたはボットのチャンネル投稿に一本化。名前と人数は一切出さない。
  メンバーの顔ぶれだけはアプリの中で参加者のみに見せる。個人宛て通知は作らない。
- **理由**: 守るべき秘密は「**誰が**」であって「成立した事実」ではない、と発注者と整理し直した。
  「押した人にだけ通知」の目的は気まずさの回避であり、名前を出さないことで満たされる。
  成立の公開はむしろ駆け込み参加を誘い、確定型の「来てね」とも噛み合う。
- **代償**: 押していない人にも成立・流れたが見える（チャンネルのノイズ）。6人なら許容。

#### 「もう行くけど、来てね」（確定型）をどう表すか

- **困った点**: 「N人集まったら行く」（条件付き）と「行くのは決まっていて追加を募るだけ」
  （確定型）は、別の機能に見えた。
- **選択**: 成立人数の下限を1人に下げ、「1人＝作った瞬間に成立」として同じ仕組みに畳んだ。
- **理由**: 新しい概念を増やさずに両方の使い方を表せる。イベントの種類という区分値を
  持つより、成立人数という既存の値の解釈で済む方が軽い。
- **代償**: 確定型でも顔ぶれは30分前まで見えない。「誰と行くか見てから決めたい」ニーズには
  応えない（質問リストに残した）。

#### イベントの取り下げ操作を作るか

- **困った点**: 立案者は匿名なので、「取り下げ」ボタンを置くと権限の持ち主を特定管理する
  ことになる。当初は「立案者が自分の参加を取り消せば人数割れで自然に流れる」で済ませる
  つもりだったが、確定型（成立人数1）では人数割れが起きず、止める手段がなくなる穴が出た。
- **選択**: 専用の取り下げ操作は作らない。代わりに「立案者が参加を取り消したら、
  イベントごと取り消しになる」というルールにした（発注者の判断：行ける人が他にいるなら、
  その人が新しく作ればいい）。
- **理由**: 操作を増やさずに確定型の穴が塞がる。イベントを作るコストは低いので、
  作り直しに寄せる方が仕組みが単純になる。
- **代償**: 開示より後に立案者が取り消すと、イベント取り消しと同時に一覧から消えた人＝
  立案者だと推測できて、永久匿名のルールが実質破れる。これを避けるため、**開示後の
  立案者の取り消しは普通の取り消しと同じ扱い（イベントは残す）と仮置きした**。要レビュー。

#### ボタンの呼び名（「行ける」か「参加」か）

- **困った点**: 対話の中で「行ける」と「参加」の両方が使われていた。
- **選択**: 「参加」。
- **理由**: スマブラ大会のような「どこかに行く」わけではないイベントもあるため（発注者の判断）。

#### 「日程未定・メンバー手選び」の発言を要求原文に含めるか

- **困った点**: 発言は確かにあったが、対話の中で「今回はやらない」と合意済み。
  原文に含めると今回のスコープに見えるし、落とすと要約になる。
- **選択**: 原文にはそのまま含めて引用し、質問リストで「今回はやらない」と仮回答した。
- **理由**: 「要求は要約しない」の規約を守るため。やらないことを原文から消すと、
  次の要求が来たときに「言っていたのに書いていない」が起きる。

#### ディレクトリ名を `invite` と仮置きした

- **困った点**: 命名は `naming.md` で評価して決める工程がまだ先にある。
- **選択**: 仮に `invite` とした。
- **理由**: ファイルを置くのに名前が要るだけの理由。`naming.md` の評価
  （7つの評価軸）で決め直し、必要なら `git mv` で改名する。
