# 命名の選定記録

対象はイベント／参加の2モデルと、コンテキストの記号名、アプリ名。
会員（`User` / `udb_user`）は簡略評価（→ 末尾）。
ドキュメントのタイトルは `<お誘い>`（要求文の「誘う」の自然な名詞形。発注者が確定）。

## 評価軸

APPENDIX_02 の7軸に、⑧を加えた8軸。重みは ①③④ を2、②⑤⑥⑦⑧ を1とする。
4点以下は致命的欠点とする。総合は8軸すべての重み付き平均（整数に四捨五入）。

① 役割差 ② 正確さ ③ 並び ④ 業務語 ⑤ 長さ ⑥ 拡張余地 ⑦ 多重度
⑧ 衝突リスク（汎用語が、将来の別概念と紛れないか）

⑧ を足したのは、最有力候補の `Event` が極めて汎用的な語のため。
ログの「イベント」、分析の「イベント」、カレンダーの「イベント」など、ソフトウェアでは
別の意味で頻出する語であり、その紛れやすさを独立した軸として見ることにした。

**④ の扱い。** 要求文にある語は「イベント」と「参加」（→ 01_requirements.md。
「匿名で『今日ランチに行きたい』というイベントを作れるようにしたい」「『参加』を押した人が」）。
stampcard のときと違い、**今回は業務語（発注者の語）がはっきり要求文に残っている**ので、
④ はこの2語からの距離で採点する。

## 決定打

**採用は `Event` / `EventEntry`。対抗は `Event / EventParticipation`（総合8）と `Invite` 系（総合8）。**

**④ ユビキタス言語が決定打。** 今回は stampcard と違い、業務語が要求文にはっきり残っている
（「イベント」「参加」）。発注者が自分の言葉で「イベントを作る」「参加を押す」と言っている以上、
それ以外の語はすべて**訳し直し**であり、コードと会話の距離を自ら広げる行為になる。

**`Event` の弱点は ⑧（衝突リスク）の6点。** ソフトウェアの世界では「イベント」が別の意味
（ログ・分析・ドメインイベント）で頻出する。それでも採ったのは、
現在のスコープにその「別のイベント」が1つも存在せず、テーブルはコンテキスト接頭辞
（`event_*`）、コードはパッケージ（`edu.event.model`）で区別できるため。
この前提が崩れる条件は「判断が変わる条件」に残す。

**`Entry` と `Participation` の差は ⑤（長さ）のみで、意味の損失が無いことを確認して `Entry` にした。**
`EventEntry` の行が誰の・どのイベントへの参加かは `eventId: Event.Id` / `userId: User.Id` の型で
分かるので、`Participation` の正確さが情報として効く場面が無い。属性名（`requiredEntryCount`）も
`Entry` と揃えられる。

**`Invite` / `Invitation` は空けておく。** 将来「宛先を指定した招待」（→ 01_requirements.md
「いつもと違うメンバーを選んで誘えたり」）が要件に入ったとき、この語がちょうど
「特定の相手に宛てた誘い」を表すために必要になる。いま汎用の意味で使ってしまうと、
その時に語が無くなる（stampcard が `Coupon` を空けておいたのと同じ手）。

**日本語の呼称は「イベント」「参加」。** 要求文の語をそのまま使う。英語と1対1で対応し、
訳の対応表は要らない。「エントリー」とは呼ばない（用語表の言い換えない欄に登録済み → 03_design.md）。

**属性名の判断（小さいもの）**

- 立案者は `plannerId`。候補は `creatorId` / `proposerId` / `plannerId`。`creator` は
  どのモデルにもありうる汎用語（作った人）で、「立案者」という業務語（発注者の語）との対応が薄い。
  `proposer` は提案→承認の含意があり、承認フローは無いのでズレる。「立案者＝planner」が最短距離
- 成立人数は `requiredEntryCount`。stampcard の `requiredStampCount` と同じ形（required + 対象 + Count）
  で、リポジトリ内の既存の語法に揃う
- 取り消し日時は `canceledAt`。stampcard の `suspendedAt` / `usedAt` と同じ形（過去分詞 + At）

## コンテキストの記号名

| 候補 | テーブル名 | 判断 |
|---|---|---|
| **`event`** | `event` / `event_entry` | **採用**。エンティティ名がコンテキスト名で始まるときは重ねない規則により、`event_event` にならず最短になる。この文脈の主語はイベントそのもの |
| `invite` | `invite_event` / `invite_event_entry` | 語を将来のために空けておく判断（→ 決定打）と矛盾する。コンテキスト名に使えば、その語はもう「宛先を指定した招待」には使えない |
| `meet` | `meet_event` / `meet_event_entry` | 短いが意味が薄く、業務語でもない |

パッケージは `edu/event/model/`、テーブルは `event` / `event_entry`。

**ディレクトリ名（`docs/domain/invite/`）はこのままにする。** ドキュメントのディレクトリ名は
ドメイン（<お誘い>）を指す名前であり、モデルの語彙（`Invite` を空けておく）とは別の層の話。
コンテキスト記号 `event` と一致しないが、stampcard もディレクトリ名（stampcard）と
コンテキスト（common / sales）は一致していない。

## 名前を並べて確認する

**クラス名**

- User            ← 今回追加（udb）
- Event           ← 今回追加（event）
- EventEntry      ← 今回追加（event）

**テーブル名**

- udb_user        ← 今回追加（8字）
- event           ← 今回追加（5字。コンテキスト名と重ねない規則）
- event_entry     ← 今回追加（11字）

会員の名前は簡略に評価した。採用は `User`（認証の主体を指す一般語で、独自の語を発明する
理由が無い）。却下は `Member`（「メンバー」は用語表の禁止語と同根）と `Account`
（属性の「アカウント状態」と紛れる）。コンテキスト記号は `udb`（user database。会員・認証の置き場）。
会員・認証もこの設計で0から作る（→ 03_design.md 付録B 判断12）。

深い階層ほど名前が長くなる：`Event`(5) < `EventEntry`(10)。
`Cart`(4) < `CartItem`(8) と同じ向き。名前順で `Event` と `EventEntry` が隣り合い、
「イベントまわりを直したい人」が一覧から同時に見つけられる。

## 属性名・区分値の棚卸し

モデル名の評価から漏れて、評価表なしで決めていた名前を棚卸しした。
評価軸は軽量版の3つ: **(1)** リポジトリの先行ドメイン（stampcard 等）の語法との一致（`〜At`・`IS_〜`・`required〜Count`）
**(2)** 英語としての誤読リスク **(3)** 用語表の日本語と1対1で結べるか（直訳である必要はない）。

| 対象 | 採用 | 却下した候補と理由 |
|---|---|---|
| 内容 | `title` | `content`（本文の含意で誤読）、`description`（補足文に見える）、`name`（`User.name` と2用途になり検索性が落ちる）。直訳ではないが1対1で結べる |
| 開始時刻 | `startAt` | `heldAt`（開催済み＝過去に読める）、`scheduledAt`（「予定を登録した時刻」にも読める）。stampcard の `distStartAt` / `distEndAt` と同族で語法も一致 |
| 場所 | `place` | `location`（座標・位置情報の含意）、`venue`（正確だが業務の人が言わない硬い語） |
| 募集中 | **`IS_RECRUITING`（`IS_OPEN` から変更）** | `IS_OPEN` は「オープン＝公開」が**開示（言い換えない欄の「公開」）と英日で混線する**ため変更した。`IS_RECRUITING` は stampcard の `IS_COLLECTING` と語法（`IS_` ＋ 進行形＝進行中）が揃う |
| 流れた | `IS_FAILED`（維持） | `IS_EXPIRED`（人数割れの流れを表せず嘘になる）、`IS_LAPSED`（最も正確だが馴染みが薄く読み手に辞書コストを払わせる）、`IS_UNFILLED`（珍しい語）。「失敗」に読める懸念は認識した上で、**主語はイベント**（イベントが成立に失敗した。人ではない）として直裁さを取った |
| 日本語の仮称（成立・開示・流れる） | そのまま | 質問リスト発の仮称だが、用語表に登録済みで運用が安定している。「流れる」は口語だが要求の空気（ゆるさ）に合う |
| 開示タイミング | `revealBefore` | `revealAt`（開示時刻の保存＝`startAt` から求まる値の保存になり原則に反する）、`revealOffset`（差分の向きが名前から読めない）、`revealMinutesBefore`（単位を名前に焼き込むと型を変えたとき嘘になる）。reveal ＝ 開示は用語表と1対1 |
| コメント | `comment` | `note`（内部メモに見える）、`message`（宛先へ送るものに見える）。直訳で誤読なし |

## アプリ名（プロダクト名）

モデルの語彙（ユビキタス言語）とは**別の層**なので、評価軸も変える:
①口頭で呼びやすい（「○○に上げといて」と言えるか）②意味が通じる ③既存サービスと被らない
④モデル語彙と混同しない。用語表には載せない（業務の語ではなくブランド名のため）。

| 候補 | ① | ② | ③ | ④ | 総合 | 判定 |
|---|---|---|---|---|---|---|
| **Osasoi（お誘い）** | 9 | 9 | 8 | 9 | **9** | **採用**。意味が一発で通じ、タイトル `<お誘い>`・ドメインと全部揃う |
| Sorou（そろう） | 8 | 7 | 8 | 9 | 8 | 閾値成立のメカニズムを名前にした対抗馬。説明されないと由来が分からない |
| Kondo（こんど） | 8 | 5 | 8 | 9 | 7 | 「今度行こうね」を社交辞令で終わらせない、の含意が伝わらない |
| Ikou（いこう） | 9 | 6 | 5 | 9 | 7 | 呼びやすいが汎用的で、検索性・被り耐性が低い |
| Quorum | 6 | 3 | 7 | 8 | 5 | 成立人数（定足数）の英語。正確だが業務の人に通じない |

## 判断が変わる条件

| 条件 | どうなるか |
|---|---|
| 宛先を指定した招待の要求が入る（→ 01_requirements.md） | 空けておいた `Invite` / `Invitation` をその概念に使う。`Event` / `EventEntry` の名は動かさない |
| ログ・分析・カレンダーなど別の「イベント」概念がこのアプリに入る | ⑧の前提が崩れる。コンテキスト接頭辞・パッケージでの区別で足りるかを再評価し、足りなければ改名を検討する（改名は全レイヤに波及するので、この行が現実になりそうな兆しの時点で動く） |
| 「行けたら行く」など参加に種別・状態が入る | `EventEntry` が状態を持つモデルになる。`Entry`（記入・応募）の語のままでよいか、`Response` / `Rsvp` 系を再評価する |
| 業務の人が「イベント」以外の呼び方を使い始める | ④の前提が変わる。呼称の実態を確認してから日本語側の呼称を見直す（英語名は安易に追従しない） |
