# <お誘い> — 思考過程（メモ・提出しない）

構造はイベント／参加の2階層＋告知先の設定。
命名の評価軸・候補・却下理由は `naming.md` に切り出す予定。ここでは仕分けと属性の判断だけを書く。

## 名詞と動詞

**名詞**：イベント、立案者、参加（ボタン）、参加者、メンバー（顔ぶれ）、成立人数、開始時刻、
内容（ランチ・飲み・スマブラ）、場所、告知先（Slack チャンネル）、募集（の投稿）、概要（プレビュー）、
URL、詳細ページ、ボット、成立、開示、流れた、取り消し、確定型、部署、アカウント（ログイン）

**動詞**：（告知先を）設定する、（イベントを）作る、（募集・成立・流れた・取り消されたを）投稿する、
（URL を）開く、（詳細を）見る、（参加を）押す、（参加を）取り消す、成立する、開示する、流れる、
（イベントが）取り消される、締める、ログインする、集合する、開催する

| 種類 | 対象 | 動詞 | 行き先 |
|---|---|---|---|
| 追加 | イベント | （イベントを）作る | レコードを1行足す |
| 追加 | 参加 | （参加を）押す | レコードを1行足す |
| 更新 or 追加 | 参加 | （参加を）取り消す | **03の論点**。行を消すか、取り消しの印を追記するか（「可変な列を履歴の根拠にしない」と関わる） |
| 状態を変える | イベント | 成立する／流れる／取り消される | イベントの状態遷移。ただしどこまで保存しどこまで導出するかは**03の論点** |
| 値を返す | イベント | 開示済みか判定する／成立しているか判定する | モデルのメソッド（開示済み＝現在時刻 ≥ 開始時刻−30分。成立＝参加者数 ≥ 成立人数） |

表に入らないもの（会員側・システムの動詞）：
ログインする（今回作る `udb`（会員・認証）側の機能。イベント側モデルの操作ではない）、
投稿する・プレビューを出す（Slack 連携の出口であって、モデルの操作ではない）、
集合する・開催する（アプリの外の現実世界。開催の事実は記録しないと質問リストで決めた）。

## ふるい分け

| 名詞 | 仕分け（エンティティ／値オブジェクト／属性／対象外／既存） | 理由 |
|---|---|---|
| アカウント（部署の人） | **エンティティ（新設。`udb` の `User`）** | ログイン・立案・参加の主体。会員・認証（`udb`）もこの設計で0から作る |
| イベント | **エンティティ（新設）** | ID で区別する。同じ内容で2件立ったら別のイベント（質問リスト「合流させない」）。作られ→成立／流れ／取り消しのライフサイクルがある |
| 参加 | **エンティティ（新設）** | 「誰が・どのイベントに・いつ押したか」を1件ずつ追う記録。取り消しの履歴も追う必要がある |
| 立案者 | 属性 | イベントが持つ `User` への参照。**画面には永久に出さない**（出さないのは表示の決めごとで、保存はする——参加者の1人に数えるため） |
| 参加者・メンバー（顔ぶれ） | 対象外（＝計算結果） | 取り消されていない参加の集合。保存しない |
| 成立人数 | 属性 | イベントが持つ。1以上（1＝確定型） |
| 開始時刻 | 属性 | イベントが持つ。開催日を含む日時（未来日も可）。必須。開示（−30分）と締め切りの基準 |
| 内容 | 属性 | イベントが持つ。自由記述。ランチ／飲み／スマブラの**区分値にはしない**（要求はカテゴリ分けを求めていない。集計要求が出たら見直す） |
| 場所 | 属性 | イベントが持つ。自由記述・任意 |
| 告知先（Slack チャンネル） | **エンティティ（新設・仮）** | ボットが投稿する先の設定。想定規模では全体で1件だが、「誰がいつ設定したか」が残る方が運用で困らない。設定値1個に畳むかは**03の論点** |
| 開示 | 対象外（＝計算結果） | 開示済みかどうかは開始時刻から求まる。保存しない |
| 確定型 | 対象外（＝解釈） | 成立人数が1のイベントのこと。区分値にしない（判断メモ済み） |
| 募集（の投稿）・概要・URL・詳細ページ | 対象外（表現） | イベントを Slack や画面にどう見せるかの話で、業務の概念ではない |
| ボット | 対象外（システムの一部） | 投稿の名義。モデルにしない |
| 部署・チャンネルのメンバー | 対象外（Slack 側の世界） | アプリはメンバー管理を持たないと決めた。境界は URL が届く範囲 |

「対象外」7件。名詞21個を全部エンティティにしていないか確認済み——新設は**イベント・参加・告知先（仮）の3つだけ**。

## 用語をそろえる（気づいたブレ）

- **「メンバー」が2つの意味で使われている**：①チャンネルのメンバー（Slack 側の人々）、
  ②開示される顔ぶれ（＝参加者）。1つの言葉が2つのものを指すのはモデルが2つある合図。
  ②は「**参加者**」に統一し、「メンバー」は用語表の「言い換えない」欄の候補にする。
  ①はアプリの概念から消えた（メンバー管理を持たない）ので、そもそも使う場面がない。
- **「募集」と「イベント」**：募集は Slack 投稿の呼び名であって、実体はイベント1つ。
  本文では「イベント」に寄せ、「募集」は Slack 上の表現の話をするときだけ使う。

## 名前を並べて確認する

コンテキストの記号を仮に `event` とする（`naming.md` で確定）。
エンティティ名がコンテキスト名で始まるなら重ねない規則により、テーブルは `event_event` にならない。

```
Event               ← 新設
EventEntry          ← 新設
SlackChannelConfig  ← 新設（置き場は03の論点）
```

```
event                 ← Event（コンテキスト名と同じなので重ねない）
event_entry           ← EventEntry
event_slack_channel_config ← 仮。名前が長い＆Slackという固有名詞が入るのが気になる → naming.md へ
```

`Event` < `EventEntry` は深い階層ほど長い向きに合っている。
`SlackChannelConfig` は一族から浮いている（`Event` 接頭辞でない）。これは「イベントの一部ではなく
アプリの設定」だから正しい浮き方だが、名前は要検討。

## コンテキストの判断

| 日常的に書き換える人 | 何を書き換えるか | 更新の頻度 | 見る画面 |
|---|---|---|---|
| 立案者（部署の誰か） | イベントを作る・取り消す | 日常（週数回） | Web の作成画面 |
| 参加者（部署の誰か） | 参加を押す・取り消す | 日常（週数回） | Web の詳細ページ |
| 告知先を決める人 | 告知先の設定 | ほぼ一度きり | Web の設定画面 |
| システム | 成立・流れの判定、Slack への投稿 | イベントのたび | — |

**判断：コンテキストは2つ作る。`udb`（会員・認証）と `event`（誘い。記号は naming.md で確定）。**
どちらも今回このアプリのために設計する（雛形にある `udb` は別用途のため使わない）。

- イベントと参加は、同じ人が・同じ画面で・同じライフサイクルの中で触る。分けない
- 会員は認証の文脈（変わる理由・ライフサイクルが別）なので `udb` に分ける。
  イベントも参加も `User.Id` を**参照する側**で、`udb` は参照される側に保つ
- 告知先の設定だけ「触る人・頻度」が違う（一度きり・管理的）。ただし触るのは同じ部署の人で、
  設定1件のためにコンテキストを分けるのは分けすぎ。**同じコンテキストに置き、03で持ち方だけ再考する**

## 判断に困ったところ（このページの分）

#### イベントの「状態」を保存するか、導出するか

- **困った点**: 成立は「参加者数 ≥ 成立人数」で求まるので、原則（求まるものは保存しない）に
  従えば保存しない。しかし「流れた」「取り消された」は**終了の事実**であって数からは求まらない。
  さらに開示前の人数割れで「成立→不成立に戻る」動きがあり、純粋な導出だと
  「一度成立の投稿をした」という事実と食い違う瞬間がある。
- **選択（仮）**: 名詞としては「状態（区分値）」で拾っておき、**保存と導出の線引きは 03 で決める**。
- **理由**: ここで決めるには EntityModel の形（何をカラムに持つか）の話になり、02 の範囲を超える。

#### 立案者の「参加」をレコードとして作るか

- **困った点**: 立案者は作った時点で参加者の1人に数える。参加のレコードを1行作る案と、
  「立案者は数に含める」というルールで済ませる（レコードは作らない）案がある。
  前者は参加者の集合が participation の一覧だけで閉じる。後者は行が減るが、
  参加者を数えるロジックに常に「＋立案者」の分岐が入る。
- **選択（仮）**: レコードを作る方に傾いている。ただし「立案者の参加レコード」を取り消すと
  イベントごと取り消しになる、という特別扱いが要る。03 で決める。
- **理由**: 「参加者＝有効な参加の集合」という1つの定義で全部が説明できる方が、
  例外の分岐より安全。特別扱いは取り消しの1点に閉じ込められる。

#### 告知先をエンティティにするか、ただの設定値にするか

- **困った点**: 想定規模では全体で1件しかない。1件のためにモデル・テーブル・リポジトリの
  4点セットを作るのは重い。かといって設定ファイルに書くと「誰がいつ設定したか」が残らない。
- **選択（仮）**: エンティティとして拾っておき、03 で「設定ファイルで始めて、複数チャンネルの
  要求が来たらエンティティに昇格」も含めて判断する。
- **理由**: 02 の段階で概念として落とすと、03 で検討した痕跡が消えるため。
