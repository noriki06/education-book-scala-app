# Osasoi — 実装への申し送り（提出物ではない）

要件・ルールの正は `03_design.md`。ここには**要件定義の範囲外だが実装前に決めた**、
画面・導線・技術構成だけを置く（stampcard の HANDOFF.md と同じ役割）。

## 入口・ルート画面

- ルート（`/`）は**縦積みの1画面**: 上に開催前イベントの一覧（仕様は 03 のまま）、
  下に「部署のお店」見出し＋提案2枠＋「店をぜんぶ見る →」。**タブ・ボトムナビは作らない**（03 付録A）。
  画面上の合成であってデータの結合ではない（提案は `ShopReview` の導出のみ。結合ゼロ維持）
- ルートは**ログイン必須**。お誘いの一覧が0件のときは
  「**いま募集中のお誘いはありません**」＋「お誘いをつくる」を出す
- 未ログインでルートに来たらログイン・登録画面へ。そこに
  「Slack に流れた URL からも参加できます」の1行。自発的にログインした人の着地先はルート
- イベント詳細ページの末尾に、**ログイン済みのときだけ**「部署のお店を見る →」リンクを1本
  （Slack 経由で入った人へのお店の唯一の入口）

## 画面の文言・体裁（お誘い）

- 参加ボタンの直下:「押したこともコメントも、開示（時刻）まで誰にも見えません」
- 成立前の詳細:「何人集まっているかは誰にも見えません」
- 開示後の一覧の上:「この一覧は URL を開いた人なら誰でも見られます」
- 取り消しの確認文は開示前後・立案者かどうかで出し分け（すべて**本人の画面にだけ**）:
  立案者・開示前=「イベントごと取り消されます」／立案者・開示後=「あなたの参加だけが取り消されます」／
  参加者・開示前=「取り消したことは誰にも見えません」／参加者・開示後=「一覧からあなたの名前が消えます」。
  いずれにも「**開始時刻より前ならまた押せます**」を添える
- 流れた・取り消されたイベントの詳細に**「同じ内容で新しく作る」**（内容・成立人数・開示タイミング・
  場所を写した新規作成。開始時刻は入れ直す）。ボタンに「**誰でも押せます**」と添える
- 未ログインで「参加」を押したら、ログイン・登録後に参加を確定して詳細へ戻す
  （持ち越すのは押す意図だけ。コメントは持ち越さない）
- 作成フォームの開示タイミングの既定値は「30分前」と「開始までの残り時間の半分」の**短い方**（判断13）
- 細かいフォームの体裁（折りたたみ・送信前プレビュー）は実装時に決める

## 画面の文言・体裁（お店）

- 店リストの並びは**近い順**（検索の中心＝環境変数からアプリ側で距離計算）。
  **座標を持たない店（手で足した店）は末尾に「場所未設定」**としてまとめる
- **店の詳細ページを作る**（評価一覧＋時間帯フィルタ＋自分の評価の編集・削除の導線）。
  店リストからは提案2枠を出さない（提案はルートに集約）
- 「名前が出る」ことの文言を3箇所（お誘いの「見えません」3箇所と対にする）:
  評価フォームの3段階の直下「この評価は、あなたの名前と一緒にずっと表示されます」／
  一言の入力欄「一言は名前と一緒に、消すまで表示されます」／一覧には添えない
- 評価の送信ボタンと参加ボタンの**見た目を揃えない**（匿名の気分のまま記名の「いまいち」を押す事故を防ぐ）
- フッターに地図データの出典表示（OpenStreetMap 系なら「© OpenStreetMap contributors」。ODbL の義務）
- 地図APIは**サーバー（Play）経由**で呼ぶ（キー秘匿・レート制御・「落ちても閲覧できる」をサーバー側で実現）

## PWA

- `start_url` はルート固定。**アイコン下の表示名は「お誘い」**（`Osasoi` はブランド名）
- manifest とアイコンを用意。**オフライン対応はしない**（Service Worker はインストール要件の最小限）
- PWA はインターネット公開とは別論点（公開の可否は 01 質問リストのまま未確認）。
  **PWA でもプッシュ通知は作らない**（03 判断20）

## ログイン要否の一覧

| 画面・API | ログイン |
|---|---|
| イベント詳細の閲覧（概要・状態・成立人数。開示後は一覧も） | **不要**（唯一の例外） |
| 「参加」を押す・取り消す・コメント | 必須 |
| ルート／イベント一覧／イベント作成 | 必須 |
| お店の全画面（リスト・詳細・評価・提案） | 必須（03 判断26） |
| 会員登録・ログイン | — |

## API と認可

- 1コントローラー＝1エンドポイント（リポジトリ規約）。見積もり: 認証4本（既存流用）＋
  お誘い6本（作成／詳細取得／参加／取り消し／コメント書き直し／一覧）＋
  お店5本（リスト・提案／検索代理／評価の投稿（店の新規作成を内包）／更新／削除）
- **未認証で叩けるのは「イベント詳細の取得」1本だけ**。開示条件（成立×時刻）を満たさない間は
  参加者を返さず、状態と（成立後は）人数だけ返す
- 型は `etc/openapi/` に定義して生成（手書きしない）

## 環境変数

| 設定値 | 用途 |
|---|---|
| Slack Incoming Webhook の URL | ボットの投稿（告知先チャンネルは Webhook に内包） |
| アプリのベース URL | Slack 投稿に入れる詳細ページ URL の組み立て |
| 検索の中心（緯度・経度） | 店の検索と近い順の計算 |
| 地図API のエンドポイント（・キー） | 店の検索 |
| セッションの署名鍵・有効期間（30日） | ログインの維持（毎日開く PWA 前提。現状 `AppModule.scala` の固定値を外部化する） |

## 実行構成・DB

- サーバーは**1台構成が前提**（スケジューラは Play 内の1分間隔の定期実行。二重投稿対策は不要。
  複数台にするときが 03 の判断が変わる条件）
- URL の形: お誘い `/events/{uuid}`（列挙対策・判断17）、お店 `/shops/{id}`（全画面ログイン必須のため
  連番で可・判断26）。**2規約の混在は意図的**
- 雛形のマイグレーション SQL（`V20260717_01__create_user.sql`）は設計に合わせて**書き換える**
  （未リリースなので可。`udb_user.state` の既定値を 100 に）。認証は雛形のサーバーサイドセッション方式を踏襲
- 一意制約・インデックス（実装時に確定）: `event.uuid`（一意）、`shop.external_id`（一意・NULL重複可）、
  `event_entry(event_id, canceled_at)`、`shop_review(shop_id, user_id)`、`shop_review.created_at`。
  コンテキストをまたぐ外部キー制約は張らない（雛形の先行例に合わせる）

## テストで必ず守るもの（型でも制約でも守れない）

1. 同じ人の二重押しで有効な参加が2行できない（判断16・悲観ロック）
2. 2人同時の成立ラインで、成立の遷移と投稿が1回だけ
3. 「押す」と「立案者の取り消し」の同時実行が直列化される
4. 開示条件は「成立 × 時刻」の2軸（片方だけで判定しない）
5. 一覧の2人以上ルールと、1人時・0人時の表示分岐
6. 発行順ではなく表示名順（文字コード順）で一覧が並ぶ（先頭＝立案者を防ぐ）
