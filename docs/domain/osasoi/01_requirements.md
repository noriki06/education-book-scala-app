# <お誘い> — 要件定義

## 受け取った要求

「**■ 匿名でイベントの募集がかけられる**

職場の人をランチに誘うのは意外とハードルが高い。お互いに気を使わず、誘いやすく断りやすくしたい。
匿名で『今日ランチに行きたい。何人集まったら行く』というイベントの募集をかけられて、
『参加』が設定した人数に達したら実施が決まる。
誰が言い出したかも、誰が押したかも、成立するまで見えない。集まらなくても誰も傷つかない。
ランチに限らず飲み会・スマブラ大会・日付を指定したランニングまで、
『2時に行く人〜』くらいの軽さで使いたい。

**■ 誘いから店選びまで、ひとつの流れでつながる**

行った店の評価を書けるようにして、部署の行き先の選択肢をどんどん増やしたい。
知らない誰かの点数より、一緒に働いている人の『ここ好き』のほうが信用できる。
書くのは星と一言、何時頃に行って並んだか。書いた人の名前が出る。
誘いを立てるとき店から場所を選んでもいいが、選ばないことのほうが多い。
毎回『みんなでどこ行こう』となるから、**開示のタイミングで『ここがいいかも』の提案が来て**、
それで決まらなければ周辺の店リストも見られるようにしたい。
食べたら、そのままレビューを書ける。誘いがメインで、店はそれを支えるおまけ。

入口は Slack に流れる URL と、ホーム画面のアイコン（アプリみたいに手元に置いておきたい）。
Slack への投稿で立案者がわかってしまわないように」

（人数・開示・取り消し・規模・店の評価の形などの細かい条件は、質問リストの仮回答で確定させる。
スタンプ・称号・位置情報での訪問チェックは不要と発注者が明言 → 03 付録A）

## 確認したいこと（質問リスト）

### お誘いについて（アプリ全体の決めごとを含む）

| 質問 | 今回の回答（仮） |
|---|---|
| 想定規模は？どこまで大きくなる想定か | まず自部署（6人）で始め、会社の成長に合わせて**30人規模**まで見込む。30人なら全員がいる雑談チャンネル1つで回るので、告知先チャンネルは当面1つのまま。部署ごとのチャンネル分けが要る規模（100人級）になったら Channel の昇格・管理者を検討する（→ 03_design.md 判断が変わる条件） |
| Slack に直接「誰か行きませんか」と書けば済むのでは | 済まない場面のために作る。①匿名で言い出せる（Slack は投稿者が必ず見える）②集まらなかったことが誰にも紐づかない（リアクション0の「さらし」が起きない）③誰が押したか見えないので、他人の反応を見てから決める様子見の連鎖が起きない。逆に、記名で「僕たち行くんで来ませんか」と言える場面は Slack で足りる——このアプリの客は「Slack に書けている人」ではなく「書けていない人」 |
| 「何人集まったら」の人数に立案者を含むか | **含む**。立案者は作った時点で参加者の1人と数える（「3人集まったら」＝立案者を入れて3人） |
| 集まる人数の下限は | **1人**。1人＝立案者だけで成立するので、作った瞬間から「成立」になり、「もう行くのは決まっていて追加を募るだけ」の使い方（仮に「確定型」と呼ぶ）を表せる。「N人集まったら行く」の条件付きは2人以上を設定する |
| 成立したあとの参加の取り消しは | **できる**。できないと『参加』を押すハードルが上がる。開示前の取り消しは誰にも知られない（→ 例外・ルール） |
| 流れた・取り消されたあと、また出すのは面倒では | 詳細ページに「**同じ内容で新しく作る**」を置く（開始時刻だけ入れ直す。誰でも押せる → HANDOFF.md） |
| 参加に添えるコメントは誰にいつ見えるか | 任意・自由記述。**開示までは誰にも見せない**（文面の癖で本人が特定されるため。参加者の一覧と同じ扱い）。開示後、一覧と一緒に見える。Slack の投稿・プレビューには載せない。本人は**開示より前なら**いつでも書き直せる（参加はそのまま。開示後は書き直せない） |
| 開示された一覧は誰が見られるか | **URL を開いた人なら誰でも**。開示後はもう記名の世界で、隠す秘密が無い。見えることが駆け込み参加を誘う。ただし Slack の投稿には名前を載せない（転送できて永久に残るため。アプリ内なら取り消しが即反映される）。**一覧が出るのは有効な参加が2人以上のときだけ**——1人だと立案者が確定してしまうため、1人の間は「参加者1人（名前は2人から表示）」とする |
| アプリはインターネットに公開するか | **未確認**。Slack のプレビューは、Slack がインターネット側から詳細ページを読めるときだけ出る。非公開運用ならプレビューは出ない（プレビュー無しでも機能は成立する）。投稿は Incoming Webhook を使う。なお配布は **PWA（ホーム画面に追加できる Web アプリ）に確定**（お店の「毎日開く」使い方が動機の、アプリ全体の決定）。PWA は HTTPS が要るがインターネット公開とは別論点で、公開の可否はこの行のまま未確認 |
| 画面は何があるか | **ルート**（上にお誘いの一覧・下にお店の提案。→ HANDOFF.md）、会員登録・ログイン、イベント作成・詳細、店リスト・店詳細・評価フォーム。一覧はログイン必須で、載せるのは募集中・成立の**7日先まで**。集まっている人数は一覧には載せない（詳細ページで見せる）。過去分の一覧・振り返りは作らない |
| 開示のタイミングはどうやって知るか | 詳細ページに開示時刻を常時表示する（「参加者の一覧は 11:30 から見られます」）。**ボットの投稿は募集1本＋状態変化ごとに1本**（通常2本。確定型は募集が成立を兼ねるので1本。成立後に流れた・取り消された場合だけ3本）で、開示のお知らせ投稿はしない |
| 開示は成立していなくても起きるか | **起きない。開示は「成立している」が前提**。未成立のまま開示時刻を過ぎても見せない（そのまま流れたとき、押した人の名前が出たままになるのを防ぐ）。開示時刻の後に成立したら、成立と同時に開示する |
| 確定型でも、参加者の一覧は開示時刻まで見えないままでよいか | 今回はルールを統一し、確定型も同じ開示ルール（既定30分前）とする。「誰と行くか見てから決めたい」という声が出たら見直す |
| 立案者はイベントを取り消せるか | 専用の取り下げ操作は作らない。**立案者が参加を取り消すと、開示前ならイベントごと取り消しになる**。行きたい人が他にいるなら、その人が新しく作ればいい。開示後の立案者の取り消しは普通の取り消しと同じ扱い（→ 例外・ルール） |
| 参加者の一覧を表示する「開始時刻の30分前」は固定か | **既定は30分前で、立案者がイベントごとに変えられる**。ただし開示時刻（開始時刻−設定値）は作成時点より未来でなければならない（ちょうども不可。作った瞬間から参加者が見えてしまい、匿名の意味がなくなるため） |
| 参加を受け付ける締切は | **開始時刻より前**（ちょうどは不可）。参加も取り消しも同じ締切。開始時刻までに成立しなければそのイベントは流れる |
| 開始時刻・場所は誰が決めるか | 立案者がイベント作成時に開始時刻（開催日を含む）を入れる（必須）。場所は**店から選んでも、自由記述でも、空欄でもよい**（選ばないことが多い前提）。空欄のまま成立したら、開示後にみんなで決める——決めた結果はアプリに書き戻さない（イベントは編集不可のまま） |
| 同じ日に同じような募集が2件立ったら | 合流させず、別々のイベントとして扱う |
| 参加できるのは誰か（参加者を絞る仕組みはあるか） | **絞る仕組み（グループ登録・承認）は持たない**。URL を開いてログインした人なら誰でも参加できる。実質、告知チャンネルにいる人が対象。URL が外に漏れて部外者が参加できてしまうリスクは、社内ツールとして許容する |
| 会員はどう登録し、どう本人確認するか | メールアドレス・表示名・**パスワード**で誰でも登録できる、最小のログイン機能。確認メールは無し（登録した瞬間に使える）。パスワードの再設定は今回作らない（忘れたら管理者が DB で対応 → 03 付録A）。メールの一意判定は大文字小文字を同一視。表示名が、開示のときに見える名前になる。パスワードの持ち方は実装時に udb 内で決める |
| Slack のプレビューや募集の投稿には何を載せるか | 内容・開始時刻・**成立人数（何人で成立か）**などの概要だけ。**立案者・参加者・集まっている人数は載せない**（ログイン前でも見える情報なので、見せないルールと矛盾しないものに限る） |
| 成立・開示の通知はどうやって届くか | **成立・流れたは、ボットがチャンネルに投稿する**（名前と人数は一切出さない）。守るべき秘密は「誰が」であって「成立した事実」ではないため。成立が見えることはむしろ駆け込み参加を誘う。参加者の一覧はアプリの詳細ページだけで見せる。DM などの個人向け通知は作らない |
| 日付の指定はどこまでできるか | 開催日＋開始時刻を立案者が**1つに決めて**指定する。当日でも未来日でもよく、**90日先まで**作れる（→ 03 入力の上限）。ただし候補日を並べてみんなで決める**日程調整はやらない**（成立条件を人数の一軸に保つ） |
| 人数が集まらなかったイベントの記録は | 消さずに残す。ただし誰が「参加」を押していたかは、本人以外の誰にも（立案者にも）表示しない |
| 要求文にない仮の呼称 | 人数が集まることを仮に「**成立**」、開示時刻に参加者の一覧が見えることを仮に「**開示**」、集まらずに終わることを仮に「**流れる**」と呼ぶ。業務の呼び方は未確認 |

### お店について

| 質問 | 今回の回答（仮） |
|---|---|
| お誘いとお店の関係は | 同じアプリの別コンテキスト（変わる理由・データの性質が違う）だが、**別案件ではなく一連の流れ**——誘いを立てる→開示で「どこ行こう」→開催→レビュー、を通しでサポートする。参照は**お誘い→お店の一方向だけ**（場所として店を選べる・提案を表示する）。お店側はお誘いを一切知らない。評価は記名の別軸情報で、匿名（立案者・開示前の参加者）とは衝突しない |
| 店はどうやってマスタに載るか | **誰かが評価を書いた店だけ**が載る。評価を書くとき地図APIで検索して店を確定し、そのとき初めてマスタに写す（相手側 ID・店名・位置）。**検索で見つからない店は、名前と大まかな場所だけで手で足せる**（相手側 ID は無しを許す）。周辺全件の取り込み・定期的な再取得はやらない——部署の誰も知らない店が視界を埋める・書きたい店が無い・再取得で評価が孤児になる、の3つの害を避けるため |
| 同じ店が別名で2行できたら | 30人規模なので許容する。統合機能は作らない（気になったら管理者が DB で直す） |
| 評価は誰が・どの店に書けるか | ログインした会員なら誰でも・書きたい人だけ。**訪問の証明はしない**（自己申告）。昔行った店もよい |
| 評価に書くことは | **3段階（また行きたい／ふつう／いまいち）だけで送信できる**。時間帯（〜11時台／12時台／13時台／14時以降）・並んだか・一言（100字まで）は**すべて任意**（昔の店は時間帯を覚えていないのが普通のため） |
| 要求文の「星」は5段階では | 要求文は段階数を指定していない。**記名の身内では星2が押せず4〜5に潰れて平均が機能しない**ため、3段階で受ける。平均点は出さず「また行きたい N人」と**人数**で見せる |
| 同じ店に何回も書けるか | 書ける（行くたびに書いてよい）。ただし「また行きたい」は**人数**で数え（同じ人が10回書いても1人）、混雑は**件数**で数える |
| 「空いていそうな店」はどう見せるか | **断定しない**。「14時台に行った3人のうち、並んだのは0人」と件数ごと見せる。その時間帯の声が**2件未満なら出さない**。混雑の集計は**投稿から6ヶ月以内**の評価だけ（混雑は腐るため） |
| 「ここがいいかも」の提案はどう出すか | **3つの場面に出す**——①イベント作成の場所選び ②**開示後のイベント詳細**（「みんなでどこ行こう」の瞬間。場所が未定のイベントに出す）③ルート。決まらないときのために**周辺の店リストへの導線**も添える。**中身は常に部署全体の評価**（また行きたいが多い店）で、**参加者の評価履歴・好き嫌いは使わない**——誰が行った/行っていないが逆算できてしまうため（→ 03 判断27）。「このメンバーだと」「苦手の考慮」は判断が変わる条件へ予約 |
| 食べたらレビューを書く流れは | 開始時刻を過ぎた成立イベントの詳細に「**この店をレビューする**」導線を出す（店が選ばれていた場合。未定なら店の検索へ）。開催の事実は記録しない——導線だけで、書くかは本人の任意（→ 03 判断10） |
| 食べログや Google の評価は使えないか | **使わない**。食べログに公式 API は無く、Google の評価は課金と「地図表示とセット」の規約制約が重い。自前の評価を主軸にし、**各店に「Google マップで見る」リンク**を置く（無料・規約問題なし）。外部の点数の取り込みもやらない——「部署のみんなが知っていること」でなくなるため（→ 03 判断32） |
| 評価の編集・削除は | 本人はいつでもできる。ただし集計は**現在有効な評価だけ**から導出するので、過去に見た数字と食い違いうる（それでよしとする） |
| 検索の中心（会社の位置）は誰がどう決めるか | 「検索の中心を決める人」（部署の誰か）が決め、環境変数で持つ（告知先チャンネルと同じ形） |
| 最初は評価ゼロでは（コールドスタート） | 機能では解かない。**リリース日に部署で「よく行く店を3件書く」15分の会**をやる（運用）。外部サイトの点数の取り込み・管理者による代理登録はやらない——「みんなが知っていること」でなくなるため |
| 要求文にない仮の呼称（お店の分） | 「**店マスタ**」「**時間帯**」「**3段階**」「**一言**」は仮の呼称。特に「一言」は、お誘いの「コメント」（参加に添える・開示まで秘匿）と**別概念**のため別の語にした |

## 業務フロー

### お誘い

[告知先を決める人（部署の誰か）]

1. 募集を流す Slack チャンネルを告知先として決める
   （今回は設定画面を作らず、デプロイ時の環境変数で実現する → 03 付録A）。

[立案者（部署の誰か）]

2. アプリにログインし、イベントを作る（内容＝ランチ・飲み・スマブラ・ランニングなど、
   開始時刻＝開催日を含む・当日でも未来日でもよい、成立人数、
   開示タイミング＝任意・既定は開始時刻の30分前、
   場所＝任意——**店から選んでも、自由記述でも、空欄でもよい**。選ぶ画面には
   部署の評価と提案が出る）。作った時点で、立案者自身は参加者の1人に数えられる。

[システム]

3. 告知先の Slack チャンネルに、ボットの名義で募集を投稿する。
   立案者の名前は載せない。概要（内容・開始時刻・成立人数）と詳細ページの URL を付ける。
4. URL が Slack に貼られたときは、概要のプレビューを出す（集まっている人数・立案者・参加者は出さない）。

[URL を見た人]

5. URL を開き、詳細（内容・開始時刻・場所・開示時刻）を見る。
   成立するまでは、いま何人集まっているかは見えない（成立後は人数だけ見える）。
6. 参加するなら、ログインして「参加」を押す。押すときに一言コメントを添えられる
   （任意。例：「遅れて行きます」）。押したこともコメントも、開示まで誰にも見えない。
   会員登録さえ済んでいれば、それ以上の手続きは無く、押せばそのまま参加者になる。
7. 気が変わったら、開始時刻より前なら参加を取り消せる。コメントは開示より前なら書き直せる。

[システム]

8. 参加者が成立人数に達したら、ボットがチャンネルに「成立した」ことを投稿する。
   名前と集まっている人数は出さない。「参加者の一覧は開示時刻からアプリで見られる」旨を添える。
9. 成立していて開示時刻（既定は開始時刻の30分前。立案者がイベントごとに変えられる）を
   過ぎたら、その時点の参加者の一覧を、コメントと一緒に、アプリの詳細ページで開示する
   （URL を開いた人なら誰でも見られる）。ボットの追加投稿はしない。
   **場所が未定のイベントなら、あわせて「ここがいいかも」の提案（部署の評価から）と
   周辺の店リストへの導線を詳細ページに出す**——「みんなでどこ行こう」の材料。
10. 開示より前に、取り消しで参加者が成立人数を割ったら、自動で流れたことにし、
    ボットがチャンネルに「流れた」ことを投稿する。
11. 開示より後に成立人数を割っても、成立のままにする。取り消しは開示済みの一覧に
    反映され、行くかどうかは残った参加者に任せる（0人になっても成立のまま。
    表示だけ「参加者がいなくなりました」になる）。
12. 開始時刻までに成立しなければ「流れた」ものとして締め、
    ボットがチャンネルに「流れた」ことを投稿する。

[参加者]

13. 開示された参加者で集合し、開催する。

[システム]

14. 開始時刻を過ぎた成立イベントの詳細に「**この店をレビューする**」の導線を出す
    （店が選ばれていた場合。未定だったなら店の検索へ）。書くかは本人の任意。

### お店

[検索の中心を決める人（部署の誰か）]

1. 店を検索するときの中心（会社の位置）を決める
   （設定画面は作らず、デプロイ時の環境変数で実現する）。

[会員]

2. リスト（近い順）で店と評価を眺める。時間帯で絞ると、その時間帯に行った人の声だけが見える。
   リストの上に「また行きたいが多い店」「自分がまだ評価していない店」が1件ずつ出る。
3. 行った店（昔でもよい）の評価を書く。店は地図APIで検索して選ぶ
   （見つからなければ名前と大まかな場所で手で足せる）。
   3段階だけで送信でき、時間帯・並んだか・一言は任意。一言には名前が表示される。

[地図API（外部サービス）]

4. 検索のたびに店の候補と位置を返す。落ちていても、すでにマスタにある店の閲覧・評価はできる
   （止まるのは店の検索と新規の追加だけ）。

[会員]

5. 声を見て店を決める。誘いたくなったら上のお誘いで誘いを立てる（場所欄でその店を選べる）。

## 例外・ルール

**お誘いについて**

- 立案者が誰かは、成立した後も開催した後も、永久に誰にも表示しない。
- 開示は「成立している」＋「開示時刻を過ぎている」の両方がそろって起きる。
  未成立のまま開示時刻を過ぎても見せない。開示時刻の後に成立したら、成立と同時に開示する。
- 成立した後も、開始時刻より前なら追加で「参加」を押せる（要求は「何人**以上**なら行く」）。
- 成立人数は1人から設定できる。1人なら作った瞬間に成立し、募集の投稿は最初から
  「やることは決まっている。来たい人はどうぞ」の体になる（確定型）。
- 通知はすべてボットのチャンネル投稿で行い、名前と集まっている人数は一切出さない。
  個人にだけ届く通知（DM）は作らない。参加者の一覧はアプリの詳細ページだけで見せる
  （開示後は URL を開いた人なら誰でも見られる。Slack には名前を載せない）。
- 参加の取り消しは開始時刻より前ならいつでもできる。開示より前の取り消しは誰にも知られない。
  開示より後の取り消しは、開示済みの一覧から消えるので参加者に見える。それは現実のドタキャンと同じ扱い。
- 立案者も参加を取り消せる。**開示より前に立案者が取り消したら、イベントごと取り消しになり**、
  ボットがチャンネルに「取り消された」ことを投稿する（誰が立案者かは出さない）。
  確定型でも同じで、これが確定型を止める唯一の手段になる。
  まだ行きたい人がいれば、その人が新しくイベントを作ればいい。
- 開示より後に立案者が取り消した場合は、イベントごと取り消しにはせず、普通の取り消しと
  同じ扱いにする。イベントごと消すと、一覧から消えた人＝立案者だと推測できてしまうため。
- 流れたイベントは、誰が「参加」を押していたかを誰にも見せない（立案者にも見せない）。
  「3人の予定が2人しか集まらず、その2人だけ気まずい」を起こさないため。
- 参加の意思表示は必ずアプリの中で押す。Slack のリアクションや返信では受け付けない
  （Slack 上では誰が反応したか全員に見えてしまい、成立まで見せないルールが守れないため）。
- URL を開けば誰でも詳細を見られるが、「参加」を押すにはログインが要る。
  参加できる範囲は URL が届く範囲（実質、告知チャンネルにいる人）で、アプリ側では絞らない。
- Slack に出る募集の投稿とプレビューには、立案者・参加者・集まっている人数を一切載せない。
  載せてよいのは内容・開始時刻・成立人数（何人で成立か）など、誰に見られてもよい概要だけ。
- 流れた・取り消されたイベントも記録として消さずに残す。

**お店について**

- 店がマスタに載るのは、誰かが最初の評価を書いたときだけ。評価が1件も無い店は存在しない。
- 集計（また行きたいの人数・混雑）は現在有効な評価だけから導出し、保存しない。
  混雑は投稿から6ヶ月以内・2件以上のときだけ表示する。
- 「また行きたい」は人数で数える（同じ人が何回書いても1人）。混雑は件数で数える。
- 提案（また行きたいが多い店・まだ評価していない店）は保存せず、開くたびに導出する。
- お店はお誘いのデータ（イベント・参加・立案者）を一切参照しない。お誘い→お店は、
  場所として選んだ店の ID と、評価・提案の**表示**だけ（一方向）。
- 開示後の詳細に出す提案は、**部署全体の評価だけ**から作る。参加者の評価履歴・好き嫌いは
  使わない（誰が行った/行っていないの逆算を防ぐ）。
- 一言は記名。承認・通報の仕組みは作らず、消せるのは本人だけ。
- 地図API が落ちても閲覧・評価はできる。出典表示などの利用条件は実装前に確認する。
