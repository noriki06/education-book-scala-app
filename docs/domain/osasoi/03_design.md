# <お誘い> — 詳細要件定義

呼称は日本語も英語もそろえる（→ 02_analysis.md / naming.md）。
追加の要求はまだ無いため、全体が①（当初の要求からある分）にあたる。
お誘い（`event`）とお店（`shop`）の2つの文脈を、1つのアプリ（Osasoi）の設計として扱う。

**この設計の要点は5つ。**

1. ドメインのモデルは5つ——会員（`User`・udb）、イベント（`Event`）・参加（`EventEntry`・event）、店（`Shop`）・評価（`ShopReview`・shop）。認証用のモデルは実装時に udb へ足す（→ 判断12）
2. 参照は `event → udb` と `shop → udb` の一方向。**event と shop は互いに参照しない（結合ゼロ）**
3. イベントの状態は4値（募集中／成立／流れた／取り消された）。**参加者数・開示済み・確定型は保存せず、計算で求める**
4. 匿名の境界は**開示**（既定は開始時刻の30分前。イベントごとに変えられる）。開示前は誰が押したか誰にも見えない。開示後は見える
5. お店側も保存しない——集計・提案・混雑はすべて評価の台帳から導出。店は最初の評価と同時に生まれる

## 用語 — 全体の用語集に追加する呼称

| 呼称（これで統一する） | 何を指すか | 言い換えない |
|---|---|---|
| 会員 | アプリにログインする部署の人。立案と参加の主体 | ユーザー、アカウント、利用者 |
| イベント | 1回の誘い。成立するか、流れるか、取り消されて終わる | 企画、飲み会、募集（Slack 投稿の表現としてだけ使う） |
| 参加 | イベントに「参加」を押した記録。取り消されていないものを**有効な参加**と呼ぶ | エントリー、出席、行ける、申し込み |
| コメント | 参加に添える短い文（例：「遅れて行きます」）。任意。開示まで誰にも見せない | メッセージ（Slack の「メッセージ ID」という技術語は例外）、メモ、備考 |
| 内容 | イベントで何をするか（例：「ランチ」「スマブラ大会」）。自由記述 | タイトル、題名、件名 |
| 場所 | 集合・開催の場所。自由記述・任意。店を含むより広い概念（会議室・集合地点も入る） | 会場、ロケーション（「店」はお店の文脈の正式呼称になったため禁止語から外した → 判断22） |
| 募集中 | イベントの状態の1つ（`IS_RECRUITING`）。成立する前の状態 | 受付中、オープン |
| 参加者 | 有効な参加を持つ人。立案者を含む | メンバー、顔ぶれ |
| 立案者 | イベントを作った人。参加者の1人に数える。誰かは永久に表示しない | 発案者、主催者、幹事、作成者 |
| 成立人数 | 立案者を含む、成立に必要な人数 | 定員（上限ではなく下限）、最低人数 |
| 開始時刻 | イベントが始まる日時。**開催日を含む**（当日でも未来日でもよい）。参加の締切・流れの判定の基準 | 開催日時、集合時間、開催時刻 |
| 開示タイミング | 開始時刻のどれだけ前に開示するか。**既定は30分前**で、立案者がイベントごとに変えられる | 公開タイミング、表示時刻 |
| 成立 | 参加者の数が成立人数に達すること | 開催決定、マッチング |
| 確定型 | 成立人数1のイベント（作った瞬間に成立。「来たい人はどうぞ」の使い方） | 開催確定イベント |
| 開示 | **成立しているイベント**で、開示時刻（開始時刻 − 開示タイミング）から、参加者の一覧（名前・コメント）が URL を開いた人に見えるようになること。一覧が出るのは有効な参加が**2人以上**のとき（→ 判断18） | 公開、発表（「公開用 UUID」「インターネットに公開」など、開示と無関係の複合語は例外） |
| 流れる | 開始時刻までに成立しない、または開示前の人数割れで終わること | 不成立、失敗、廃案 |
| （イベントの）取り消し | 開示前に立案者が参加を取り消して、イベントが終わること | 中止、取り下げ、キャンセル、削除（評価の物理削除という操作の語としては使う。イベントの取り消しの言い換えとしてだけ禁止） |
| 告知先 | ボットが投稿する Slack チャンネル | 通知先、連携チャンネル |
| 店 | 評価の対象。最初の評価と同時にマスタに載る | 飲食店、レストラン、ストア（「お店」は文脈の呼び名としてだけ使う） |
| 評価 | 店への1回の投稿。3段階＋任意の時間帯・並んだか・一言 | レビュー、口コミ、点数、評点 |
| 3段階 | 評価の値。**また行きたい／ふつう／いまいち** | 星、スコア |
| 時間帯 | 行った時間の区分。〜11時台／12時台／13時台／14時以降 | タイムスロット（「時刻」は開始時刻・開示時刻の構成語なので語自体は禁止せず、時間帯の言い換えとしてだけ使わない） |
| 一言 | 評価に添える記名の短い感想。**コメント（参加に添える・開示まで秘匿）とは別概念**（常時表示） | メッセージ、感想 |
| 店マスタ | マスタに載った店の全体（＝店エンティティの集合の呼び名）。独立したモデルではなく、取り込みバッチも無い | 店舗一覧、店データ |
| 混雑の声 | 「その時間帯に行った N人のうち、並んだのは M人」という表示。断定しない | 空き情報、混雑度 |
| 提案 | 店リストの上に出す2枠（また行きたいが多い店・自分がまだ評価していない店）。本人向け | おすすめ、レコメンド |

## EntityModel

5つとも今回このアプリのために設計する（会員・認証も設計対象。→ 判断12）。
`User` にイベント側の情報（参加履歴など）は1列も足さない。名前は `naming.md` で確定済み。

### <会員（User）>

ログインする人。立案者・参加者の主体。開示のときに参加者へ見えるのは `name`（表示名）。

```scala
case class User(
  id:        Option[Id],                // 管理 ID（永続化前は None）
  uuid:      UUID,                      // 公開用 UUID
  email:     String,                    // ログイン ID（一意）
  name:      String,                    // 表示名。開示のときに参加者へ見える名前
  state:     Status = Status.IS_ACTIVE, // 会員の状態（区分値）
  updatedAt: LocalDateTime = Now,       // データ更新日
  createdAt: LocalDateTime = Now        // データ作成日
) extends EntityModel[Id]

object User:

  type   Id   = Id.Repr
  type   UUID = UUID.Repr
  object Id extends Entity.Id[Long]

  /** 公開用 UUID */
  object UUID extends Entity.Id[String]:
    def generate: UUID = UUID(java.util.UUID.randomUUID.toString)

  /** 会員の状態 */
  enum Status(val code: Short) extends EnumStatus[Short]:
    case IS_INACTIVE extends Status(code = -100) // 無効（運用上の停止。退会機能は作らない → 付録A）
    case IS_ACTIVE   extends Status(code =  100) // 有効
```

### <イベント（Event）>

```scala
case class Event(
  id:                 Option[Id],                        // 管理 ID（永続化前は None）
  uuid:               UUID,                              // 公開用 UUID。URL にはこれを使う（→ 判断17）
  plannerId:          User.Id,                           // 立案者（User と *:1）。画面には永久に出さない（→ 判断6）
  title:              String,                            // 内容（例："ランチ"、"スマブラ大会"）。自由記述・50字まで
  place:              Option[String] = None,             // 場所。自由記述・任意・100字まで
  requiredEntryCount: Int,                               // 成立人数。立案者を含む頭数（1〜30）。1 なら確定型
  startAt:            LocalDateTime,                     // 開始時刻（開催日を含む。未来日も可）。締切・流れの基準
  revealBefore:       Duration = Duration.ofMinutes(30), // 開示タイミング。開始時刻のどれだけ前に開示するか（→ 判断13）
  state:              Status = Status.IS_RECRUITING,     // イベントの状態（区分値、→ 判断1）
  updatedAt:          LocalDateTime = Now,               // データ更新日
  createdAt:          LocalDateTime = Now                // データ作成日
) extends EntityModel[Id]

object Event:

  type   Id   = Id.Repr
  type   UUID = UUID.Repr
  object Id extends Entity.Id[Long]

  /** 公開用 UUID */
  object UUID extends Entity.Id[String]:
    def generate: UUID = UUID(java.util.UUID.randomUUID.toString)

  /** イベントの状態 */
  enum Status(val code: Short) extends EnumStatus[Short]:
    case IS_CANCELED   extends Status(code = -200) // 取り消された（開示前に立案者が参加を取り消した）
    case IS_FAILED     extends Status(code = -100) // 流れた（開始時刻までに成立しなかった／開示前の人数割れ）
    case IS_RECRUITING extends Status(code =  100) // 募集中
    case IS_CONFIRMED  extends Status(code =  200) // 成立
```

### <参加（EventEntry）>

```scala
case class EventEntry(
  id:         Option[Id],                   // 管理 ID（永続化前は None）
  eventId:    Event.Id,                     // どのイベントへの参加か（Event と *:1）
  userId:     User.Id,                      // 誰の参加か（User と *:1）
  comment:    Option[String] = None,        // 参加に添える一言（例："遅れて行きます"）。開示まで誰にも見せない（→ 判断14）
  canceledAt: Option[LocalDateTime] = None, // 取り消した日時。None なら有効な参加。一度入れたら戻さない（押し直しは新しい行）
  updatedAt:  LocalDateTime = Now,          // データ更新日
  createdAt:  LocalDateTime = Now           // データ作成日 ＝「参加」を押した日時
) extends EntityModel[Id]

object EventEntry:

  type   Id = Id.Repr
  object Id extends Entity.Id[Long]
```

### <店（Shop）>

評価の対象。**最初の評価が書かれたときに生まれる**（単独で作る画面は無い）。

```scala
case class Shop(
  id:         Option[Id],              // 管理 ID（永続化前は None）
  externalId: Option[String] = None,   // 地図API側の ID。手で足した店は None（→ 判断25）
  name:       String,                  // 店名（50字まで）
  latitude:   Option[BigDecimal],      // 緯度。手で足した店は None のことがある
  longitude:  Option[BigDecimal],      // 経度。同上
  address:    Option[String] = None,   // 大まかな場所（自由記述・100字。手で足した店の目印用）
  updatedAt:  LocalDateTime = Now,     // データ更新日
  createdAt:  LocalDateTime = Now      // データ作成日 ＝ 最初の評価が書かれた日時
) extends EntityModel[Id]

object Shop:

  type   Id = Id.Repr
  object Id extends Entity.Id[Long]
```

### <評価（ShopReview）>

「誰が・どの店を・どう言ったか」の1件。**本人はいつでも書き直せる・消せる**（→ 判断24）。

```scala
case class ShopReview(
  id:        Option[Id],               // 管理 ID（永続化前は None）
  shopId:    Shop.Id,                  // どの店への評価か（Shop と *:1）
  userId:    User.Id,                  // 誰の評価か（User と *:1）。名前は常時表示される
  rating:    Rating,                   // 3段階（これだけで送信できる）
  timeSlot:  Option[TimeSlot] = None,  // 行った時間帯。昔の店は覚えていないので任意
  waited:    Option[Boolean]  = None,  // 並んだか。未回答を許す
  remark:    Option[String]   = None,  // 一言（100字・改行なし）。任意
  updatedAt: LocalDateTime = Now,      // データ更新日
  createdAt: LocalDateTime = Now       // データ作成日 ＝ 投稿日時（混雑の集計の6ヶ月判定に使う）
) extends EntityModel[Id]

object ShopReview:

  type   Id = Id.Repr
  object Id extends Entity.Id[Long]

  /** 3段階 */
  enum Rating(val code: Short) extends EnumStatus[Short]:
    case IS_DISAPPOINTED extends Rating(code = -1) // いまいち
    case IS_NEUTRAL      extends Rating(code =  1) // ふつう
    case IS_WANT_AGAIN   extends Rating(code =  2) // また行きたい

  /** 時間帯 */
  enum TimeSlot(val code: Short) extends EnumStatus[Short]:
    case IS_UNTIL_11  extends TimeSlot(code = 1) // 〜11時台
    case IS_AROUND_12 extends TimeSlot(code = 2) // 12時台
    case IS_AROUND_13 extends TimeSlot(code = 3) // 13時台
    case IS_FROM_14   extends TimeSlot(code = 4) // 14時以降
```

**ここで型が語っていること**（理由は付録Bの番号を参照）

- `EventEntry` は状態を持たない台帳に近い。有効か取り消し済みかは `canceledAt` の有無で分かる（→ 判断4）
- 参加者数・開示済み・確定型は保存しない。すべて計算で求める（→ 判断2・判断8）
- 立案者の参加も `EventEntry` の1行。立案者かどうかは `Event.plannerId` との比較で分かる（→ 判断3）
- 告知先はモデルにしない。環境変数で持つ（→ 判断7）
- `ShopReview` は状態（Status）を持たない。台帳ではなく**上書き・削除を許す可変の記録**（→ 判断24。
  お誘いの「追記のみ」原則からの意図的な逸脱）
- お店側の集計・提案はどこにも保存しない。すべて `ShopReview` から導出（→ 判断23）
- `Shop` に公開用 UUID は持たない。店の画面はすべてログイン必須で、隠すものがない（→ 判断26）

**型では守れない決めごと**

- 有効な参加（`canceledAt` が `None`）は、同じ人 × 同じイベントで**最大1行**。
  `canceledAt` は `None` に戻さない。押し直しは新しい行
- `comment` は本人が**開示より前なら**いつでも書き直せる（参加はそのまま）。
  開示後と、取り消し済みの行は編集不可。可変列だが履歴の根拠には使わない（→ 判断14）
- イベント作成時は `Event` と立案者の `EventEntry` を**同じトランザクションで**作る。
  成立人数1なら `IS_CONFIRMED` で作る（確定型）
- `state` の更新は「作る」「押す」「取り消す」「時刻で締める」の4つの操作関数に絞る。
  **成立しているかの正は `state`。** 参加者数から数え直さない（→ 判断1）
- 「参加」を押せるのは `IS_RECRUITING` / `IS_CONFIRMED` で、開始時刻より前のイベントだけ。
  **参加の取り消しも開始時刻より前まで**（開始時刻ちょうどはどちらも不可）
- 参加の追加・取り消しと状態遷移は、**イベント行をロックして同じトランザクションで**行う
  （二重押し・成立の二重投稿・立案者の取り消しとの競合を防ぐ → 判断16）
- 入力の上限（確定）: 内容50字・場所100字・コメント100字（改行なし）・成立人数1〜30・
  開始時刻は90日先まで・開示タイミングは0〜24時間（分単位の整数で保存する）。
  メールアドレスの一意判定は大文字小文字を同一視する
- `requiredEntryCount`（1以上）・`plannerId`・`revealBefore` は作成後に変更しない
- `startAt` は開催日を含む日時。当日でも未来日でもよいが、**立案者が1つに決める**（候補日は持たない → 判断11）
- `revealBefore` は0以上。**開示時刻（`startAt` − `revealBefore`）は作成時点より未来で
  なければならない**（ちょうども不可。確定型が作った瞬間に開示される抜け道を塞ぐ → 判断13）
- 時刻はすべて日本時間（JST）固定で扱う（サーバー・DB とも。**アプリ全体の決めごとで、
  お店の6ヶ月判定・時間帯にも適用する**）。スケジューラは1分間隔で、
  「流れた」の投稿が数分遅れることは許容する

**型では守れない決めごと（お店）**

- `Shop` は最初の評価と**同じトランザクションで**作る。評価0件の `Shop` を作る経路は無い。
  最後の評価が消えても `Shop` は残す（評価0件の店は画面に出さないだけ）
- 同じ `externalId` の店は2行作れない（DB の一意制約で防ぐ。`None` どうしの重複は可）
- `Rating` の code はマイナス＝否定的、プラス＝肯定的（状態ではないので100刻みは適用しない）
- 「また行きたい」の集計は**人数**（同じ人の複数評価は1人と数え、`createdAt` が最新の `rating` を使う）。
  混雑の集計は**件数**で、`createdAt` が6ヶ月以内・その時間帯が2件以上のときだけ表示する
- 入力の上限: 店名50字・場所メモ100字・一言100字（改行なし）。字数は文字（コードポイント）で
  数え、前後の空白は除いて保存する（お誘い側の入力にも共通のポリシー）
- お店にスケジューラ・バッチは無い

| 102 | 21 | B | **10:31** | 10:15 | B は一度押して取り消した |
| 103 | 21 | C | `None` | 10:40 | C が押して2人 |
| 104 | 21 | B | `None` | 11:05 | **B の押し直し（行102は書き換えず、新しい行）**。3人で成立 |

B が迷った履歴（行102・104）はそのまま残るが、画面に出るのは有効な参加だけ。

- B の評価202は3段階だけの最小投稿（時間帯・並び・一言すべて未回答）——これが許される形

## 区分値の考え方

マイナスが終了、プラスが進行中〜正常。遷移は4本だけ。

| 遷移 | きっかけ |
|---|---|
| `IS_RECRUITING` → `IS_CONFIRMED` | 参加者数が成立人数に達した（成立の投稿と同時） |
| `IS_CONFIRMED` → `IS_FAILED` | **開示前**の取り消しで成立人数を割った（流れたの投稿と同時） |
| `IS_RECRUITING` → `IS_FAILED` | 開始時刻が来ても成立しなかった |
| `IS_RECRUITING` / `IS_CONFIRMED` → `IS_CANCELED` | **開示前**に立案者が参加を取り消した |

- 「成立」を参加者数からの導出にしないのは、**開示後は人数が割れても成立のままにする**
  （数と状態がわざと食い違う）仕様のため（→ 判断1）
- **開示済みは状態に入れない。** 「成立している かつ 現在時刻 ≥ 開始時刻 − 開示タイミング」で求まる（→ 判断2・判断15）
- **開催済みも状態に入れない。** `IS_CONFIRMED` のまま開始時刻を過ぎたら開催とみなす（→ 判断10）

## 判定ルール

### いつ何をするか

| きっかけ | すること |
|---|---|
| イベントを作った | `Event` と立案者の `EventEntry` を1行ずつ作る（成立人数1なら `IS_CONFIRMED` で）。ボットが募集を投稿（名前は出さない。**確定型は募集の投稿が成立を兼ね、別途の成立投稿はしない**。体裁は「やります。来たい人どうぞ」） |
| 「参加」を押した | 有効な参加が無いことを確認して1行足す。**`IS_RECRUITING` で**成立人数に達したら `IS_CONFIRMED` にして成立を投稿（**遷移が起きた1回だけ。成立後の追加参加では投稿しない**） |
| 参加を取り消した | `canceledAt` を書く。**開示前**に成立人数を割ったら `IS_FAILED` にして流れたを投稿。**開示後**は `state` を変えない（一覧から消えるだけ。0人になっても状態は変えず、表示だけ「参加者がいなくなりました」にする） |
| 立案者が参加を取り消した | **開示前**：`IS_CANCELED` にして取り消されたを投稿（人数は関係ない。確定型を止める唯一の手段）。押す前に**本人の画面にだけ**「イベントごと取り消される」ことの確認を出す（本人にしか見えないので匿名は破れない）。**開示後**：普通の取り消しと同じ（→ 判断6） |
| 開始時刻が来た | `IS_RECRUITING` のままなら `IS_FAILED` にして流れたを投稿。`IS_CONFIRMED` はそのまま（開催とみなす）。`IS_FAILED` / `IS_CANCELED` には何もしない。**この判定は分単位のスケジューラが実行する**（画面を開いたときの判定だと、誰も開かなければ投稿されないため） |
| 開示時刻（開始時刻 − 開示タイミング）が来た | **何も書き込まない**。成立していれば詳細ページの表示が変わるだけ（スケジューラも不要）。未成立なら何も起きない。ボットの追加投稿もしない |

ボットの投稿は**募集1本＋状態変化ごとに1本**（通常2本。**確定型は募集が成立を兼ねるので
通常1本**。成立の後に流れた・取り消された場合だけ3本）。どの投稿にも内容・開始時刻・
成立人数・詳細ページの URL を入れ、成立の投稿には開示時刻も明記する
（どのイベントの話か、投稿単体で分かるように）。
投稿は状態の変更と**切り離す**。正はあくまで状態で、投稿できなくても
イベントの状態は巻き戻さない。再試行や投稿の編集もやらない（→ 付録A）。

### 誰に何が見えるか

**開示は「成立している」＋「開示時刻を過ぎている」の両方がそろって起きる**（→ 判断15）。
未成立のまま開示時刻を過ぎても、その後に成立するまでは何も見せない。

| 情報 | 成立前 | 成立後〜開示前 | 開示後 |
|---|---|---|---|
| 内容・開始時刻・場所・開示時刻 | URL を開けば誰でも | 同左 | 同左 |
| 成立人数（何人で成立か）・イベントの状態 | 誰でも | 誰でも | 誰でも |
| 集まっている**人数** | **誰にも見えない** | **誰でも**見える | 誰でも見える |
| 参加者の**一覧**（名前・コメント） | 誰にも見えない | 誰にも見えない | **URL を開いた人なら誰でも**見える（有効な参加のみ。**2人以上のときだけ**。並びは**表示名順（文字コード順）** → 判断18） |
| 立案者が誰か | 誰にも見えない | 誰にも見えない | 誰にも見えない（**永久**） |
| 自分が押しているか・自分のコメント | 本人にだけ見える | 本人にだけ見える | 本人にだけ見える（一覧にも載る） |

流れた・取り消されたイベントは、成立しないまま（または開示前に）終わるため**開示は一度も
起きない**。誰が押していたかは永久に誰にも見えず、集まっていた人数も出さない（結末の表示だけ）。
イベントの取り消しでは、他の参加者の `canceledAt` は書かない（取り消したのは立案者だけ。
イベントの状態が終了を表す）。

Slack に出してよいのは、この表の上2行（内容・開始時刻・場所・開示時刻・成立人数・状態）の
範囲に限る。**集まっている人数・立案者・参加者の名前は Slack には絶対に載せない**
（転送できて永久に残るため。アプリ内なら取り消しが即反映される）。

参加者数は、その `eventId` の `EventEntry` のうち `canceledAt` が `None` の行数（立案者の行も含む）。
この数を使ってよいのは、遷移の判定・成立後の人数表示・開示後の一覧表示で、
「成立しているか」は `state` を見る。

### 画面の決めごと

- 「誰に何が見えるか」の表は、**画面の文言仕様でもある**。参加ボタンの直下に
  「押したこともコメントも、開示（時刻）まで誰にも見えません」、成立前の詳細に
  「何人集まっているかは誰にも見えません」、開示後の一覧の上に
  「この一覧は URL を開いた人なら誰でも見られます」を出す
- 流れた・取り消されたイベントの詳細ページに**「同じ内容で新しく作る」**を置く
  （内容・成立人数・開示タイミング・場所を写した新規作成。開始時刻は入れ直す。誰でも押せる）。
  ボタンには「**誰でも押せます**」と添える——作り直し＝立案者の再投稿、という推測を成り立たなくするため
- 未ログインで「参加」を押したときは、ログイン・登録のあと参加を確定して詳細ページへ戻す
  （持ち越すのは押す意図だけ。コメントは持ち越さず、登録後に書いてもらう——
  一番複雑で一番通らない経路を初回から作らない）
- 開催前のイベントの**一覧ページ**を作る。**ログイン必須**（未ログインに全件を列挙させない
  → 判断17）。載せるのは `IS_RECRUITING` / `IS_CONFIRMED` で開始時刻が**7日先まで**のもの
  （流れた・取り消されたは載せない）。**集まっている人数は一覧には載せない**
  （「参加者1人」が並ぶ光景を作らない。人数は詳細ページで見せる）。並びは開始時刻の昇順。
  過去分の一覧・振り返りは作らない（→ 付録A）
- 取り消しの確認文は、開示前後・立案者かどうかで出し分ける（すべて**本人の画面にだけ**出す）。
  立案者・開示前=「イベントごと取り消されます」／立案者・開示後=「あなたの参加だけが取り消されます」／
  参加者・開示前=「取り消したことは誰にも見えません」／参加者・開示後=「一覧からあなたの名前が消えます」。
  いずれにも「**開始時刻より前ならまた押せます**」を添える
- 作成フォームの開示タイミングの既定値は「30分前」と「開始までの残り時間の半分」の**短い方**
  （直前の「2時に行く人〜」が既定値のまま作れるように → 判断13）
- 細かいフォームの体裁（既定値・折りたたみ・送信前プレビュー）は実装時に決める

### お店の導出ルール

| 出すもの | 求め方 | 出さない条件 |
|---|---|---|
| また行きたい N人 | その店の評価者ごとに最新の `rating` を取り、`IS_WANT_AGAIN` の人数 | 0人なら表示しない |
| 混雑の声 | 時間帯ごとに「行った N件のうち `waited=true` は M件」 | その時間帯の6ヶ月以内・`waited` 回答ありが2件未満なら「まだ声がありません」 |
| 提案①（また行きたいが多い店） | 全店から人数最多を1件（同数は評価の新しい方） | 全店0人なら枠ごと出さない |
| 提案②（まだ評価していない店） | 自分の評価が無い店から、また行きたいの人数最多を1件 | 該当なしなら枠ごと出さない |
| 時間帯フィルタ | その時間帯の評価が付いた店だけに絞り、その時間帯の声だけを見せる | — |

すべて開くたびに導出し、保存しない。評価の書き直し・削除には自動で追従する
（過去に見た数字と食い違いうることは質問リストで許容済み）。

### お店の画面の決めごと

- 店リストの並びは**近い順**。距離は検索の中心（環境変数）からアプリ側で計算する。
  **座標を持たない店（手で足した店）は末尾に「場所未設定」としてまとめる**
- **店の詳細ページを作る**（評価の一覧＋時間帯フィルタ＋自分の評価の編集・削除の導線）。
  同じ店に複数の評価を書けるので、編集対象は詳細ページの自分の評価から選ぶ
- 店リストからは提案2枠を**出さない**（提案はルートに集約 → アプリ全体の決めごと）。
  リストは一覧と時間帯フィルタに純化する
- **「名前が出る」ことの文言**を3箇所指定する（お誘い側の「見えません」3箇所と対にする）:
  評価フォームの3段階の直下に「この評価は、あなたの名前と一緒にずっと表示されます」／
  一言の入力欄に「一言は名前と一緒に、消すまで表示されます」／一覧には添えない（名前が並ぶ姿が自明）
- 評価の送信ボタンと、お誘いの参加ボタンの**見た目を揃えない**
  （匿名の気分のまま記名の「いまいち」を押す事故を防ぐ）
- 画面のフッターに地図データの出典表示を置く（OpenStreetMap 系なら
  「© OpenStreetMap contributors」。ODbL の義務）
- 地図APIの呼び出しは**サーバー（Play）経由**にする（キーの秘匿・レート制御・
  「落ちても閲覧できる」の実現をサーバー側に寄せる）

## アプリ全体の決めごと（統合で生まれた層）

**入口・ルート画面**

- ルート（`/`）は**縦積みの1画面**: 上に開催前イベントの一覧（既存仕様のまま）、
  下に「部署のお店」見出し＋提案2枠＋「店をぜんぶ見る →」。**タブ・ボトムナビは作らない**（→ 付録A）。
  画面上の合成であってデータの結合ではない（提案は `ShopReview` の導出のみ。結合ゼロは維持）
- ルートは**ログイン必須**（一覧・お店とも元々ログイン必須なので段差は生まれない）。
  お誘いの一覧が0件のときは「**いま募集中のお誘いはありません**」＋「お誘いをつくる」を出す
- 未ログインでルートに来たらログイン・登録画面へ。そこに
  「Slack に流れた URL からも参加できます」の1行を置く。自発的にログインした人の着地先はルート
- イベント詳細ページの末尾に、**ログイン済みのときだけ**「部署のお店を見る →」のリンクを1本置く
  （Slack 経由で入った人へのお店の唯一の入口）

**PWA**

- `start_url` はルート固定（詳細ページを起動先にすると、そのイベントが終わった翌日から死ぬ）。
  **ホーム画面のアイコン下の表示名は「お誘い」**（`Osasoi` はブランド名として維持）
- manifest とアイコンを用意する。**オフライン対応はやらない**（→ 付録A。
  Service Worker はインストール可能性の要件を満たす最小限）
- PWA はインターネット公開とは別論点（公開の可否は 01 質問リストのまま未確認）。
  **PWA でもプッシュ通知は作らない**（→ 判断20）

**ログイン要否の一覧**

| 画面・API | ログイン |
|---|---|
| イベント詳細の閲覧（概要・状態・成立人数。開示後は一覧も） | **不要**（唯一の例外） |
| 「参加」を押す・取り消す・コメント | 必須 |
| ルート／イベント一覧／イベント作成 | 必須 |
| お店の全画面（リスト・詳細・評価・提案） | 必須（→ 判断26） |
| 会員登録・ログイン画面 | —（画面一覧に含める。→ 01 質問リスト） |

**API と認可**

- 規約どおり1コントローラー＝1エンドポイント。見積もりは認証4本（既存流用）＋
  お誘い6本（作成／詳細取得／参加／取り消し／コメント書き直し／一覧）＋
  お店5本（リスト・提案／検索代理／評価の投稿（店の新規作成を内包）／更新／削除）
- **未認証で叩けるのは「イベント詳細の取得」1本だけ**。その1本の中で、開示条件
  （成立×時刻）を満たさない間は参加者を返さず、状態と（成立後は）人数だけ返す
- 型は `etc/openapi/` に定義して生成する（手書きしない。リポジトリ規約）

**環境変数（一覧）**

| 設定値 | 用途 |
|---|---|
| Slack Incoming Webhook の URL | ボットの投稿（告知先チャンネルは Webhook に内包） |

- サーバーは**1台構成を前提**とする（スケジューラは Play 内の1分間隔の定期実行。

- URL の形: お誘いは `/events/{uuid}`（列挙対策 → 判断17）、お店は `/shops/{id}`
  （全画面ログイン必須のため連番で可 → 判断26）。**2規約の混在は意図的**と明記する

## 置き場所（コンテキスト）

- **会員（`User`）は `udb`（会員・認証）に置く。** `udb` も今回新設するコンテキスト
  （雛形にある同名のものは別用途のため使わない → 判断12）。認証の文脈で、参照される側に保ち、
  イベントの都合の情報は持たせない
- **イベント・参加は新しいコンテキスト `event` に置く**（→ naming.md）。どちらも `User.Id` を
  参照する側なので `udb` には置けない。参照は `event → udb` の一方向
- **店・評価は新しいコンテキスト `shop` に置く**（→ naming.md）。`shop → udb` の一方向。
  **`event` と `shop` は互いに参照しない（結合ゼロ）**——誘いの場所欄に店名を書き写すのは
  人の手で、データは繋がない（→ 判断が変わる条件）
- テーブルは `udb_user` / `event` / `event_entry` / `shop` / `shop_review`
  （エンティティ名がコンテキスト名で始まるときは重ねない規則）

# 付録A：今回やらないこと

- **日程調整**（候補日を並べてみんなで決める形は作らない。開始時刻は立案者が1つに決める → 判断11）
- **開催前のリマインド投稿**（開催が近づいても投稿は増やさない。忘れられて流れたら記録に残るだけ）
- **パスワードの再設定・登録時の確認メール**（登録した瞬間に使える。忘れたら管理者が DB で
  対応する運用。メール送信基盤は持たない）
- **立案者の記名オプション**（匿名か記名かを選べる形は作らない。まず匿名一本で始める）
- **宛先の手選び・複数チャンネル**（告知先は環境変数の1チャンネルのみ）
- **参加の承認制**（URL ＋ ログインで誰でも参加できる。漏えいリスクは社内ツールとして許容 → 判断19）
- **個人向け通知（DM）**（通知はボットのチャンネル投稿だけ。開示の確認はアプリを開いて行う → 判断20）
- **開示のお知らせ投稿**（開示は投稿しない。開示時刻は詳細ページに常時表示する）
- **退会・会員の削除機能**（`User.state` の `IS_INACTIVE` は運用上の停止用。
  停止した会員の参加・一覧の表示はそのまま残す）
- **Slack プレビューの保証**（プレビューは Slack がインターネット側から詳細ページを読める
  場合にだけ出る。非公開運用ならプレビューは出ないが、機能自体はプレビュー無しで成立する）
- **ボット投稿のランダム遅延**（投稿タイミングから立案者を推測される問題は対策しない）
- **開催の記録・実施報告・精算**（成立のまま開始時刻を過ぎたら開催とみなす）
- **イベントの編集**（内容・時刻・人数は作成後に変更できない。取り消して作り直す → 判断9）
- **告知先の設定画面**（環境変数で代替。01 の業務フロー〈お誘い〉1はデプロイ設定として実現する。
  お店の「検索の中心」〈お店〉1も同じ形）
- **「行けたら行く」などの曖昧な回答**（参加か、押さないかの2択）
- **過去イベントの一覧・振り返り・集計画面**（データは残すが、振り返る画面は作らない。
  **開催前のイベントの一覧は作る** → 画面の決めごと）
- **イベントへのコメント欄・チャット**（会話のやりとりは作らない。成立後の相談は開示された
  参加者同士が Slack で直接やる。**参加に添える一言コメント（→ 判断14）は別物**で、これは作る）

**お店について**

- **好きなもの・嫌いなものの登録と、苦手を考慮した提案**（分類マスタと管理者が生えるため。
  次の要求の候補。やる場合もアレルギー対応は保証しない）
- **「このメンバーだとここがいいかも」**（参加者単位の提案 → 判断27で見送りの理由を記録）
- **地図UI**（リストのみ。載る店は評価された数十件で、地図は実装が重い割に効かない）
- **周辺全店の取り込み・定期的な再取得**（店は評価の初回投稿で載る → 判断25）
- **訪問の証明・スタンプ・称号・制覇・「誰も行っていない店が光る」**（要求で明示的に不要）
- **常連バッジ・フォロー・「あの人」の仕組み**（一言に名前が出るだけ）
- **店の重複統合・編集画面**（別名で2行できたら許容。直すなら管理者が DB で対応）
- **評価への承認・通報・他人による削除**（消せるのは本人だけ）
- **評価の履歴・変更ログ**（上書き・削除を許す → 判断24 の代償）
- **店の集計・振り返り画面**（月間ランキング等。導出はその場の表示だけ）

**アプリ全体について**

- **タブ・ボトムナビ等のナビゲーション部品**（ルートの縦積みと、詳細からの戻り・リンクで足りる。
  部品を持つと押されなかった側が視界から消える）
- **オフライン対応**（PWA はホーム画面から起動するためのもので、オフラインでは動かさない）
- **複数サーバー構成**（1台前提。増やすときはスケジューラの二重起動対策とセットで
  → 判断が変わる条件）
- **停止会員の特別扱い**（停止中はログインできない。それ以外は何もしない——停止会員の
  有効な参加は数に含め、一覧にも名前が出て、立案したイベントもそのまま進む）
- **Slack 投稿の再試行・編集・削除**（投稿は投げっぱなし。失敗しても状態が正で、巻き戻さない。
  投稿のメッセージ ID を写す列も持たない。再試行が要る規模になったら列ごと見直す）
- **管理者によるイベントの強制取り消し・通報**（不適切な募集への対処は作らない。
  30人規模なら口頭と Slack で対処できる。100人級に広げるときに管理者アクターごと検討する）

# 付録B：判断の記録

全件が①（当初の要求の範囲で決めたこと）。番号は通し番号。

### **1. イベントの状態（`state`）を保存するか、導出するか**

**保存する（4値）。** 「流れた」「取り消された」は出来事で、参加の行からは求まらない。
「成立」も、開示後は人数が割れても成立のままにする仕様のため、**数と状態はわざと食い違う**。
却下案は全部導出——この仕様を表現できない。
**代償**：参加者数との二重管理。更新経路を4つの操作関数（作る・押す・取り消す・時刻で締める）に絞って対応する。

### **2. 開示済みを状態に含めるか**

**含めない。** 「成立している かつ 現在時刻 ≥ 開始時刻 − 開示タイミング」で求まり（→ 判断15）、
書き込むきっかけ（誰かの操作）が無い。
却下案は `IS_REVEALED` の5値目——時刻監視のバッチが要り、遅れれば「開示時刻なのに開示されない」が起きる。
**代償**：「成立していて開示済みか」の判定が `state` と時刻の2軸になる。

### **3. 立案者の参加を `EventEntry` の行として作るか**

**作る。** 「参加者＝有効な参加の集合」という1つの定義で全部が説明できる。
却下案は行を作らず「＋1」で数える——数える箇所すべてに分岐が散らばる。
立案者の印は持たない（`plannerId` との二重管理になる）。
**代償**：立案者の行の取り消しだけ特別扱いが要る（→ 判断6）。分岐は取り消しの関数1箇所に閉じる。

### **4. 参加の取り消しを、行の削除で表すか、取り消し日時の追記で表すか**

**`canceledAt` の追記。行は消さず、押し直しは新しい行。**
却下案は物理削除（取り消した事実ごと消える）と、`canceledAt` を `None` に戻す案
（可変な列を履歴の根拠にすることになる）。
残した履歴の読み手は**分析ではなく調査**（問い合わせ対応）。画面には一切出さない。
**代償**：有効な参加を探す条件に常に `canceledAt IS NULL` が付く。忘れると取り消した人を数えてしまう。

### **5. 成立後の人数割れ（開示前）を、終了にするか、募集中に戻すか**

**終了（`IS_FAILED`）。**
却下案は募集中に戻す——成立⇄流れの投稿が繰り返されてチャンネルがノイズになり、
「成立しました」の重みが消える。
**代償**：復活の余地が無い。割れた瞬間に終わる。まだやりたければ作り直す。

### **6. 立案者の取り消しの扱い（01 の判断メモから引き継ぎ）**

**開示前はイベントごと取り消し（`IS_CANCELED`）、開示後は普通の取り消しと同じ。**
専用の取り下げボタンは作らない（匿名の立案者にだけ出すボタンは、それ自体が正体の手がかりになる）。
開示後に限って通常扱いにするのは、一覧から消えた人と同時にイベントが消えると立案者だと推測できるため。
**代償**：開示後は誰もイベントを止められない。相談は開示された参加者同士に委ねる。

### **7. 告知先をモデルにするか、環境変数にするか**

**環境変数。** 全体で1件しかない設定に、モデル・テーブル・リポジトリの4点セットは重い。
**代償**：誰がいつ設定したか残らず、変更にはデプロイが要る。
複数チャンネルの要求が出たらエンティティに昇格する（→ 判断が変わる条件）。

### **8. 確定型を区分値で持つか、成立人数の解釈で表すか**

**解釈で表す（成立人数1＝確定型）。** 種別を持つと、種別と人数の組み合わせに矛盾がありうる。
**代償**：`requiredEntryCount == 1` という条件が散らばりやすい。判定はモデルのメソッドに1箇所だけ書く。

### **9. イベントの編集を許すか**

**許さない。取り消して作り直す。** 編集を許すと、成立人数を後から下げて即成立させる等、
すでに押した人の前提を裏切る変更ができる。参加の根拠が動くなら押し直しであるべき。
**代償**：タイポ1つでも作り直しになる。

### **10. 開催済みの状態を持つか**

**持たない。** `IS_CONFIRMED` のまま開始時刻を過ぎたら開催とみなす。
状態にするには実施報告（やらないと決めた）か時刻バッチ（判断2と矛盾）が要る。
**代償**：開催済みの集計は「`IS_CONFIRMED` かつ `startAt` が過去」の2条件になる。

### **11. 未来日のイベントを許すか**

**許す。** `startAt` は開催日を含む日時で、当日でも未来日でもよい
（「この日にランニングに行こう」という発注者の要求）。
却下案は候補日を並べる日程調整——成立条件が「人数」の一軸でなくなり、このアプリの軽さが死ぬ。
日付は立案者が1つに決める。
**代償**：募集から開催まで日が空くと忘れられる（リマインドは無い → 付録A）。
成立後に参加を取り消せる期間も長くなり、人数割れで流れる機会が増える。

### **12. 会員に何を持たせるか**

**最小構成（id / uuid / email / name / state）にする。**
ログイン・「誰が押したかの識別」・「開示での表示名」という今回の要求は、この5つで全部満たせる。
会員・認証（`udb`）も**この要件定義の設計対象として0から作る**。
雛形リポジトリに同名の `udb` があるが、別用途で用意されたものなので使わない。
**実装時は雛形の `User.scala` をこの設計の実装として置き換える**（結果的に形が似ていても、
それは最小構成の帰結であって流用ではない）。`Status` の code も規約どおり100刻み
（`-100` / `100`）にし、雛形の `-1` / `1` には合わせない。
本人確認は**メール＋パスワード**。パスワードのハッシュは `User` 本体に持たせず、
実装時に `udb` 内の別モデルとして足す（認証の技術詳細は実装フェーズで確定）。
却下案は部署・役職などのプロフィール列——今回の業務フローに使う場面が1つも無い。
イベント側の情報（参加履歴・立案回数）も足さない。参照を `event → udb` の一方向に保つため。
**代償**：プロフィール（アイコン・自己紹介など）の要求が来たら、そのとき列を足すことになる。

### **13. 開示タイミングを固定にするか、イベントごとに選べるようにするか**

**選べるようにする。既定は開始時刻の30分前**（発注者の要望）。
持ち方は開示時刻そのものではなく、開始時刻からの差分（`revealBefore`）。
開示時刻は `startAt − revealBefore` で求まるので保存しない（求まるものは保存しない）。
却下案は固定（入力項目が増えず軽い）——既定値を置くことで軽さは守れると判断した。
**代償**：入力項目が1つ増える。「**開示時刻は作成時点より未来**（ちょうども不可）」という
決めごとも要る——作成と同時に開示される抜け道（確定型で顕在化する）を塞ぐため。
作成直後に開示が来る極端な設定は依然作れるが、開示時刻はページに常時表示されるので
隠れた挙動にはならない。
また**既定30分を固定にすると、開始まで30分を切ったゆる募（「2時に行く人〜」を13:50に立てる）が
一切作れない**。既定値は「30分前」と「開始までの残り時間の半分」の短い方に自動調整する
（→ 画面の決めごと）。

### **14. 参加にコメントを添えられるようにするか・書き直せるようにするか**

**添えられるようにする**（`EventEntry.comment`。任意・自由記述。「遅れて行きます」など）。
そして**本人は開示より前ならいつでも書き直せる**（参加はそのまま）。
開示後と取り消し済みの行は編集不可——誰でも見える一覧の文面が後から変わると、
見た人と見えている文面が食い違うため。
**開示までは誰にも見せない**——文面の癖や内容で本人が特定され、
「成立まで誰が押したか見えない」ルールが実質破れるため。参加者の一覧と同じ扱いにする。
書き直しは、当初「編集機能を作らず、取り消して押し直す」としていたが、監査で副作用が
見つかり改めた——コメントを直すための取り消しが人数割れを起こして判断5により
イベントが流れ、**立案者に至っては判断6によりイベントごと取り消される**
（＝立案者はコメントを一度も直せない）。編集を許す方が安全。
却下案はイベントへのコメント欄（チャット）——会話が始まると匿名の維持が難しく、
Slack と役割が被る（→ 付録A）。
**代償**：`comment` が可変列になる。履歴の根拠には使わない（表示専用。調査で見るのも
最終値だけ）。一言だけなので会話はできず、返事が要る事情は開示後に Slack で直接やる。

### **15. 開示の条件と、開示後に誰が見られるか**

開示まわりを見直した回の判断を、5つまとめて記録する。

- **開示は「成立している」が前提。** 時刻だけで開示すると、未成立のまま開示時刻を過ぎた
  イベントで押した人の名前が露出し、そのまま流れたら「集まらなくても誰も傷つかない」が破れる。
  開示時刻の後に成立したら、成立と同時に開示する（開示済みは導出なので自動で成り立つ）
- **開示後の一覧は URL を開いた人なら誰でも見られる**（当初は参加者限定だった）。
  開示後はもう記名の世界で隠す秘密が無く、見えることが駆け込み参加を誘う。
  ただし Slack には名前を載せない（転送できて永久に残る。アプリ内なら取り消しが即反映）
- **成立後は人数だけ誰でも見える**（名前は開示まで伏せる）。「結構集まってるな」という
  判断材料になる。募集中に人数を隠すルールは成立前だけの話なので矛盾しない
- ボットの投稿は**募集1本＋状態変化ごとに1本**（通常2本。確定型は募集が成立を兼ねるので
  通常1本。成立の後に流れた・取り消された場合だけ3本）。開示のお知らせ投稿はせず、
  詳細ページに開示時刻を常時表示する（却下案：開示時の追加投稿——チャンネルのノイズが増える）
- 開示の一覧には**最低表示人数（2人）と並び順（表示名順・文字コード順）**の条件がある（詳細は判断18）

**代償**：開示済みの判定が「`state` × 時刻」の2条件になる（判断2の式に成立が加わる）。
開示の瞬間を知らせる手段がアプリに無いので、開示時刻を自分で見て開きに来ることになる。
なお**開示の条件の正はこの判断15**。他の箇所の記述はここを参照する。

### **16. 同時操作をどう守るか**

**参加の追加・取り消しと状態遷移は、イベント行をロックして1トランザクションで行う（悲観ロック）。**
守るもの: ①同じ人の二重押しで有効な参加が2行できない ②2人が同時に成立ラインを踏んでも
成立の遷移と投稿は1回だけ ③「押す」と「立案者の取り消し」が同時でも直列化される。
却下案は DB の一意制約（「`canceledAt` が `None` の行は1つ」は条件付き一意で、
MySQL では単純なユニークインデックスで表現できない）と、楽観ロック（列が増え、
失敗時のリトライ設計が要る）。
**代償**：同じイベントへの操作が直列化される（30人規模では問題にならない）。
型でも制約でも守れないため、テストで守る。

### **17. イベントの URL に何を使うか**

**公開用 UUID（`Event.uuid`）を使う。** 連番の `id` を URL に使うと、数字を変えるだけで
全イベントを列挙でき、「URL が届く範囲を対象者の境界にする」前提が崩れるため。
`User.uuid` と同じ形で一貫する。
却下案は連番のまま（社内ツールとして許容する案）——URL の推測は「漏えい」と違って
手元だけで完結し、起きても気づけないため採らない。
**代償**：列が1つ増える。

### **18. 開示の一覧に最低表示人数を設けるか**

**設ける。有効な参加が2人以上のときだけ一覧（名前・コメント）を表示**し、
1人の間は「参加者1人（名前は2人から表示）」とする。
理由: 確定型（成立人数1）で誰も乗らないまま開示されると、一覧に並ぶのは立案者1人
＝**永久匿名が破れる**。成立人数2で開示後に1人が取り消した場合も同じ。
却下案は、確定型に限り記名と割り切る案（記名オプションはやらないと決めた方針と衝突）。
並び順は**表示名順（文字コード順）**にする——押した順だと、立案者の行は作成と同時にできるため
**一覧の先頭が必ず立案者**になり、順序から特定できてしまう。当初は「五十音順」としたが、
表示名に読み仮名が無く漢字は五十音に並ばないため、実装できる形に改めた
（目的は「押した順にしない」ことで、コード順で足りる。読み仮名の列は増やさない）。
**この閾値の限界も明記する**: 2人以上ルールが効くのは**第三者**だけで、参加者本人には
効かない。参加者がちょうど2人のとき、自分は立案者でないと知っている本人には、
もう1人が立案者だと確定する（3人でも2分の1に絞られる）。これは現実として防げない
（2人で行けば誘い主は分かる）。「立案者は永久に表示しない」は**画面に表示しない**という
約束であり、推測まで防ぐ約束ではない。画面にこの注意書きは出さない（ハードルを上げるため）。
**代償**：開示後の表示が人数で変わる分岐が1つ増える。2人イベントで開示後に1人が
取り消すと、一覧は人数表示に戻る（すでに見た人の記憶までは消せない）。
そのとき**残った本人には自分の参加とコメントを見せ続ける**（自分の状態を確認できない
不安の方が大きい）。

### **19. 参加者を絞る仕組み（グループ・メンバー登録・承認）を持たない**（01 の判断メモから引き継ぎ）

**持たない。URL を開いてログインした人なら誰でも参加できる。** 対象者の境界は
Slack チャンネル（URL が届く範囲）に委ねる。
当初はアプリ側でグループに人を登録する案だったが、Slack チャンネルにいる人と
ズレたとき「募集は見えるのに押せない人」が生まれる。同期 API は重く、
ネイティブアプリ＋プッシュ通知案は「ダウンロードは面倒」という要求と衝突するため却下。
**代償**：URL が漏れると部外者もログインすれば参加できる。社内ツールとして許容し、
承認制は次の要求の候補（→ 付録A）。

### **20. 通知を個人宛てにするか、チャンネルに流すか**（01 の判断メモから引き継ぎ）

**ボットのチャンネル投稿に一本化する。名前と集まっている人数は出さない。**
守るべき秘密は「誰が」であって「成立した事実」ではない。成立が見えることは
むしろ駆け込み参加を誘う。個人宛て通知（DM）は実装が重く、作らない（→ 付録A）。
**代償**：押していない人にも成立・流れたが見える（チャンネルのノイズ）。
30人規模なら1日数件で許容範囲と判断。ノイズが問題になったらスレッド返信化を検討
（→ 判断が変わる条件）。
**PWA 化（→ 01 質問リスト）の後もこの判断は維持する。** PWA はプッシュ通知が
技術的に可能になるが、「通知はチャンネル投稿だけ」という整理は通知手段によらず有効。

### **21. 立案者を成立人数に数えるか**（01 の判断メモから引き継ぎ）

**数える。** 「3人集まったら行く」＝立案者を含めて3人。
立案者は当然行く人であり、「3人いれば行ける」という感覚は自分を含めた頭数のはず。
却下案は「立案者＋N人」方式——参加者数を数えるすべての箇所に「＋1」の分岐が散らばる
（判断3と同じ理由）。
**代償**：確定型（成立人数1）が「立案者だけで成立」を意味することになり、
1という値の解釈（判断8）とセットで理解する必要がある。

### **22. 禁止語「店」を用語表から外すか（お店の文脈の登場）**

**外す。** 当初「場所」の言い換えとして「店」を禁止したのは、このドメインの `place`
（自由記述の集合場所）を「店」と呼ばせないため——場所は店とは限らない（会議室・集合地点）。
その後、お店の機能（shop コンテキスト）が「店」を主役の業務語として持つことになり、
概念そのものの禁止は維持できなくなった。禁止の射程を「このドメインの『場所』の言い換えとしては
使わない」に絞り直す。
**代償**：「場所」と「店」が近い語として共存し、どちらを使うかの判断が都度要る。
**「言い換え候補を禁止語登録すると、新しい正式語と衝突して跳ね返ることがある」**
という規約運用の代償が現実化した事例として記録する。

### **23. お店の集計・提案を保存するか、導出するか**

**すべて導出。** また行きたいの人数・混雑の声・提案2枠・「まだ評価していない」は、
評価の台帳から開くたびに求める。書き直し・削除に自動で追従する。
**代償**：店リストの表示のたびに集計クエリが走る。30人×数十店の規模では問題にならない。

### **24. 評価を上書き・削除できる可変の記録にするか、追記のみの台帳にするか**

**上書き・削除を許す**（お誘い側で徹底した「追記のみ」原則からの**意図的な逸脱**）。
要求が「本人はいつでも書き直せる・消せる」であり、消えた評価に業務価値が無い
（参加の取り消しと違い、気まずさの保護も履歴の要求も無い）。
却下案は `canceledAt` 式の追記——守るものが無いのに複雑さだけ増える。
**代償**：「この店の評価が消えた経緯」は調査できない。集計は現在有効な評価だけから
導出されるため、過去に見た数字と食い違いうる（質問リストで許容済み）。

### **25. 店マスタをどう作るか**

**最初の評価と同時に生まれる**（検索して選ぶ、または名前と大まかな場所で手で足す）。
周辺全店の取り込みは、①誰も知らない店が視界を埋める ②地図APIに無い店が書けない
③再取得で評価が孤児になる、の3つの害があるため却下。
`externalId` は `Option`——手で足した店は地図API側の ID を持たない。
**代償**：同じ店が別名で2行できうる（統合機能は作らず許容）。「まだ誰も行っていない店を探す」
用途は満たさない。最後の評価が消えた店の行が残る（画面に出さないだけ）。

### **26. 店に公開用 UUID を持たせるか**

**持たせない。** `Event.uuid` は「未ログインでも詳細が見える」ための列挙対策だった。
店の画面は**すべてログイン必須**で、ログインした人にはリストで全店見えるのが仕様。
隠すものが無いので、列が1つ減る方を取る。
**代償**：将来「店の詳細を未ログインに見せたい」となったら、そのとき列を足す。

### **27. 提案を「参加者単位・開示後」にしなかった**

**本人向け・常時表示。** 理由は3つ——①開示（既定30分前、直前ゆる募なら5分前）では店を
決めるには遅く、場所欄は編集不可で反映先が無い ②「参加者の誰も評価していない店」は
記名で常時表示される評価と突き合わせると参加者の否定情報として逆算できる（判断18 が塞いだ穴を
開け直す）③お店（おまけ）がお誘い（主機能）に依存を作る。
**代償**：要求文の「このメンバーだと」には応えない。判断が変わる条件へ。

### **28. 評価を3段階・人数集計にした**

記名の身内では星5段階は4〜5に潰れて平均が意味を失う。3段階（また行きたい／ふつう／いまいち）
なら中間が逃げ場になる。「また行きたい」は人数で数え、1人の連投が部署の総意に見えるのを防ぐ。
同じ人の複数評価は**最新の `rating`** を使う（昔いまいち→最近また行きたい、を反映する）。
**代償**：平均点での並べ替えはできない。混雑（件数）と評価（人数）で集計単位が分かれる。

### **29. 時間帯を区分値にした**

時刻の自由入力ではなく4区分（〜11時台／12時台／13時台／14時以降）。
「空いていそう」の集計単位＝入力の単位にするため。刻みを細かくすると1マスあたりの件数が
枯れて、2件未満ルールにより何も表示されなくなる。
**代償**：境界の時刻は区分に丸められる。14時以降が1括りになる（14時ランチ派の要求には足りる）。

### **30. お誘いとお店を、1つのドメイン（1ディレクトリ・1つの4点セット）に統合した**

**統合する。** ドメインの粒度を「Osasoi アプリ全体」に取り、`docs/domain/osasoi/` の
1つの4点セットで udb / event / shop の3コンテキストを扱う
（stampcard が common と sales を1ディレクトリで扱う前例に倣う）。
きっかけは発注者の「レビューは一つの要件定義で行いたい」。
お店の要求は実際には対話の後半で出たが、提出前のドラフト統合なので規約の①②③
（**提出後**に来る要求の書式）は使わず、「最初から入っていた」形に語り直した（経緯は 01 判断メモ）。
タイトルは規約どおり**最初の要求の業務語** `<お誘い>` のまま——お店は要求文が
「誘いがメインで、店はおまけ」と序列を明言しており、包含にねじれは無い。
却下案は別ディレクトリ2セットの維持——レビューが2重になり、アプリ全体の決めごと
（入口・PWA・ログイン一覧）の置き場が無い。
**代償**：ファイルが長くなる（03 は800行級）。節の境界を跨いだ混入事故が起きやすくなる
（実際に統合直後の監査で3行の混入を検出・修正した）。お誘いとお店で「例外・ルール」等に
ラベルを付けて区切る運用で抑える。
