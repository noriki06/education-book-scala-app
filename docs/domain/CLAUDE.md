# docs/domain — ドメイン設計ドキュメントの書き方

1ドメイン1ディレクトリ。ディレクトリ名は英小文字（例：`stampcard`、`cookingmnagement`）。
**`stampcard/` が現時点で一番作り込まれた見本。**新しいドメインはこの構成と書き方に合わせる。

## 4点セット

| ファイル | 何を書くか | 提出物か |
|---|---|---|
| `01_requirements.md` | 受け取った要求（原文）、質問リスト、業務フロー、例外・ルール | 提出する |
| `02_analysis.md` | 名詞と動詞の洗い出し、ふるい分け、ユビキタス言語、コンテキストの判断 | **メモ。提出しない** |
| `03_design.md` | 用語表、ER図、EntityModel（Scala）、決めごと、判定ルール、付録A/B | 提出する |
| `naming.md` | 命名の評価軸・候補・却下理由 | 提出する |
| `img/er-*.svg` | ER図。手書きの SVG（Mermaid ではない） | — |

タイトルは `# <ドメイン名> — 要件定義` の形。**`<>` の中は最初の要求で使われていた業務語**を入れる
（あとから命名で決めた語ではなく、お客さんが言った語。例：リワードカードではなく `<スタンプ>`）。

## 追加の要求が来たときの書き方

要求が追加されたら、既存の記述を上書きせず **①②③に節を分けて並べる**。

| 節 | 中身 |
|---|---|
| ① 当初の要求からある分 | 追加の要求では動いていないもの |
| ② 追加の要求で変わった分 | 当初にもあったが内容や条件が変わったもの。**「（当初は〜だった）」を添える** |
| ③ 追加の要求で加わった分 | 当初には無かったもの |

**必ず ① → ② → ③ の順**に並べる。行末に印を付ける方式は使わない（読みにくい）。
唯一の例外は `01_requirements.md` の業務フローで、時系列がフローそのものなので並べ替えず行末に
〔追加要求〕〔追加要求で変更〕を付ける。

お客さんの発言をそのまま引用している箇所（「受け取った要求」「追加の要求」）は、
**用語を統一する一括置換の対象から外す。**言葉を直してはいけない。

## 用語の扱い

`03_design.md` の用語表が正。**「言い換えない」欄に入れた語は本文で使わない。**
新しい語を導入したら、**そのとき言い換え候補も禁止語として登録する**（あとで全面修正になる）。

要求文に出てこない語（業務が何と呼んでいるか未確認の語）は、業務語として扱わない。
仮の呼称であることを質問リストに残す。

## 付録の使い分け

- **付録A：今回やらないこと。** スコープ外を明記する。「将来やるかも」ではなく「今回やらない」と書く
- **付録B：判断の記録。** 判断ごとに「採用した案」「却下した案」「却下した理由」「代償」を書く。
  **代償を書かない判断は、書いたことにならない。**
  `#### 見出し` 単位で、①②③のグループに分けて並べる

## ER図（SVG）

`viewBox` を持つ手書きの SVG。box の高さと y 座標を直に書いているので、
**行を増やすときは rect の height と外枠のコンテキスト枠も一緒に広げる**。
`03_design.md` 側の代替テキスト（`![...]`）にも、図に載っている属性と多重度をすべて書く。
図を直したら代替テキストも直す。
