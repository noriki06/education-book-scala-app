# <お店> — 詳細要件定義

呼称は日本語も英語もそろえる（→ 02_analysis.md / naming.md）。
追加の要求はまだ無いため、全体が①（当初の要求からある分）にあたる。

**この設計の要点は3つ。**

1. 新設は `Shop`（店）と `ShopReview`（評価）の2モデルだけ。参照は `shop → udb` の一方向で、
   `event`（お誘い）とは互いに参照しない（結合ゼロ）
2. 集計と提案（また行きたいの人数・混雑・提案2枠・まだ評価していない）は**すべて保存せず導出**
3. 店は「最初の評価」と同時に生まれる。評価の無い店は存在しない

## 用語 — 全体の用語集に追加する呼称

| 呼称（これで統一する） | 何を指すか | 言い換えない |
|---|---|---|
| 店 | 評価の対象。最初の評価と同時にマスタに載る | 飲食店、レストラン、ストア（「お店」はドメインの題名としてだけ使う） |
| 評価 | 店への1回の投稿。3段階＋任意の時間帯・並んだか・一言 | レビュー、口コミ、点数、評点 |
| 3段階 | 評価の値。**また行きたい／ふつう／いまいち** | 星、スコア |
| 時間帯 | 行った時間の区分。〜11時台／12時台／13時台／14時以降 | 時刻、タイムスロット |
| 一言 | 評価に添える記名の短い感想。**お誘いの「コメント」とは別概念**（常時公開） | コメント、メッセージ、感想 |
| 混雑の声 | 「その時間帯に行った N人のうち、並んだのは M人」という表示。断定しない | 空き情報、混雑度 |
| 提案 | 店リストの上に出す2枠（また行きたいが多い店・自分がまだ評価していない店）。本人向け | おすすめ、レコメンド |

## EntityModel

2つとも今回作る。`User` は invite 側で設計済みのものを参照するだけ（1列も足さない）。
英語名は `naming.md` で確定済み（`Shop` / `ShopReview`）。

### <店（Shop）>

評価の対象。**最初の評価が書かれたときに生まれる**（単独で作る画面は無い）。

```scala
case class Shop(
  id:         Option[Id],              // 管理 ID（永続化前は None）
  externalId: Option[String] = None,   // 地図API側の ID。手で足した店は None（→ 判断3）
  name:       String,                  // 店名（50字まで）
  latitude:   Option[BigDecimal],      // 緯度。手で足した店は None のことがある
  longitude:  Option[BigDecimal],      // 経度。同上
  address:    Option[String] = None,   // 大まかな場所（自由記述・100字。手で足した店の目印用）
  updatedAt:  LocalDateTime = Now,     // データ更新日
  createdAt:  LocalDateTime = Now      // データ作成日 ＝ 最初の評価が書かれた日時
) extends EntityModel[Id]

object Shop:

  type   Id = Id.Repr
  object Id extends Entity.Id[Long]
```

### <評価（ShopReview）>

「誰が・どの店を・どう言ったか」の1件。**本人はいつでも書き直せる・消せる**（→ 判断2）。

```scala
case class ShopReview(
  id:        Option[Id],               // 管理 ID（永続化前は None）
  shopId:    Shop.Id,                  // どの店への評価か（Shop と *:1）
  userId:    User.Id,                  // 誰の評価か（User と *:1）。名前は常時表示される
  rating:    Rating,                   // 3段階（これだけで送信できる）
  timeSlot:  Option[TimeSlot] = None,  // 行った時間帯。昔の店は覚えていないので任意
  waited:    Option[Boolean]  = None,  // 並んだか。未回答を許す
  remark:    Option[String]   = None,  // 一言（100字・改行なし）。任意
  updatedAt: LocalDateTime = Now,      // データ更新日
  createdAt: LocalDateTime = Now       // データ作成日 ＝ 投稿日時（混雑の集計の6ヶ月判定に使う）
) extends EntityModel[Id]

object ShopReview:

  type   Id = Id.Repr
  object Id extends Entity.Id[Long]

  /** 3段階 */
  enum Rating(val code: Short) extends EnumStatus[Short]:
    case IS_DISAPPOINTED extends Rating(code = -1) // いまいち
    case IS_NEUTRAL      extends Rating(code =  1) // ふつう
    case IS_WANT_AGAIN   extends Rating(code =  2) // また行きたい

  /** 時間帯 */
  enum TimeSlot(val code: Short) extends EnumStatus[Short]:
    case IS_UNTIL_11  extends TimeSlot(code = 1) // 〜11時台
    case IS_AROUND_12 extends TimeSlot(code = 2) // 12時台
    case IS_AROUND_13 extends TimeSlot(code = 3) // 13時台
    case IS_FROM_14   extends TimeSlot(code = 4) // 14時以降
```

**ここで型が語っていること**（理由は付録Bの番号を参照）

- `ShopReview` は状態（Status）を持たない。台帳ではなく**上書き・削除を許す可変の記録**（→ 判断2。
  お誘いの「追記のみ」原則からの意図的な逸脱）
- 集計・提案はどこにも保存しない。すべて `ShopReview` から導出（→ 判断1）
- `Shop` に公開用 UUID は持たない。店の画面はすべてログイン必須で、隠すものがない（→ 判断4）
- 好き嫌い・分類・カテゴリのモデルは無い（今回やらない → 付録A）

**型では守れない決めごと**

- `Shop` は最初の評価と**同じトランザクションで**作る。評価0件の `Shop` を作る経路は無い。
  最後の評価が消えても `Shop` は残す（評価0件の店は画面に出さないだけ）
- `rating` の code はマイナス＝否定的、プラス＝肯定的（状態ではないので100刻みは適用しない）
- 「また行きたい」の集計は**人数**（同じ人の複数評価は1人と数える。その人の最新の `rating` を使う）。
  混雑の集計は**件数**で、`createdAt` が6ヶ月以内のものだけ・その時間帯が2件以上のときだけ表示する
- 提案の2枠: 「また行きたいの人数が最多の店」（同数なら評価の新しい方）と
  「自分の評価が1件も無い店のうち、また行きたいの人数が最多の店」。該当が無い枠は出さない
- 入力の上限: 店名50字・場所メモ100字・一言100字（改行なし）
- 時刻は JST 固定（お誘いと同じ）。スケジューラ・バッチはこのドメインには無い

**保存されるデータの例**（会員 A・B・C）

`Shop`

| id | externalId | name | latitude/longitude | address | どうやって載ったか |
|---|---|---|---|---|---|
| 31 | osm:9012 | 大三元 | あり | `None` | A が検索して選び、最初の評価を書いた |
| 32 | `None` | まるまる食堂 | `None` | 「郵便局の裏」 | 検索で見つからず、B が手で足した |

`ShopReview`

| id | shopId | userId | rating | timeSlot | waited | remark |
|---|---|---|---|---|---|---|
| 201 | 31 | A | IS_WANT_AGAIN | IS_AROUND_12 | true | 回鍋肉がやばい。12時台は並ぶ |
| 202 | 31 | B | IS_NEUTRAL | `None` | `None` | `None` |
| 203 | 31 | A | IS_WANT_AGAIN | IS_FROM_14 | false | 14時なら並ばない |
| 204 | 32 | B | IS_WANT_AGAIN | IS_AROUND_13 | false | `None` |

- 大三元の「また行きたい」は**2人**（A は2件書いているが1人と数える）
- 大三元の14時以降の混雑の声は1件なので**まだ表示しない**（2件未満）。12時台も1件で同様
- B の評価202は3段階だけの最小投稿（時間帯・並び・一言すべて未回答）——これが許される形

## 導出のルール（判定ルールに相当）

| 出すもの | 求め方 | 出さない条件 |
|---|---|---|
| また行きたい N人 | その店の評価者ごとに最新の `rating` を取り、`IS_WANT_AGAIN` の人数 | 0人なら表示しない |
| 混雑の声 | 時間帯ごとに「行った N人（件数）のうち `waited=true` は M件」 | その時間帯の6ヶ月以内・`waited` 回答ありが2件未満なら「まだ声がありません」 |
| 提案①（また行きたいが多い店） | 全店から人数最多を1件（同数は評価の新しい方） | 全店0人なら枠ごと出さない |
| 提案②（まだ評価していない店） | 自分の評価が無い店から、また行きたい人数最多を1件 | 該当なしなら枠ごと出さない |
| 時間帯フィルタ | その時間帯の評価が付いた店だけに絞り、その時間帯の声だけを見せる | — |

すべて開くたびに導出し、保存しない。評価の書き直し・削除には自動で追従する
（過去に見た数字と食い違いうることは 01 で許容済み）。

## 置き場所（コンテキスト）

- **店・評価は新しいコンテキスト（記号は仮に `shop`。→ naming.md）に置く。**
  どちらも `User.Id` を参照する側なので `udb` には置けない。参照は `shop → udb` の一方向
- **`event`（お誘い）とは互いに参照しない（結合ゼロ）。**
  誘いの場所欄に店名を書き写すのは人の手で、データは繋がない（→ invite 判断が変わる条件）
- テーブルは `shop` / `shop_review`（エンティティ名がコンテキスト名で始まるときは重ねない規則）

# 付録A：今回やらないこと

- **好きなもの・嫌いなものの登録と、苦手を考慮した提案**（分類マスタと管理者が生えるため。
  第2弾候補。やる場合もアレルギー対応は保証しない）
- **「このメンバーだとここがいいかも」**（参加者単位の提案。開示後では遅い・否定情報が逆算できる・
  お誘いへの依存が生まれる、の3点で見送り → 判断5）
- **地図UI**（リストのみ。載る店は評価された数十件で、地図は実装が重い割に効かない）
- **周辺全店の取り込み・定期的な再取得**（店は評価の初回投稿で載る → 判断3）
- **訪問の証明・スタンプ・称号・制覇・「誰も行っていない店が光る」**（要求で明示的に不要）
- **常連バッジ・フォロー・「あの人」の仕組み**（一言に名前が出るだけ）
- **店の重複統合・編集画面**（別名で2行できたら許容。直すなら管理者が DB で対応）
- **承認・通報・他人の評価の削除**（消せるのは本人だけ。30人規模なら口頭と Slack で対処）
- **評価の履歴・変更ログ**（上書き・削除を許す → 判断2 の代償）
- **集計・振り返りの画面**（月間ランキング等。導出はその場の表示だけ）

# 付録B：判断の記録

全件が①（当初の要求の範囲で決めたこと）。

### **1. 集計・提案を保存するか、導出するか**

**すべて導出。** また行きたいの人数・混雑の声・提案2枠・「まだ評価していない」は、
評価の台帳から開くたびに求める。書き直し・削除に自動で追従する。
**代償**：店リストの表示のたびに集計クエリが走る。30人×数十店の規模では問題にならない。

### **2. 評価を上書き・削除できる可変の記録にするか、追記のみの台帳にするか**

**上書き・削除を許す**（お誘いの「追記のみ」原則からの**意図的な逸脱**）。
要求が「本人はいつでも書き直せる・消せる」であり、消えた評価に業務価値が無い
（お誘いの取り消しと違い、気まずさの保護も履歴の要求も無い）。
却下案は `canceledAt` 式の追記——守るものが無いのに複雑さだけ増える。
**代償**：「この店の評価が消えた経緯」は調査できない。集計は現在有効な評価だけから
導出されるため、過去に見た数字と食い違いうる（01 で許容済み）。

### **3. 店マスタをどう作るか**

**最初の評価と同時に生まれる**（検索して選ぶ、または名前と大まかな場所で手で足す）。
周辺全店の取り込みは、①誰も知らない店が視界を埋める ②地図APIに無い店が書けない
③再取得で評価が孤児になる、の3つの害があるため却下（→ 01 判断メモ）。
`externalId` は `Option`——手で足した店は地図API側の ID を持たない。
**代償**：同じ店が別名で2行できうる（統合機能は作らず許容）。「まだ誰も行っていない店を探す」
用途は満たさない。最後の評価が消えた店の行が残る（画面に出さないだけ）。

### **4. 店に公開用 UUID を持たせるか**

**持たせない。** お誘いの `Event.uuid` は「未ログインでも詳細が見える」ための列挙対策だった。
店の画面は**すべてログイン必須**で、ログインした人にはリストで全店見えるのが仕様。
隠すものが無いので、列が1つ減る方を取る。
**代償**：将来「店の詳細を未ログインに見せたい」となったら、そのとき列を足す。

### **5. 提案を「参加者単位・開示後」にしなかった**（01 判断メモから引き継ぎ）

**本人向け・常時表示。** 理由は3つ——①開示（既定30分前、直前ゆる募なら5分前）では店を
決めるには遅く、場所欄は編集不可で反映先が無い ②「参加者の誰も評価していない店」は
記名公開の評価と突き合わせると参加者の否定情報として逆算できる（invite 判断18 が塞いだ穴を
開け直す）③おまけが主機能（お誘い）に依存を作る。
**代償**：要求文の「このメンバーだと」には応えない。判断が変わる条件へ。

### **6. 3段階・人数集計にした**（01 判断メモから引き継ぎ）

記名の身内では星5段階は4〜5に潰れて平均が意味を失う。3段階（また行きたい／ふつう／いまいち）
なら中間が逃げ場になる。「また行きたい」は人数で数え、1人の連投が部署の総意に見えるのを防ぐ。
同じ人の複数評価は**最新の `rating`** を使う（昔いまいち→最近また行きたい、を反映する）。
**代償**：平均点での並べ替えはできない。混雑（件数）と評価（人数）で集計単位が分かれる。

### **7. 時間帯を区分値にした**

時刻の自由入力ではなく4区分（〜11時台／12時台／13時台／14時以降）。
「空いていそう」の集計単位＝入力の単位にするため。刻みを細かくすると1マスあたりの件数が
枯れて、2件未満ルールにより何も表示されなくなる。
**代償**：「13:45 は？」のような境界は区分に丸められる。14時以降が1括りになる
（14時ランチ派の要求には足りる）。

## 判断が変わる条件（まとめ）

| 条件 | どうなるか | 関連する判断 |
|---|---|---|
| 苦手を考慮した提案の要望が続く | 店の分類（地図APIのカテゴリを写すか、固定マスタか）と、苦手の登録を設計する。管理者が生えることも込みで | 付録A・判断5 |
| 「このメンバーだと」をやりたくなる | 開示のタイミング・否定情報の漏えい・依存の向きの3点を再設計してから。判断5 の理由が全部生きている | 判断5 |
| 店の重複・誤登録が実際に困る量になる | 統合・編集の管理機能と管理者アクターを検討する | 判断3 |
| 評価の件数が増えて集計が重くなる | 導出をやめて集計の保存（キャッシュ）を検討する。書き直し追従の利点が消える代償と引き換え | 判断1 |
| 店の詳細を未ログインに見せたい要望が出る | `Shop` に公開用 UUID を足し、可視性のルールを設計し直す | 判断4 |
| 地図UIの要望が出る | リストに加えて地図を検討（PWA での地図実装コストと引き換え） | 付録A |
