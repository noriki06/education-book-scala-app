# <お店> — 思考過程（メモ・提出しない）

構造は店／評価の2階層。命名の評価は `naming.md` に切り出す。ここでは仕分けと属性の判断だけ。

## 名詞と動詞

**名詞**：店、店マスタ、評価、3段階（また行きたい・ふつう・いまいち）、時間帯、並んだか、一言、
名前（書いた人の）、相手側 ID、検索の中心、提案（また行きたいが多い店・まだ評価していない店）、
混雑（〜人のうち並んだのは〜人）、リスト、会員、地図API

**動詞**：（店を）検索する、（店を）足す・写す、（評価を）書く・書き直す・消す、
（時間帯で）絞る、（人数・件数を）数える、（提案を）出す、眺める

| 種類 | 対象 | 動詞 | 行き先 |
|---|---|---|---|
| 追加 | 店 | 検索して選ぶ／手で足す | **最初の評価が書かれたとき**に1行足す（それ以外で店は増えない） |
| 追加 | 評価 | 書く | レコードを1行足す |
| 更新 | 評価 | 書き直す | 本人がいつでも。行を書き換える（→ 03 の論点: お誘いの「追記のみ」と違う扱いでよいか） |
| 削除 | 評価 | 消す | 本人がいつでも。**物理削除を許すか**は 03 の論点 |
| 値を返す | — | 数える／提案を出す／絞る | モデルのメソッド・クエリ（また行きたいの人数、時間帯の混雑、提案2枠）。保存しない |

表に入らないもの：検索する（地図APIの機能）、ログインする（udb）、眺める（画面）。

## ふるい分け

| 名詞 | 仕分け（エンティティ／値オブジェクト／属性／対象外／設計済み） | 理由 |
|---|---|---|
| 会員 | **設計済み**（`udb` の `User`。→ invite） | 評価の主体。変更しない |
| 店 | **エンティティ（新設）** | ID で区別。評価がぶら下がる。評価の初回投稿で生まれるライフサイクル |
| 評価 | **エンティティ（新設）** | 「誰が・どの店を・どう言ったか」の1件ずつの記録 |
| 3段階 | 属性（区分値） | 評価が持つ。また行きたい／ふつう／いまいち |
| 時間帯 | 属性（区分値・任意） | 評価が持つ。〜11時台／12時台／13時台／14時以降。昔の店は覚えていないので任意 |
| 並んだか | 属性（任意） | 評価が持つ。並んだ／並ばなかった／未回答 |
| 一言 | 属性（任意・100字） | 評価が持つ。お誘いの「コメント」とは別概念なので別の語 |
| 相手側 ID | 属性（任意） | 店が持つ。地図API側の ID。手で足した店は持たない |
| 店マスタ | ＝店エンティティの集合の呼び名 | 独立した概念ではない |
| 検索の中心 | 対象外（環境変数） | お誘いの告知先と同じ形 |
| 地図API | 対象外（外部サービス） | 検索時の供給元。写した属性だけが残る |
| 提案・混雑・また行きたい人数・まだ評価していない | **対象外（＝計算結果）** | すべて評価の台帳から導出。保存しない |
| 名前・リスト | 既存属性（`User.name`）・表現 | — |

「対象外」5件。新設は**店・評価の2つだけ**。

## 用語のブレ

- 「一言」⇔ invite の「コメント」: 別概念（常時記名公開 vs 開示まで秘匿）なので語を分けた（01 で確定済み）。
  英語名も `comment` を使い回すと日本語2語⇔英語1語で1対1が壊れるため、別の語にする（→ naming.md）。
- 「評価」の言い換え候補（レビュー・口コミ・点数・評点）は 03 の用語表で禁止語に登録する。

## 名前を並べて確認する

コンテキスト記号を仮に `shop` とする（naming.md で確定）。
エンティティ名がコンテキスト名で始まるときは重ねない規則により、テーブルは `shop` / `shop_review`。

```
User        ← 設計済み（udb）
Event       ← 設計済み（event）
EventEntry  ← 設計済み（event）
Shop        ← 新設（shop）
ShopReview  ← 新設（shop）
```

`Shop`(4) < `ShopReview`(10) で深いほど長い向き。名前順で隣り合う。
※ 注意: `docs/domain/stampcard/`（別の研修課題）の設計にも `Shop` があるが、あちらは
ハンバーガーショップの店舗で、このアプリ（Osasoi）には実装されない。衝突しない（→ naming.md）。

## コンテキストの判断

| 日常的に書き換える人 | 何を書き換えるか | 更新の頻度 | 見る画面 |
|---|---|---|---|
| 会員 | 評価を書く・直す・消す（店は初回評価で自動生成） | 昼どき | 店リスト・評価フォーム |
| 検索の中心を決める人 | 検索の中心（環境変数） | ほぼ一度きり | —（デプロイ設定） |
| 地図API（外部） | —（検索候補を返すだけ。こちらのデータは書かない） | 検索のたび | — |

**判断：新しいコンテキストを1つ作る（記号は仮に `shop`）。**

- 店と評価は同じ人が同じ画面・同じライフサイクルで触る。分けない
- `udb` には置けない（`User.Id` を参照する側）。`event` にも置けない（誘いとは変わる理由が違い、
  結合ゼロと決めた）。参照は `shop → udb` の一方向のみ

## 判断に困ったところ（このページの分）

#### 評価の書き直し・削除を、お誘いの「追記のみ」と同じ扱いにするか

- **困った点**: お誘いは「可変な列を履歴の根拠にしない」を徹底し、取り消しも追記（`canceledAt`）だった。
  評価も同じにすべきか。
- **仮の選択**: 評価は**上書き・物理削除を許す**。要求が「本人はいつでも書き直せる・消せる」で、
  消えた評価に業務価値（履歴要求・気まずさ保護）がない。集計が変わるのは 01 で許容済み。
- **代償は 03 で明記**: 調査（この店の評価が消えた経緯）はできなくなる。

#### 店に公開用 UUID を持たせるか

- **困った点**: お誘いの `Event` は URL 列挙を防ぐため UUID を持った。店はどうか。
- **仮の選択**: 持たない。店の画面は**すべてログイン必須**（一覧がログイン必須なので詳細も同様）で、
  ログインした人にはリストで全店見えるのが仕様。隠すものがないので列挙対策が不要。03 で確定。
