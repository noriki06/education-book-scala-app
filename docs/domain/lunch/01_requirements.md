# <お店> — 要件定義

## 受け取った要求

「会社の周りのどの店がいいか、部署のみんなが知っていることを見えるようにしたい。
知らない誰かの点数より、一緒に働いている人の『ここ好き』のほうが信用できる。

マップか、現在地周辺の店のリストがあって、行った店の評価を書きたい人が書ける。
昔行った店の評価も書いていい。書くのは星と、何時頃に行ったか、並んでいたか、あとは一言。
コメントには書いた人の名前が出る。それだけでいい。

会員が好きなもの・嫌いなものを登録できて、『このメンバーだとここがいいかも』と
提案してくれるとうれしい。出てくるのは高評価の店と、初来店になる店の2つくらい。
2時にランチに行くことも多いから、時間で絞って空いていそうな店が分かるとありがたい。
こういう毎日開く使い方だと、URL だけだと使いにくい。アプリみたいに手元に置いておけるようにしたい。

これは別のアプリではなく、Osasoi（お誘い）の機能の拡充。
スタンプ・称号・『誰も行っていない店が光る』みたいな要素はいらない。
訪問を位置情報で証明するのも、店が乱立していて難しそうだからやらない」

（項目の細かい条件と、要求からの読み替えは、質問リストの仮回答で確定させる）

## 確認したいこと（質問リスト）

| 質問 | 今回の回答（仮） |
|---|---|
| Osasoi（お誘い）との関係は | **別アプリではなく Osasoi の機能拡充**。同じアプリの中の別ドメイン（コンテキスト）として設計する。ただし**お互いのデータは一切参照しない**（結合ゼロ。提案を本人向けにしたため、開示後の参加者すら使わない → 下の提案の行） |
| 店はどうやってマスタに載るか | **誰かが評価を書いた店だけ**が載る。評価を書くとき地図APIで検索して店を確定し、そのとき初めてマスタに写す（相手側 ID・店名・位置）。**検索で見つからない店は、名前と大まかな場所だけで手で足せる**（相手側 ID は無しを許す）。周辺全件の取り込み・定期的な再取得はやらない——部署の誰も知らない店が視界を埋める・書きたい店が無い・再取得で評価が孤児になる、の3つの害を避けるため |
| 同じ店が別名で2行できたら | 30人規模なので許容する。統合機能は作らない（気になったら管理者が DB で直す） |
| 評価は誰が・どの店に書けるか | ログインした会員なら誰でも・書きたい人だけ。**訪問の証明はしない**（自己申告）。昔行った店もよい |
| 評価に書くことは | **3段階（また行きたい／ふつう／いまいち）だけで送信できる**。時間帯（区分値: 〜11時台／12時台／13時台／14時以降）・並んだか（並んだ／並ばなかった）・一言（100字まで）は**すべて任意**（昔の店は時間帯を覚えていないのが普通のため） |
| 要求文の「星」は5段階では | 要求文は段階数を指定していない。**記名の身内では星2が押せず4〜5に潰れて平均が機能しない**ため、3段階で受ける。平均点は出さず「また行きたい N人」と**人数**で見せる |
| 同じ店に何回も書けるか | 書ける（行くたびに書いてよい）。ただし「また行きたい」は**人数**で数え（同じ人が10回書いても1人）、混雑は**件数**で数える——集合知の主語は「何人が」であって「何回」ではないため |
| 「空いていそうな店」はどう見せるか | **断定しない**。「14時台に行った3人のうち、並んだのは0人」と件数ごと見せる。その時間帯の声が**2件未満なら出さない**（「まだ声がありません」）。混雑の集計は**投稿から6ヶ月以内**の評価だけ（混雑は腐るため）。時間帯フィルタは「その時間帯に行った人の声だけを見る」絞り込み |
| 「ここがいいかも」の提案はどう出すか | **本人向けの常時表示**に読み替えた——店リストの上に「みんなが『また行きたい』と言っている店1件＋あなたがまだ評価していない店1件」。**お誘いのイベント・参加者とは連動しない**（理由は判断メモ: 開示後では遅すぎる／参加者の否定情報が逆算できる／おまけが主機能に依存を作る）。「このメンバーだと」「苦手の考慮」は判断が変わる条件へ予約 |
| 好きなもの・嫌いなものの登録は | **今回はやらない**。「好き」は提案ロジックのどこにも使われず、「苦手」との突き合わせには店の分類マスタと管理する人が生えて、おまけが主機能より重くなる。要望が続いたら第2弾で検討する（その場合もアレルギー対応は保証しない前提） |
| 「あの人」を決める仕組み（常連バッジ・フォロー等）は | **作らない**。一言に書いた人の名前が出るだけ |
| 評価の編集・削除は | 本人はいつでもできる。ただし集計は**現在有効な評価だけ**から導出するので、過去に見た数字と食い違いうる（それでよしとする） |
| 画面はマップかリストか | **リストのみ**（近い順）。載る店は評価された数十件で、「どこにあるか」より「誰が何と言ったか」が主役。地図UIは PWA での実装が重い割に効かないため作らない。要望が出たら検討 |
| 入口は | **PWA**（ホーム画面に追加できる Web アプリ。アプリ全体の決定）。**PWA はインターネット公開とは別論点**——公開の可否は未確認のまま（→ invite 01 質問リスト）。**PWA にしてもプッシュ通知は作らない**（「通知はチャンネル投稿だけ」の整理は通知手段によらず有効 → invite 判断20） |
| 検索の中心（会社の位置）は誰がどう決めるか | 「検索の中心を決める人」（部署の誰か）が決め、環境変数で持つ（お誘いの告知先チャンネルと同じ形） |
| 通報・他人の評価の削除は | **作らない**。消せるのは本人だけ。30人規模なら口頭と Slack で対処し、データの修正の問い合わせは管理者が DB で対応する |
| 最初は評価ゼロでは（コールドスタート） | 機能では解かない。**リリース日に部署で「よく行く店を3件書く」15分の会**をやる（運用）。外部サイトの点数の取り込み・管理者による代理登録はやらない——「みんなが知っていること」でなくなるため |
| 要求文にない仮の呼称 | 「**店マスタ**」「**時間帯**」「**3段階**」「**一言**」は仮の呼称。特に「一言」は、お誘いの「コメント」（参加に添える・開示まで秘匿）と**別概念**のため別の語にした。業務の呼び方は未確認 |

## 業務フロー

[検索の中心を決める人（部署の誰か）]

1. 店を検索するときの中心（会社の位置）を決める
   （設定画面は作らず、デプロイ時の環境変数で実現する）。

[会員]

2. リスト（近い順）で店と評価を眺める。時間帯で絞ると、その時間帯に行った人の声だけが見える。
   リストの上に「また行きたいが多い店」「自分がまだ評価していない店」が1件ずつ出る。
3. 行った店（昔でもよい）の評価を書く。店は地図APIで検索して選ぶ
   （見つからなければ名前と大まかな場所で手で足せる）。
   3段階だけで送信でき、時間帯・並んだか・一言は任意。一言には名前が表示される。

[地図API（外部サービス）]

4. 検索のたびに店の候補と位置を返す。落ちていても、すでにマスタにある店の閲覧・評価はできる
   （止まるのは店の検索と新規の追加だけ）。

[会員]

5. 声を見て店を決める。誘いたくなったら Osasoi で誘いを立てる
   （場所欄に店名を書き写す。自動連携はしない）。

## 例外・ルール

- 店がマスタに載るのは、誰かが最初の評価を書いたときだけ。評価が1件も無い店は存在しない。
- 集計（また行きたいの人数・混雑）は現在有効な評価だけから導出し、保存しない。
  混雑は投稿から6ヶ月以内・2件以上のときだけ表示する。
- 「また行きたい」は人数で数える（同じ人が何回書いても1人）。混雑は件数で数える。
- 提案（また行きたいが多い店・まだ評価していない店）は保存せず、開くたびに導出する。
- お誘い側のデータ（イベント・参加・立案者）はこのドメインから一切参照しない。
  お誘い側もこのドメインを参照しない（結合ゼロ）。
- 一言は記名。承認・通報の仕組みは作らず、消せるのは本人だけ。
- 地図API が落ちても閲覧・評価はできる。出典表示などの利用条件は実装前に確認する。

## ドラフトの判断メモ（提出物ではない・レビュー用）

設計に関わる判断は 03 の付録Bへ引き継ぐ予定。この節は経緯の記録。

#### 要求文の出所

- 発注者との対話（壁打ち）を語り直したもので、発注者がレビュー済み。仕様値（星・2つくらい等）が
  文中に残るのは当時の発言のままのため。**読み替え（星→3段階、提案→本人向け）は質問リストで裁く**
  ——原文は直さない、という規約に従う。

#### 位置情報による訪問判定を捨てた

- 店が乱立するエリアでは GPS 精度で誤判定し、判定距離の調整に体験が振り回される。
  発注者も「難しい気がする」と判断。訪問証明をやめた結果、スタンプ・称号・制覇が連鎖して消え、
  **お誘い側の判断10（開催の事実を記録しない）も覆さずに済んだ**。

#### 提案を「参加者単位・開示後」から「本人向け・常時」に変えた（3周目監査）

- **困った点が3つ同時に出た**: ①開示は既定で開始30分前（直前ゆる募なら5分前）で、店を決めるには
  遅すぎ、しかも場所欄は編集不可・立案者は匿名なので反映する先がない（行き止まり）
  ②「参加者の誰も評価していない店」の提案は、記名公開の評価と突き合わせると
  **参加者の否定情報として逆算できる**（判断18が塞いだ穴を開け直す）
  ③提案をお誘いの画面に出すと、おまけが主機能に依存を作る。
- **選択**: 本人向け（また行きたい多数の店＋自分が未評価の店）を店リストに常時表示。結合ゼロ。
- **代償**: 要求文の「このメンバーだと」には応えない。判断が変わる条件へ予約し、
  やるなら開示・分類マスタ・情報漏えいの3点を再設計する。

#### 好き嫌いを今回やらない

- 「好き」は提案ロジックに使われていない（ドラフト内の不整合を監査が検出）。
  「苦手」は店の分類マスタ＋管理者を生み、おまけが主機能より重くなる。
- **代償**: 苦手（辛いもの・生魚等）を避ける提案はできない。第2弾候補。
  アレルギーは扱わない（提案した店で事故が起きたときにアプリが根拠にされるため、やるとしても保証しない）。

#### 店マスタを「評価された店だけ」にした

- 周辺全件の取り込みは、①部署の誰も知らない店（評価ゼロ）が視界の大半を占める＝要求の逆
  ②OSM に無い店が書けない ③再取得で店が消えると評価が孤児になる、の3つの害。
- **選択**: 評価の初回投稿で店がマスタに写る。見つからない店は手で足せる（相手側 ID 無しを許す）。
- **代償**: 同じ店が別名で2行できうる（許容）。「まだ誰も行っていない店を探す」用途は満たさない
  （それは Google マップの仕事）。

#### 評価を3段階・人数集計にした

- 記名の身内では星2が押せず、5段階は4〜5に潰れて平均が意味を失う。3段階なら中間が逃げ場になる。
  「また行きたい」は人数で数える——1人が10回書いた店が部署の総意に見えるのを防ぐ。
- **代償**: 「星4.6」のような並べ替えはできない（母数が小さいうちは元々意味がない）。

#### 同じアプリの別ドメイン・タイトル

- 発注者確認: **別アプリではなく Osasoi の機能拡充**。同じアプリの中の別コンテキスト。
  タイトルは `<お誘い>` と語感を揃えた `<お店>` でよい（要求文の語は「店」だが、発注者が確認済み）。
- ディレクトリは仮に `lunch`。コンテキスト記号は naming.md で確定するまで、本文では
  「このドメイン」と書く（`place` という未定義の記号を本文で使わない）。
