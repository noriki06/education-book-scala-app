# <調理管理> — 詳細要件定義

## 用語 — 全体の用語集に追加する呼称
| 呼称（これで統一する） | 何を指すか | 言い換えない |
|---|---|---|
| 未受け取り | 受取準備完了のまま閉店を迎え、会員が受け取りに来なかった注文 | 「破棄」「ノーショー」「店舗キャンセル」 |
| 混雑 | その店舗で調理中の注文が閾値以上ある状態 | 「ピーク」「繁忙」 |
| 会員側のキャンセル | 会員の操作で取り消された注文 | 「顧客都合」 |
| 店舗側のキャンセル | 店舗の都合で取り消した注文 | 「店都合」「お店キャンセル」 |
| キャンセル理由 | 取り消しの説明。会員向けと店舗向けで内容が異なる | 「備考」「メモ」 |

「未受け取り」と「キャンセル」は、**作ったかどうか**で区別する。
作ったが渡せなかったものが未受け取り、作る前に取り消されたものがキャンセル。

「会員側」と「店舗側」は、**誰が取り消したか**で区別する。

## EntityModel

新しいエンティティは作らない。既存の `Order` に区分値2つと属性2つを追加する。

```scala
case class Order(
  // …既存のフィールド…
  state:               Status,                // 注文の状態
  cancelReasonForUser: Option[String] = None, // 会員に表示するキャンセル理由（今回追加）
  cancelReasonForShop: Option[String] = None, // 店舗に表示するキャンセル理由（今回追加）
  // …
) extends EntityModel[Id]

object Order:

  /** 注文の状態 */
  enum Status(val code: Short) extends EnumStatus[Short]:
    case IS_CANCELED_BY_USER extends Status(code =  -1) // 会員側のキャンセル
    case IS_CANCELED_BY_SHOP extends Status(code =  -2) // 店舗側のキャンセル（今回追加）
    case IS_NOT_PICKED_UP    extends Status(code =  -3) // 未受け取り（今回追加）
    case IS_RECEIVED         extends Status(code = 100) // 受付
    case IS_COOKING          extends Status(code = 200) // 調理中
    case IS_READY            extends Status(code = 300) // 受取準備完了
    case IS_PICKED_UP        extends Status(code = 400) // 受け渡し完了
```

**ここで型が語っていること**

- code のマイナス側が終了、プラス側が進行中。並べるだけで注文の終わり方が3通りあると読める
- 100 刻みにしたのは、将来の状態を間に挟めるようにするため
- `IS_PICKED_UP` と `IS_NOT_PICKED_UP` が同じ語の肯定・否定。渡せたか渡せなかったかが対で読める
- キャンセル理由は `Option[String]`。自由記載とし、区分値にはしない（→ 付録B）
- 誰がキャンセルしたかは `state` が持つ。理由の属性は **表示先** で分かれており、役割が重ならない

**型では守れない決めごと**

- 未受け取りにできるのは受取準備完了の注文だけ。受付・調理中からは遷移できない
- 未受け取り・キャンセルは終端。ここから他の状態には戻らない
- `cancelReasonFor*` を入れてよいのは、`state` がキャンセル（会員側・店舗側）のときだけ。
  未受け取りには書かない。閉店時に一括操作するもので、注文ごとの理由がないため
- 会員向けの理由は会員に見える。店舗向けの理由は社内にとどめる（表示先を取り違えない）

**状態遷移**

| 変更前 | 変更後 | きっかけ |
|---|---|---|
| 受付 | 調理中 | スタッフが「調理中」を押す |
| 調理中 | 受取準備完了 | スタッフが「受取準備完了」を押す |
| 受取準備完了 | 受け渡し完了 | スタッフが「受け渡し完了」を押す |
| **受取準備完了** | **未受け取り** | **閉店時、スタッフが一括で操作する（今回追加）** |
| 受付 | 会員側のキャンセル | 会員の取り消し |
| 受付 / 調理中 | **店舗側のキャンセル** | **スタッフが取り消す。理由を書く（今回追加）** |

**保存されるデータの例**

| 注文 ID | 状態 | cancelReasonForUser | cancelReasonForShop | どうなったか |
|---|---|---|---|---|
| 3001 | 受け渡し完了 | `None` | `None` | 時間どおり受け取られた |
| 3012 | **未受け取り** | `None` | `None` | 作ったが来なかった。理由は書かない |
| 3020 | 会員側のキャンセル | `None` | `None` | 会員が自分で取り消した |
| 3033 | **店舗側のキャンセル** | 材料の都合により<br>お作りできませんでした | パティ在庫切れ<br>18:40 店長判断 | 会員には謝罪文、店舗には事実を残す |

3033 が、理由を2つ持つ意味を示している。
会員に「パティ在庫切れ」とだけ返すわけにはいかず、
店舗の記録に謝罪文だけを残しても後から原因が分からない。

## <複数のエンティティにまる判定ルール>

### 注文一覧の並び順

1. その店舗の注文のうち、受付・調理中・受取準備完了のものを集める
2. 調理中の件数を数える
3. 閾値以上なら、受け取り時間の近い順に並べる
4. 閾値未満なら、通常の並び順（受付が古い順）で返す

混雑かどうかは保存しない。一覧を返すたびに数えて判定する。

### 閉店時の一括操作

1. その店舗の注文のうち、受取準備完了のものを集める
2. すべて未受け取りにする

### 店舗側でキャンセルするとき

1. その注文が受付または調理中であることを確認する
2. `state` を店舗側のキャンセルにする
3. 会員向けの理由と店舗向けの理由を、それぞれ書き込む


## 置き場所（コンテキスト）

**判断：** 新しいコンテキストは作らない。何も動かさない。

**理由：** 新しいエンティティを作らないため、置き場所を決める必要がない。
触るのは `sales` の `Order` と `shop` の `ShopMenuStock` で、どちらも既存の位置のまま。

調理管理という新しいコンテキストを作る案も検討したが、採らない。
作っても自分のモデルを1つも持たず、salesのOrderとshopのShopMenuStockを呼ぶだけになる。
配線だけが1セット増えるだけになるため。

# 付録A：今回やらないこと
- **スタッフのログイン・権限・シフト管理。**
タブレットは店舗ごとに設置され、店舗を選んで使う。誰が操作したかは記録しない
- **未受け取り・キャンセルにした注文の返金処理。**
支払いの状態は変更しない。返金は既存の運用に任せる。
店舗都合のキャンセルは返金が必要になるが、`Payment` の設計は今回のスコープ外
- **受取準備完了になった後で渡せなくなったケース。** 運用で個別に対応する（→ 付録B 論点5）
- **混雑判定の閾値の店舗別設定。** 全店舗共通の固定値とする
- **調理時間の記録・分析。** 「調理中」から「受取準備完了」までの所要時間は測らない
- **キャンセル理由の集計。** 自由記載のみとし、区分値による分類はしない
- **キャンセル理由を書いた人の記録。** スタッフ個人を識別しないため、誰が書いたかは残さない


# 付録B：判断の記録

### 論点3：「混雑」を保存するか、都度計算するか

**判断：** 保存しない。一覧を返すたびに、調理中の注文数を数えて判定する。

店舗に「混雑中」というフラグを持たせる案もあった。
しかし混雑かどうかは調理中の件数から分かるので、保存すると同じ事実が2か所に現れる。
件数と食い違ったとき、どちらが正しいか判断できない。

スタッフが手で切り替える案も採らない。
いちばん忙しいときに操作を1つ増やすことになる。
切り替え忘れれば、並び順が実態と合わなくなる。

### 論点1：キャンセル理由を1つにするか、2つにするか

**判断：** 2つ持つ。会員に表示するものと、店舗に表示するものを分ける。

1つで済ませる案もあった。誰が取り消したかは `state` が持っているので、
理由は1つあれば足りるように見える。

しかし会員に見せる文章と、店舗に残す記録は同じ内容にできない。
「パティ在庫切れ 18:40 店長判断」を会員に返すわけにはいかず、
謝罪文だけを店舗に残しても後から原因が分からない。**読み手が違えば別の情報である。**

代償として、片方だけ埋まる組み合わせを型で防げなくなった。
`state` がキャンセル・未受け取りでないときは両方 `None`、という制約は文章で守る。

### 論点2：キャンセル理由を区分値にするか、自由記載にするか

**判断：** 自由記載（`Option[String]`）にする。

区分値なら集計でき、スタッフの入力も速い。
しかし選択肢にない理由は必ず出るため、結局「その他」＋自由記載欄が要る。
そうすると1つの理由に対してフィールドが2本ずつ、合計4本になる。

いま「なぜキャンセルが多いか」を分析する要求はないため、自由記載のみとする。
集計が要件になった時点で、区分値との併用に切り替える。

### 論点4：「未受け取り」を新しい区分値にするか、キャンセルで済ませるか

**判断：** 新しい区分値を追加する。

キャンセルで済ませれば区分値は増えない。
しかしそうすると、店舗が作らなかった注文と、作ったが取りに来られなかった注文が、同じ記録になる。

材料費が無駄になったのか、そもそも作っていないのかは、店舗にとって別の事実である。
売上の集計や廃棄の把握で区別が必要になる。

### 論点5：未受け取りにできる状態を、受取準備完了だけに限るか

**判断：** 限る。受付・調理中からは未受け取りにできない。

閉店時に受付や調理中のまま残っている注文は、店舗側が作れなかったということ。
これを未受け取りにすると、お客さんが来なかったという記録になり、事実と違う。
そうした注文は **店舗側のキャンセル** にして、理由を書く。

受取準備完了になった後で渡せなくなった場合（落として使えなくなった等）は、
今回は扱わない。作り終えている以上どちらの記録も事実と合わないため、
運用で個別に対応する。頻度が上がったら区分値の追加を検討する。

### 論点6：新しいコンテキストを作るか

**判断：** 作らない。

タブレット向けの機能なので「調理管理」コンテキストを作る案もあった。
しかし作っても自分のモデルを1つも持たず、`sales` の `Order` と `shop` の `ShopMenuStock` を呼ぶだけになる。

1つの画面が2つのコンテキストにまたがるのは問題ではない。
画面の単位でモデルを分けると、既存のモデルを分断することになる。
