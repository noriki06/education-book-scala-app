# <調理管理> — 要件定義

## 受け取った要求
「店舗のタブレットで、入った注文を見られるようにしたい。
『調理中』『できあがり』を押していく。 混んでいるときは、受け取り時間の近いものから作りたい。
急に材料が切れたら、その場で商品を売り切れにしたい。
お客さんが来なかった注文は、閉店時に一括で『未受け取り』として片付けたい。」

## 確認したいこと（質問リスト）
| 質問 | 今回の回答（仮） |
|---|---|
| 「未受け取り」にした注文の支払いはどうするか | 今回は何もしない。返金は既存の運用に任せる |
| 売り切れにした商品は、いつ提供可に戻すか | 店舗スタッフが手で戻す。翌日の自動復帰はしない |
| 調理を始めたあとに材料が切れたら、その注文はどうするか | その注文は作りきる。売り切れにするのは以降の注文向け |
| スタッフのログイン・権限・シフト管理は必要か | 今回は作らない。タブレットは店舗ごとに設置され、店舗を選んで使う想定 |
|「混んでいるとき」は誰がどう判断するか。|システムが判定する。調理中の注文数が閾値以上なら混雑とみなす|
|混雑時と通常時で、注文の並び順を変えるのか|変える。混雑時は受け取り時間の近い順、通常時は「今すぐ受け取り」を優先する|
| 店舗の都合で注文を取り消すことはあるか | ある。材料切れや機器の故障で作れなくなった場合。会員のキャンセルとは区別する |
| キャンセルの理由は誰に見せるか | 会員と店舗の両方。ただし**表示する内容は分ける**。会員には案内文、店舗には事実の記録 |
| キャンセル理由は選択式か自由記載か | 自由記載。選択肢にない理由が必ず出るため。集計は今回やらない |
| 店舗都合でキャンセルした注文の返金はどうするか | 返金は必要だが、`Payment` の設計は今回のスコープ外。既存の運用に任せる |
| 受取準備完了になった後で渡せなくなった場合は | 今回は扱わない。作り終えているため、未受け取りにも店舗キャンセルにも当てはまらない |


## 業務フロー
1. [会員] アプリで注文を確定し、支払う
2. [システム] その店舗の注文一覧に、新しい注文を「受付」として表示する
3. [システム] 調理中の注文数が閾値以上であれば、一覧を受け取り時間の近い順に並べる
4. [店舗スタッフ] タブレットで注文一覧を見て、次に作るものを決める
5. [店舗スタッフ] 調理を始めるとき「調理中」を押す
6. [店舗スタッフ] 調理中に材料が切れたら、その商品を「売り切れ」にする
7. [システム] 売り切れになった商品を、会員のアプリで選べなくする
8. [店舗スタッフ] 作れなくなった注文は「店舗側のキャンセル」にし、
   会員向けと店舗向けのキャンセル理由をそれぞれ書く
9. [システム] 会員のアプリに、会員向けのキャンセル理由を表示する
10. [店舗スタッフ] できあがったら「受取準備完了」を押す
11. [会員] 店舗で受付番号を見せて商品を受け取る
12. [店舗スタッフ] 商品を渡したら「受け渡し完了」を押す
13. [店舗スタッフ] 材料が入荷したら、売り切れにした商品を「提供可」に戻す
14. [店舗スタッフ] 閉店時、受け取りに来なかった注文をまとめて「未受け取り」にする

[例外・ルール]
 - 調理を始めたあとに材料が切れても、その注文は作りきる。売り切れにするのは以降の注文向け
 - 受け取り時間を過ぎても、システムは自動で「未受け取り」にしない。スタッフが閉店時に操作する
 - 売り切れは店舗ごとに設定する。他の店舗には影響しない
 - スタッフ個人は識別しない。誰が操作したかは記録しない
 - 未受け取りにできるのは、受取準備完了の注文だけ。
 - 店舗側のキャンセルができるのは、受付・調理中の注文だけ。受取準備完了になったものは作り終えている
 - キャンセル理由は会員向けと店舗向けで別に書く。
   会員には案内できない事情（在庫の内訳、担当者の判断）を店舗側だけに残すため
